Add stream retention for StreamSubscriptions: the new `retention_maxlen` config field bounds a subscription's broker stream so processed messages don't accumulate forever. After each batch the stream is trimmed. With more than one consumer group the Redis broker trims by `XTRIM MINID` at the slowest group's last-delivered position, so an entry a slow group has not yet read is never removed — but a group parked at `0-0` (a dead consumer, or a handler that was removed) holds the floor down and the stream keeps growing until that group is deleted. With at most one group the broker uses a plain `XTRIM MAXLEN`: this is a fixed-size cap, so if the lone handler falls more than `retention_maxlen` behind (catch-up on a pre-existing stream, an outage, a slow handler under a fast producer) the oldest unread entries are dropped. Trimming is approximate and size-based (no time-based TTL), off by default, and each built-in profile carries a default cap (`production`/`fast` 100,000, `batch` 500,000, `debug` 1,000, `projection` none — it reads the event store, not a stream). Custom `[server.profiles]` sections may set `retention_maxlen` too. Brokers without a persistent stream (inline) treat `trim()` as a no-op.
