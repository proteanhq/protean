`protean add` now splits the aggregate it plans across a generation-gap seam: a generated base (`aggregate_base.py`, structure and wiring) and a hand-owned subclass (`aggregate.py`, your invariants and behavior). Each planned file records an `ownership` marker (`generated` or `hand_owned`) on the change plan, so once apply lands a re-run of `add` can refresh the generated base without touching the hand-owned subclass. `add` still only previews the plan today.
