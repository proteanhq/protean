Seven aggregate design pattern pages now run their examples from `docs_src`, and tests check what each example does. The fixes below correct code that did not run as printed.

- Aggregate state machines: the example now defines `OrderPaid`, imports `Domain` and `ValidationError`, imports `invariant` from `protean`, and its events carry `order_id` as an `Identifier`.
- Encapsulate state changes: the "after" example is complete. The `atomic_change` example imports from `protean` and adds items through the aggregate. The event-sourced `Account` gets an `AccountOpened` event, an `open()` method and an `@apply` handler. The shipping address change uses a `ShippingAddress` value object.
- Factory methods for aggregate creation: the "after" example has its imports and elements, items are added through `add_items`, and the Stripe subscriber names its stream and defines `__call__`.
- Design small aggregates: the examples raise `ValidationError` instead of an undefined exception, define the `CustomerLoyalty`, `PlaceOrder`, `Inventory` and `TaskCompleted` elements they use, and import the base classes they subclass. The event handlers now stay with the aggregate that owns the event and issue a command (`AwardPoints`, `ReserveStock`, `RecalculateProgress`) to the other aggregate, whose command handler skips a repeat.
- Creating identities early: aggregates are built inside a domain context, the handler passes the fields the aggregate needs, and the API example defines `CreateOrderRequest`.
- Optimistic concurrency as a design tool: the retry loops open a fresh `UnitOfWork` for each attempt and catch `ExpectedVersionError` outside it. The old loops missed a conflict that surfaced when the unit of work commits. The seat reservation example no longer catches `ExpectedVersionError` in its handler, where catching it either does nothing or stops the framework's retry. The `reserve()` precondition raises `SeatAlreadyTaken` on the framework's retry, and the API example maps it to a 409 response.
- One aggregate per transaction: the `OrderPlaced` handler now lives in the `Order` cluster and issues commands, and the command handlers skip an order they have already applied. The old handler was registered on `Inventory` and never received the event. The `OrderPlaced` handler sends one `ReserveStock` per product, so two lines for one product are both reserved. The money transfer credit skips a transfer it has already applied. The example also defines `TransferMoney` and `CreditPolicy` and imports `ValidationError`. The bulk operations example is now an application service that opens one unit of work per order.
- Error handling guide: the "When auto-retry is not enough" paragraph now says a handler should not catch `ExpectedVersionError` itself, so the decision belongs in aggregate preconditions that run again on each retry.
