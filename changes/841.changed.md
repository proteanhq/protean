`protean ir diff` now downgrades an event-sourced aggregate's breaking field removal to safe when one of the events that rebuilds it has an upcaster-covered version bump and every rebuilding event whose payload changed is covered too. Replay rebuilds the aggregate, so the removal is earned-safe on the same terms as the events that replay it. An uncovered bump, a payload change made without a bump, or no bump at all leaves the aggregate breaking, and so does a covered bump on an `@apply` handler added in the same diff, which never rebuilt historical state. A rebuilding event that lost a field under the deprecation grace counts as uncovered: stored payloads still carry that field and the event rejects them, so replay cannot start. The payload question is answered from the event's fields in the two snapshots, so it also catches changes the checker reports nothing for: an existing field turning required, or a field dropping a `renamed_from` alias that stored payloads are still written under. A rename is inert only while the new field keeps the old shape, since the alias routes the old key to a field that still has to accept the value. A field type change stays breaking, because a stored snapshot can still hold the old value in a shape the new field accepts, so the aggregate loads from that snapshot and never replays through the upcaster. A new required field stays breaking too, because replay runs no required-field check and nothing in the IR shows whether an `@apply` handler assigns the field. An aggregate whose `stream_category` or identity field moved stays breaking as well: replay reads the stream `"{stream_category}-{identifier}"`, so moving either half leaves the whole history under a key the new code never asks for. That covers a change to the identity field's own shape, since the key carries its value as a string and an identity turned from `Float` into `Integer` asks for `account-5` where the history sits under `account-5.0`. The payload question follows a field into the value object it embeds, so dropping a field from that value object counts as a payload change even though the event's own field entry did not move. Inside a value object a `renamed_from` alias earns nothing, because alias resolution rewrites the event's top-level payload only, and a newly recorded `@invariant.post` counts as a payload change, because constructing the value object runs it against the stored nested dict. A classic table-backed aggregate is never touched by this path; `exclude` stays the only escape hatch there.
