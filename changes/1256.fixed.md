On the PostgreSQL and MSSQL adapters, a Unit of Work now runs as one real database transaction instead of buffering writes under an AUTOCOMMIT engine (ADR-0027). Reads inside a UoW now see the UoW's own pending writes (read-your-writes) through `filter`, `count`, `exists`, and `get`, and in-UoW uniqueness validation sees them too. The UoW is now atomic for every relational aggregate shape: rolling back a UoW that added a child-bearing aggregate no longer leaves an orphaned parent, and a domain write commits atomically with its outbox message (both are written on the same session and committed together). This brings PostgreSQL and MSSQL in line with the Memory and SQLite adapters, which already ran each UoW as a real transaction. The engine now runs at the default read-committed isolation, and a UoW holds a database connection for its duration, so keep units of work short and do no external I/O inside them.

Two related hardening fixes ship with it, on every adapter. A nested Unit of Work (one started while another is active on the same context) now joins the outermost transaction instead of committing or rolling back on its own, so nesting is safe rather than silently breaking atomicity. And an optimistic-concurrency conflict that a read surfaces inside a Unit of Work (through `filter` or `count`, because the read flushes pending writes) now raises `ExpectedVersionError` like the commit path, so the version-retry machinery handles it.
