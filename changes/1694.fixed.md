Nineteen guide pages now run their examples from `docs_src`: the consume-state guides, the compose-a-domain guides, evolving events, multi-domain applications, architecture fitness functions and the two pathway pages. Tests check what each example does. The fixes below correct code that did not run as printed.

- Activate a domain: the `g` example registers its cleanup with `domain.teardown_domain_context`, not the Flask name `teardown_appcontext`, defines the `open_log_file()` it calls, and skips the cleanup when no file was opened.
- Choosing adapters and production configuration: the Elasticsearch `database_uri` is a TOML table (`{ hosts = [...] }`). The old quoted string failed to parse. The search projection now has an identifier field.
- Initialize a domain: the string-reference example defines the `User` aggregate that `Account` refers to.
- Inspecting the IR: the first example is a complete domain that runs, and the sample output shows the `contracts` section and puts each element's `method_edges` under that element.
- Schema generation: the validate example writes the schema files before it reads them, and the sample schemas match the generated output (`minLength`, `maxLength`).
- When to compose: the FastAPI and console examples define their own domain. The Flask example pops the domain context it pushed, in `teardown_request`, and no longer reads a `LOGGING_CONFIG` key the domain does not have.
- Event handlers: the error handler reads the message type from `message.metadata.headers.type`, and the dead-letter queue example sets `subscription_type="stream"`, without which the queue stays off. The examples define the events, commands and aggregates they use.
- CloudEvents: the sample output shows the `id` and `sequence` values Protean produces and the `proteansequencetype` attribute, and notes that the event shown has no `proteancorrelationid` or `proteancausationid` because it was raised outside a command handler. The consuming and subscriber examples define what they use.
- Event upcasting and evolving events: each example defines its domain and the aggregate its events belong to, the event handler example uses an aggregate the page defines, and the lenient event example is complete. The name-splitting upcaster reads `customer_name` without a default, and the page says what happens when a stored event lacks `customer_name` or `amount`.
- Projections: the examples define the fields, value object and record they use.
- Query handlers: `OrderSummary` has the `customer_id` field the handler filters on, and dispatch runs after `init` inside a domain context, on records the example writes first. The typed query example is complete.
- Subscribers: the named-broker example configures the `analytics` broker, and the duplicate check uses `repo.exists(Q(...))`, because `find()` does not take keyword filters.
- Event sourcing pathway: the `placed` handler sets the aggregate's `id`, so an order loaded from the repository keeps it.
- Migrating between architectures: `@apply` takes no argument, aggregates are built through an `Order.place()` factory, and the events carry the fields the projector reads. The FastAPI endpoints add `DomainContextMiddleware`, without which the request has no active domain, and the CQRS command handler calls `order.place()` so the projector receives `OrderPlaced`.
- Multi-domain applications: the examples define the events, aggregates and commands they use, including a handler for the `CreateRecipient` command the subscriber issues. The Elasticsearch `database_uri` is a TOML table. The API tests call routes the app defines. The cross-domain test hands the published event to the fulfillment handler, because a domain in sync mode runs only its own handlers.
