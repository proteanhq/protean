Under the mypy plugin, a class decorated with an element decorator is a subclass of its Protean base class, as it is at runtime. A decorated element is accepted wherever a signature names the base (`domain.cache_for`, `BaseCache.add`, `x: BaseValueObject = Money(...)`), base properties such as `state_` bind to it, and `super().__init__(...)` in a decorated domain service reaches the base. Like the decorator, the plugin drops a mixin listed as a base. A class extending a decorated element takes its parent's fields as keywords. The synthesized `__init__` also takes plain annotations (`note: str`, typed `Any`), and an element with no fields gets one that takes no keywords. `BaseEntity` declares its fields keyword-only to type checkers, so mypy no longer reports "Attributes without a default cannot follow attributes with one". `@domain.query_handler` and `@domain.upcaster` classes now get their base too. mypy now reports a field that reuses a base-class attribute name with a different type as an `assignment` error instead of `no-redef`.

**Migration:** [mypy sees decorated elements as subclasses of their base](https://docs.proteanhq.com/reference/migration/v0-18/#mypy-sees-decorated-elements-as-subclasses-of-their-base)
