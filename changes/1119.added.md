Added `Custom`, a public field factory for a field over a custom Python type: `Custom(python_type, *, validators=(), serializers=(), **constraints)`. Pass the type plus the Pydantic validators (a `PlainValidator` parses a raw value into it, an `AfterValidator` checks it after) and serializers it needs, and it behaves like any built-in field: `required`, defaults, constraints, and `ResolvedField` reflection all work. Implement `to_dict()` on the type and it round-trips through save, reload, and event replay, because Protean's persistence and event payloads serialize through `ResolvedField.as_dict`; query filters serialize the same way, so `unique=True` and a filter carrying a live instance both work against a real database. `choices` is rejected at declaration, because a choice set would discard the custom type. The mypy plugin reads the type from the first argument, so `Custom(Color, required=True)` type-checks as `Color`. `Custom` ships Stable. A type that needs no Protean machinery still uses the raw `Annotated[YourType, Field(...)]` escape hatch. A reusable conformance check, `protean.integrations.pytest.custom_field_conformance.run_custom_field_conformance`, runs a `Custom` field against the whole contract (validation order, reflection, and the round-trip). The IR schema carries a `field_custom` definition, so a domain holding a `Custom` field still emits IR that validates. See the custom-fields reference page and ADR-0044. (#1119)
