**Breaking, custom database adapters.** `BaseDAO` is split in two. An adapter's DAO class implements the `DAOPort` protocol, whose operations `filter`, `count`, `insert`, `update`, `update_all`, `delete` and `delete_all` take the session as their first argument and leave it open. The Elasticsearch adapter ignores the session and writes at once. Its `has_table` takes no session. Protean wraps it in a `DAO` service from `protean.infra.dao`, which runs the save lifecycle and the capability checks, and commits or rolls back each standalone operation through the provider's new abstract `new_session()`, `commit(session)` and `rollback(session)`. A provider can also override the new `flush(session)`. The service's `update_all` takes the values as one mapping, and its `delete_all()` returns the number of rows deleted. A `save_if_absent` override becomes `InsertIfAbsentPort` with the `INSERT_IF_ABSENT` flag, and a provider that subclasses `SADatabase` directly declares that flag to keep `save_if_absent` returning `None` when two writers race. A provider that declares a flag whose port its DAO class does not subclass raises `ConfigurationError` when the `DAO` service is built: at table registration for a SQL provider, and at the first use of a repository otherwise. `from protean.port.dao import BaseDAO` raises `ImportError`, and `SessionProtocol.is_active` is a property. Code that uses repositories and `QuerySet` needs no other change, though a standalone read now commits its session.
