**Breaking.** Saving the same aggregate instance again in a later transaction, without
reloading it, now writes a new version. Events raised on it after the first
save get new ids (`<stream>-1.1` and so on). Before, the second save wrote the
version the instance already had. Event handlers that deduplicate by event id
then dropped the second event, and a stale copy loaded before the second save
could overwrite it without an `ExpectedVersionError`.

When a transaction commits, `_version` and `_next_version` on each saved
instance now match what a reload returns. Adding the same instance several
times inside one `UnitOfWork` writes one version for that transaction, and the
events raised between those adds are numbered within it (`0.1`, `0.2`). When a
transaction rolls back, each instance it saved gets back the `_version` it had
before the transaction. On a provider without transactions, such as
Elasticsearch, the rollback does not undo the write, so the instance instead
keeps the version it wrote, as it would after a commit. The same holds
when a transaction spans several providers and one fails to commit after
another has: instances saved through the provider that committed keep the
version they wrote. Unless another writer
saved the aggregate in the meantime, the instance can be changed and saved
again without a reload.

Reading an aggregate inside the transaction that saved it no longer drops the
saved instance from the `UnitOfWork`. Before, the read copy took its place, so
events raised on the saved instance were never stored or published.

Event-sourced aggregates track their versions from their events and are not
affected.
