`DatabaseModelPort` in `protean.port.provider` lists the three class methods Protean calls on an adapter's database model class: `from_entity()`, `to_entity()` and `to_records()`. `ProviderPort.model_for()` returns `type[DatabaseModelPort]`, and `ProviderPort.dao_for()`, `BaseDAO` and `LookupPort` take the model class as `type[DatabaseModelPort]`. `BaseDatabaseModel` satisfies the Port, so a model declared with `@domain.database_model` is unchanged. The memory adapter's `MemoryModel` subclasses the Port; the SQLAlchemy and Elasticsearch model classes satisfy it structurally, because their library metaclasses conflict with the Protocol metaclass. `BaseDAO` reads a stored value for the unique-key check in `save_if_absent()` through its own `_stored_value()`, which reads an attribute, instead of the model class's `_get_value()`. A DAO whose records are not objects overrides `_stored_value()`, as the memory adapter's `DictDAO` does. A third-party adapter whose `dao_for()` annotates `model_cls` as `type[BaseDatabaseModel]` fails mypy against the Port until it uses `type[DatabaseModelPort]`.
