**Breaking, custom database adapters.** `DatabaseModelPort` in `protean.port.provider` lists the three class methods Protean calls on an adapter's database model class: `from_entity()`, `to_entity()` and `to_records()`. `ProviderPort.model_for()` returns `type[DatabaseModelPort]`. `ProviderPort.dao_for()`, `BaseDAO` and `LookupPort` take the model class as `type[DatabaseModelPort]`. `BaseDatabaseModel` satisfies the Port. The memory adapter's `MemoryModel` subclasses the Port. The SQLAlchemy and Elasticsearch model classes satisfy it structurally, because their library metaclasses conflict with the Protocol metaclass. `BaseDAO.save_if_absent()` reads each unique-key value through the DAO's `_stored_value()`, which reads an attribute. It no longer calls the model class's `_get_value()`. A DAO with dict records overrides `_stored_value()`, as the memory adapter's `DictDAO` does. Without the override, `save_if_absent()` raises `AttributeError` on such records. mypy rejects a third-party `dao_for()` that annotates `model_cls` as `type[BaseDatabaseModel]`. mypy also rejects a DAO that reads a `BaseDatabaseModel` member, such as `meta_`, through `self.database_model_cls`. Declare the concrete model class on the DAO to fix it. On the memory provider, Protean raises a metaclass conflict `TypeError` on first use of a database model whose metaclass is not `type`, `abc.ABCMeta` itself or derived from the Protocol metaclass.

**Migration:** [A provider's model class is typed as `DatabaseModelPort`](https://docs.proteanhq.com/reference/migration/v0-19/#a-providers-model-class-is-typed-as-databasemodelport)
