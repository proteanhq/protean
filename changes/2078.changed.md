**Breaking, custom database adapters.** `DatabaseModelPort` in `protean.port.database` lists the three class methods Protean calls on an adapter's database model class: `from_entity()`, `to_entity()` and `to_records()`. `DatabasePort.model_for()` returns `type[DatabaseModelPort]`. `DatabasePort.dao_for()`, `DAOPort` and `LookupPort` take the model class as `type[DatabaseModelPort]`. `BaseDatabaseModel` satisfies the Port. The memory adapter's `MemoryModel` subclasses the Port. The SQLAlchemy and Elasticsearch model classes satisfy it structurally, because their library metaclasses conflict with the Protocol metaclass. mypy rejects a third-party `dao_for()` that annotates `model_cls` as `type[BaseDatabaseModel]`. mypy also rejects a DAO that reads a `BaseDatabaseModel` member, such as `meta_`, through `self.database_model_cls`. Declare the concrete model class on the DAO to fix it. On the memory provider, a database model with its own metaclass gets a metaclass derived from both its own and the Protocol metaclass.

**Migration:** [A provider's model class is typed as `DatabaseModelPort`](https://docs.proteanhq.com/reference/migration/v0-19/#a-providers-model-class-is-typed-as-databasemodelport)
