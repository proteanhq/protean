Added a `mysql` database provider, serving both MySQL and MariaDB through SQLAlchemy and PyMySQL. Install it with `pip install "protean[mysql]"` and point `database_uri` at `mysql+pymysql://` or `mariadb+pymysql://`. It declares `RELATIONAL | NATIVE_JSON`: MySQL 8 has a real `JSON` column type, and no array type, so a `List` field is stored as JSON the way the MSSQL provider already does. The capability-gated conformance battery passes against MySQL 8.4 and MariaDB 11.4 with `native_array` the only deselection, and both servers run in the `protean test -c FULL` matrix. Four things are set up front because MySQL's defaults are wrong for Protean and fail silently: tables are created `CHARSET=utf8mb4` with an accent- and case-sensitive collation (`utf8mb4_0900_as_cs` on MySQL, `utf8mb4_uca1400_as_cs` on MariaDB, which is the only name MariaDB before 11.4.5 knows), because the server default ignores case and accents and would make `exact`, `contains`, `startswith` and `endswith` match rows they should not; every `DateTime` maps to `DATETIME(6)`, because a plain `DATETIME` drops microseconds on write with no error; the engine opens at `READ COMMITTED`, because InnoDB's `REPEATABLE READ` default breaks the ADR-0027 Unit of Work contract; and a `String` with no `max_length` becomes `TEXT`, because MySQL cannot create a `VARCHAR` without a length. A string column that is a primary key or `unique=True` raises `IncorrectUsageError` naming the field when it has no length or exceeds 768 characters, which is InnoDB's 3072-byte index key limit in `utf8mb4`. The outbox claim and the bounded delete take the portable path: MySQL has `SKIP LOCKED` but no `UPDATE ... RETURNING`, and rejects a subquery that reads the table being deleted from. `collation` is a provider config key, validated against the charset at `domain.init()`; the charset itself is pinned to `utf8mb4`, since a narrower one cannot hold the 4-byte characters Protean stores. See the [MySQL reference](reference/adapters/database/mysql.md). (#1580)
