The message handling reliability pattern pages now run their examples from `docs_src`, and running them corrected what several pages taught:

- **Idempotent event handlers.** The handlers declared `part_of` an aggregate other than `Order`, so they never received `OrderPlaced`. They now use `part_of=Order`. The examples catch `ObjectNotFoundError` from `repo.get()`, which never returns `None`. They define the entities, events and repository methods they use, and assign a new list to a `List` field instead of appending in place.
- **Command idempotency.** A replayed command on an event-sourced aggregate does not raise `ExpectedVersionError` once the first copy has committed. Two copies running at once do conflict, but the handler's version retry runs the second copy again, so expected version alone does not stop a duplicate. The page no longer shows a `try/except ExpectedVersionError` inside a handler, which could never catch the error. Event handlers do not get the command's idempotency key, so the transfer example guards on `transfer_id`. The cached result must be JSON-serializable, and `idempotency.redis_url` is unset by default.
- **Classifying async processing errors.** The subscription that delivered a message retries a failed handler with a fixed delay. A stream subscription makes `max_retries` attempts in total, and an event store subscription retries `max_retries` times after the first failure. The outbox only retries publishing. `handle_error` runs after each failed attempt. Handlers that react to another aggregate's events set `stream_category`. A subscriber's `handle_error` receives the raw payload `dict`.
- **Designing for concurrent event processing.** Solution A works only when the creation event is written first. Solution B uses the current process manager API, and its association handler starts the process, so an early association event is no longer dropped. Solution C's unique constraint raises `ValidationError` at add, or `TransactionError` at commit when two runs race, and the handler's version retry catches neither; the handler now checks for an existing client first.
- **Calling external systems from handlers.** The partner notification sends `confirmed_at` as an ISO string, since a `datetime` is not JSON-serializable. With sync event processing, a failed call after the commit raises to the caller while the confirmed order stays saved.
- **Coordinating long-running processes.** An event that arrives before the process manager exists is skipped and never redelivered. The failure handlers call `mark_as_complete()` instead of `end=True`, which would end the process even when the handler's guard returns early.
- **Store positions reach handlers.** An event or command rebuilt from the store now keeps its `_metadata.event_store`, so a handler sees the message's `position` and `global_position`. Before, `_metadata.event_store` was always `None` in a handler, which broke the Strategy 2 example on the idempotent event handlers page. Writing a rebuilt message again stores no copied positions; the store assigns new ones.
