**Breaking.** An aggregate, entity or projection with `identity_type = "integer"` now builds its model on the SQLAlchemy providers (SQLite, PostgreSQL, MySQL/MariaDB, MSSQL). Before, building it raised `TypeError: Integer() takes no arguments`. A declared `Auto` or `Identifier` holds its value as a string, and the integer identity column now turns it into an `int` before binding it, so it saves and loads on PostgreSQL under psycopg 3 too. Under the `uuid` strategy an integer identity is a 128-bit number that no SQL integer column holds, so `Domain.init()` now raises `ConfigurationError` for that case. The message names the element and the provider, and points to `identity_strategy = "function"` or `Auto(increment=True)`. The check also applies when the identifier sets `identity_type="integer"` or `identity_strategy="uuid"` itself. An identifier that sets `identity_type="integer"` on a domain whose `identity_type` is `string` used to save the number into a text column, and is now refused. On an `integer` domain, an identifier that sets `identity_type="string"` or `"uuid"` itself is refused too, because its column is an integer column. The same check runs when a SQL model is first built, so an element registered after `Domain.init()` is refused on first use. Event-sourced and abstract aggregates are not checked, and neither is an element whose custom database model declares the identity column itself. The memory and Elasticsearch providers are unchanged.

**Migration:** [An integer identity under the `uuid` strategy is refused on SQL](https://docs.proteanhq.com/reference/migration/v0-18/#an-integer-identity-under-the-uuid-strategy-is-refused-on-sql)
