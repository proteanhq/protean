Fixed three gaps in subscription status reporting, which feeds `protean subscriptions status`, the `protean.subscription.*` metrics, the Observatory and the `/readyz` probe. Outbox processors configured through `outbox.external_brokers` now get a row instead of being counted but never described; providers with `managed = false` no longer get a row for a processor the engine never started; and a `sequential_by` category now sums lag across its per-key partition streams instead of reading an empty base stream and reporting `unknown`. A lag that cannot be computed is also reported as `null` rather than falling back to the pending count, which made an unreadable subscription look healthy. For a partitioned category the consumer count is now the number of distinct workers rather than the sum across partitions, which reported one worker reading five partitions as five consumers. A partitioned category also gets the same `XRANGE` lag fallback the unpartitioned path has always had, so it reports a number on Redis before 7.0 instead of `unknown`. With `outbox.external_brokers` configured, each processor's row now counts only the rows bound for its own broker, instead of every row repeating one combined backlog.

**Breaking (reported values).** This changes the same surface `changes/832.changed.md` covers: `/readyz` `checks.subscriptions.details`, `protean subscriptions status`, and the `protean.subscription.*` gauges. `lag` is now `int | None` and reports `null` where it used to fall back to the pending count, so a monitor treating it as always-numeric needs a null branch; rows for outbox processors appear and disappear to match what the engine runs; and a partitioned category's consumer count is now the number of distinct workers rather than a sum across partitions, so it drops by roughly the partition count.

**Migration:** [`/readyz` reports an object where it reported a number](https://docs.proteanhq.com/reference/migration/v0-17/#readyz-reports-an-object-where-it-reported-a-number)
