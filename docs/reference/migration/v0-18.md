# Migrating to 0.18

!!! abstract "From 0.17 to 0.18"

Protean 0.18 right-sizes the runtime dependency surface. A plain
`pip install protean` no longer forces a web server, an ASGI stack, an
interactive REPL, and a project scaffolder onto every install. Those concerns
now live behind install extras, matching how the database and broker adapters
have always worked. See
[ADR-0029](https://github.com/proteanhq/protean/blob/main/docs/adr/0029-runtime-dependency-boundary-and-extras.md)
for the boundary and the rationale.

**This is a Tier-1 breaking change**, but a small one: nothing in your code
changes, and the fix when you hit it is a one-word extra. If a feature you use
now needs an extra, the CLI or the import tells you exactly which one.

- [A `ValueError` at commit is no longer reported as a version conflict](#a-valueerror-at-commit-is-no-longer-reported-as-a-version-conflict): it raises `TransactionError`, and the memory event store raises `ExpectedVersionError` itself
- [An omitted value object argument gets the value object's default](#an-omitted-value-object-argument-gets-the-value-objects-default): a flattened argument you leave out is no longer passed as `None`
- [A domain with no environment set logs at INFO](#a-domain-with-no-environment-set-logs-at-info): `PROTEAN_ENV=development` or `PROTEAN_LOG_LEVEL=DEBUG` brings the DEBUG lines back
- [A non-dict positional argument raises `TypeError`](#a-non-dict-positional-argument-raises-typeerror): so does a `renamed_from` of the wrong type
- [An event or command rebuilt from a stored message keeps its trace IDs and origin stream](#an-event-or-command-rebuilt-from-a-stored-message-keeps-its-trace-ids-and-origin-stream): `correlation_id`, `causation_id` and `origin_stream` come from the stored message

- [A failed IR build now fails `check`](#a-failed-ir-build-now-fails-check): the failure is an error in the result, not a logged traceback beside a `pass`
- [Domain traversal loads modules in name order](#domain-traversal-loads-modules-in-name-order): enrichers registered by traversed modules can run in a different order
- [A missing MySQL or MSSQL driver fails `domain.init()` with `ConfigurationError`](#a-missing-mysql-or-mssql-driver-fails-domaininit-with-configurationerror): it used to raise the driver's `ModuleNotFoundError`
- [The `database_model` element option is removed](#the-database_model-element-option-is-removed): register a custom model with `@domain.database_model(part_of=...)`
- [`protean test -c FULL` runs its service-free tests in parallel](#protean-test-c-full-runs-its-service-free-tests-in-parallel): only for work on Protean itself; `--workers 0` or `--sequential` keeps one process

## What moved behind extras

Five packages that used to be hard runtime dependencies are now install extras:

| Package(s) | Extra | Feature it gates |
|------------|-------|------------------|
| `fastapi`, `uvicorn`, `jinja2` | `protean[server]` | `protean observatory`, `protean.integrations.fastapi` |
| `ipython` | `protean[shell]` | `protean shell` |
| `copier` | `protean[scaffold]` | `protean new` |

Two convenience bundles are also available:

- `protean[cli]`: The full interactive CLI experience (`shell` + `scaffold`).
- `protean[all]`: Everything that used to ship in the core install
  (`server` + `cli`).

`import protean` and defining a domain, persisting through the memory adapter,
and running `protean server` (the async engine) need **none** of these: they
were already lazy, and they stay in the lean core.

## The one-line fix

If your project relied on the old fat install and you would rather not think
about which extras you need, install `all`:

```shell
pip install "protean[all]"
```

That restores every package that shipped in the 0.17 core. From there you can
trim to the specific extras you actually use whenever you like.

## What each feature needs now

You only need to act if you use one of these features **and** you install a
trimmed set of dependencies (for example in a production image that installs
`protean` without `[all]`):

- **Running the Observatory** (`protean observatory`) or using the FastAPI
  integration (`from protean.integrations.fastapi import ...`):

  ```shell
  pip install "protean[server]"
  ```

- **Opening the domain shell** (`protean shell`):

  ```shell
  pip install "protean[shell]"
  ```

- **Scaffolding a project** (`protean new`):

  ```shell
  pip install "protean[scaffold]"
  ```

If you run one of these without its extra, the command fails with a clear
message naming the extra to install, not a raw `ModuleNotFoundError`:

```text
Error: 'protean observatory' requires the 'fastapi' package. Install it with 'pip install "protean[server]"'.
```

`bleach` stays in the core install. String and Text fields no longer sanitize
by default (see
[String and Text no longer sanitize by default](#string-and-text-no-longer-sanitize-by-default)),
but `bleach` still backs the opt-in `sanitize=True` path.

## cffi and greenlet left the core install

0.17 installed `cffi` and `greenlet` as hard dependencies, but nothing in
Protean imports either package. They only ever arrived as transitive
dependencies: SQLAlchemy 2.0 (the `postgresql`, `postgresql-psycopg2`,
`sqlite`, `mssql` and `mysql` extras) requires `greenlet` on common platforms, and `cryptography` requires
`cffi` (`sendgrid` pulls it directly, and `mysql` through `pymysql[rsa]`).

In 0.18 both are out of the core install. Their version floors moved onto the
extras that pull them (`greenlet>=3.2.3,<4` on the SQLAlchemy extras,
`cffi>=2.0.0` on `sendgrid` and `mysql`), so installing one of those extras
still resolves a version with wheels for the newest supported Python.
SQLAlchemy 2.1 no longer requires `greenlet`. The SQL extras keep it so that
an install at the SQLAlchemy 2.0 floor still works.

You only need to act if your own code imports `cffi` or `greenlet` and relied
on Protean to provide it. Declare the package in your own project instead.

## PostgreSQL defaults to psycopg 3

0.17 capped SQLAlchemy at `<2.1`, and `protean[postgresql]` installed
`psycopg2-binary`. In 0.18:

- The SQL extras accept SQLAlchemy `>=2.0.36,<2.2`, so an application that
  needs SQLAlchemy 2.1 can install them. The 2.0.36 floor is unchanged.
- `protean[postgresql]` installs psycopg 3 (`psycopg[binary]`).
- The new `protean[postgresql-psycopg2]` extra installs `psycopg2-binary`.

The driver follows `database_uri`:

| `database_uri` | Driver |
|----------------|--------|
| `postgresql+psycopg://...` | psycopg 3 |
| `postgresql+psycopg2://...` | psycopg2 |
| `postgresql://...` | psycopg 3 if it is installed, otherwise psycopg2 |

Protean resolves the plain `postgresql://` form itself. SQLAlchemy 2.0 reads
it as psycopg2 and SQLAlchemy 2.1 as psycopg 3, so leaving it to SQLAlchemy
would make the driver depend on which SQLAlchemy is installed. When the driver
a URL needs cannot be imported, `domain.init()` raises a `ConfigurationError`
that names the extra to install.

### Who is affected

- **You install `protean[postgresql]` and use a plain `postgresql://` URL.**
  A fresh install (a new Docker image, a CI run) now gets psycopg 3, and your
  application runs on it. Protean's own queries behave the same on both
  drivers. Raw SQL you run yourself through the session can see psycopg 3's
  differences, for example in how some Python types are adapted. See the
  [psycopg 3 differences](https://www.psycopg.org/psycopg3/docs/basic/from_pg2.html)
  guide.
- **You want to stay on psycopg2.** Install `protean[postgresql-psycopg2]`
  and write `postgresql+psycopg2://` in `database_uri`. The explicit URL keeps
  psycopg2 even when psycopg 3 is also installed.
- **You upgrade in place with both drivers installed.** A plain URL moves to
  psycopg 3, because psycopg 3 comes first. Pin the driver in the URL if you
  want to control when that happens.

### Why it was not put behind a flag

The `postgresql-psycopg2` extra and the `postgresql+psycopg2://` URL already
select the old behaviour, so a flag would be a third way to say the same
thing.

## werkzeug left the core install

0.17 used Werkzeug's `LocalProxy`/`LocalStack` to back `current_domain`,
`current_uow`, and `g`. In 0.18 these context locals are backed by stdlib
`contextvars`, and `werkzeug` is no longer a core dependency.

For nearly all code this is transparent: the same push/pop nesting, the same
proxy behavior, and the same async support (in fact, `contextvars` follows
asyncio tasks and `await` boundaries natively). The public surface of
`current_domain`, `current_uow`, and `g` is unchanged.

You only need to act if your own code depends on Werkzeug-specific details of
the proxy or stack, such as inspecting the underlying `LocalStack` directly.
Internal helpers like `_domain_context_stack` and `_uow_context_stack` remain
private and have changed their implementation type.

## `check` and `verify` machine output changed shape and exit codes

`protean check --format json` and `protean verify --json` now emit one shared,
versioned [result envelope](../cli/conventions.md) and adopt one exit-code
convention (that other commands can converge onto later). `check`'s JSON output
has shipped before (0.15.0; the diagnostic schema and `[lint].level` gating
landed in 0.17.0) and `verify` is new in this cycle, but Protean is still
pre-1.0 and neither has a stability guarantee yet, so this is a direct
correction rather than a deprecation-managed break. You only need to act if you
already parse `check --format json` or `verify --json` output, or branch on
their exit codes.

**The JSON shape.** `check --format json` was the raw `Domain.check()` document
(`domain`, `status`, `errors`, `diagnostics`, `counts` at the top level). It is
now the envelope:

```json
{
  "version": "0.1.0",
  "status": "fail",
  "data": { "domain": "...", "status": "warn", "errors": [], "counts": {} },
  "diagnostics": [ "..." ]
}
```

The check report moved under `data`; `diagnostics` is at the top level. A
consumer reading `counts` now reads `data.counts`; one reading `diagnostics`
reads the top-level `diagnostics` (unchanged path). `verify --json` gained the
same frame: its old `{verdict, stages}` is now under `data`.

The `sarif` and `github-annotations` formats are unchanged: they are external
standard schemas and are not wrapped.

**`--level` no longer filters the JSON envelope.** `--level` is now a display
filter for the human `rich`/`--quiet` views only; the JSON, SARIF, and
github-annotations machine formats always carry the full, unfiltered set of
findings (a machine consumer can filter for itself). `diagnostics` can still be
empty on a `status="fail"` envelope, because a fatal error (a malformed `[lint]`
config, an unresolved reference) fails the run without ever building
diagnostics; check `data.errors` for those. If you relied on
`check --format json --level error` to pre-filter diagnostics, filter the
output with `jq` instead.

**The exit codes.**

`check`:

| Case | Old | New |
|------|-----|-----|
| Clean | `0` | `0` |
| Validator errors | `1` | `1` |
| Gating warning/info at the floor | `2` | `1` |
| Bad option, unloadable domain, malformed `[lint]` config | `1` | `2` |

The `1`-error-vs-`2`-warning split collapsed into a single findings-failure code
(`1`); the severity now lives in the envelope. Load and config errors became
usage errors (`2`).

`verify` shifted its codes up so `2` is reserved for usage:

| Case | Old | New |
|------|-----|-----|
| All green | `0` | `0` |
| Usage (bad/missing `--domain`, `--path` not a directory) | `1` | `2` |
| Init failed | `2` | `3` |
| Check failed | `3` | `4` |
| Tests failed | `4` | `5` |

**Clean stdout.** Under machine output, stdout now carries only the envelope,
exactly one JSON object. Logs and error lines go to stderr, so
`protean check --format json | jq` and `protean verify --json | jq` stay
parseable.

## `events catalog`, `subscriptions status`, and `projection status` JSON moved onto the envelope

`protean events catalog --json`, `protean subscriptions status --json`, and
`protean projection status --json` each printed a bare JSON array. They now emit
the same [result envelope](../cli/conventions.md) that `check` and `verify` use,
so one shape parses every command. The array moves under `data`, keyed by the
command:

| Command | Old top level | New location |
|---------|---------------|-------------|
| `events catalog --json` | array of events | `data.events` |
| `subscriptions status --json` | array of subscriptions | `data.subscriptions` |
| `projection status --json` | array of projections | `data.projections` |

A run that read the array at the top level now reads it under its `data` key:

```json
{
  "version": "0.1.0",
  "status": "pass",
  "data": { "events": [] },
  "diagnostics": []
}
```

All three are pre-1.0 with no stability guarantee, so this is a direct
correction with no deprecation window. You only need to act if you already parse
one of these `--json` outputs: read `data.events`, `data.subscriptions`, or
`data.projections` in place of the top-level array.

All three also adopt the shared exit codes and clean stdout on their error paths
under `--json`. Under `--json`, any usage or load failure (an unloadable
`--domain`, a missing/unreadable `--ir` file, or, for `events catalog`, neither
`--domain` nor `--ir` or both at once) is now the error envelope
(`status="error"`, the message under `data.error`) on stdout and exits `2`, so
`| jq` stays parseable.

Two things change without `--json` as well. The `events catalog` usage errors
(neither `--domain` nor `--ir`, or both at once) now print to stderr and exit
`2`, where they exited `1` before. A domain or `--ir` **load** failure without
`--json` is unchanged: it prints a human message and exits `1`.

## The memory cache no longer raises on an absent key

**Behavioural break, memory cache only.** `remove(projection)`,
`remove_by_key(key)` and `set_ttl(key, ttl)` raised `KeyError` when the key was
not in the cache. They now do nothing, which is what the Redis cache has always
done: Redis' `DEL` and `PEXPIRE` are no-ops on a missing key. The port
documents the silent behaviour as the contract, so the two adapters answer
alike.

An expired entry counts as absent. A key whose TTL has run out is treated the
same as one that was never written, on both adapters.

### Who is affected

Anyone who used the `KeyError` as a presence check on a memory-backed cache.
That code no longer takes its `except` branch, and nothing tells you: the call
succeeds quietly. It is the only shape that breaks.

```python
# fragment
# Before: worked on the memory cache, never fired on Redis
try:
    cache.remove_by_key(key)
except KeyError:
    log.info("nothing cached for %s", key)
```

After:

```python
--8<-- "reference/migration/v0-18/001.py:remove_by_key"
```

Nothing inside Protean relied on the `KeyError`, so this only affects your own
code.

### What did not change

`set_ttl` still rejects an invalid TTL when the key is absent. A TTL that is
not a positive, finite number of seconds raises `ConfigurationError` whether or
not there is a key to apply it to, so a malformed TTL cannot hide behind a
missing key.

`get_ttl` now answers alike on both adapters too; see
[get_ttl returns None or math.inf instead of a raw sentinel](#get_ttl-returns-none-or-mathinf-instead-of-a-raw-sentinel).

### Why it was not put behind a flag

The behaviour was a divergence between two adapters of the same port, not an
intentional contract, so no program that runs on both could have depended on
it. A flag preserving the `KeyError` would have kept the divergence alive on
the adapter that is documented for development and testing, which is the one
place the inconsistency is least worth paying for.

## `get_ttl` returns `None` or `math.inf` instead of a raw sentinel

**Behavioural break, both cache adapters.** `get_ttl(key)` used to answer
differently depending on the adapter, and neither answer was easy to use. The
memory cache raised `KeyError` for a missing key and could never report a
never-expiring key. Redis returned its raw `PTTL` sentinels: `-2` for a missing
key, `-1` for a key with no expiry. A caller that wanted to work on both had to
handle an exception and two magic negatives.

Both adapters now answer the same three cases:

- `None` when there is no such key.
- `math.inf` when the key exists and never expires.
- the seconds remaining otherwise (unchanged).

An expired entry counts as absent, so `get_ttl` returns `None` for it, the same
way `get` does. `math.inf` only ever comes from Redis: the memory cache writes
every entry with a concrete TTL, so it has no never-expiring keys to report.

### Who is affected

Anyone who read `get_ttl`'s old return value directly.

```python
# fragment
# Before: two shapes, one per adapter
try:
    ttl = cache.get_ttl(key)          # memory: raises KeyError if absent
except KeyError:
    ttl = None
if ttl is not None and ttl < 0:       # redis: -2 absent, -1 no expiry
    ttl = None
```

After:

```python
--8<-- "reference/migration/v0-18/001.py:ttl_imports"
--8<-- "reference/migration/v0-18/001.py:get_ttl"
```

A `ttl < 0` check on the old Redis return no longer fires, because the negative
sentinels are gone. A `ttl < math.inf` check is the way to ask "does this key
expire".

### Why it was not put behind a flag

Like the absent-key change above, this was a divergence between two adapters of
the same port, not an intentional contract. `BaseCache` is a Provisional API, so
its signatures can still change without a deprecation period. Nothing inside
Protean read `get_ttl`, so only your own callers are affected.

## Cache key patterns are a glob on every adapter

**Behavioural break, memory cache.** `_get_all`, `count`, and
`remove_by_key_pattern` take a `key_pattern`. The memory cache used to compile
it as a Python regular expression, while Redis passed it to `SCAN ... MATCH` as
a glob. The same string selected different keys depending on which adapter you
ran, and a pattern that leaned on regex behaviour matched nothing once you
switched to Redis.

The memory cache now matches with `fnmatch`, the same glob language Redis uses.
`*` matches any run of characters, `?` matches one, `[...]` is a character class,
and other characters, including `.`, are literal. Adapters agree on `*`, `?`, and
literal characters; bracket negation and escaping can differ, so keep patterns to
the `name:::*` shape.

### Who is affected

Anyone who passed a regex-flavoured `key_pattern` to the memory cache. Cache
keys are `name:::identifier`, so most patterns are already a name and a `*`,
which is a valid glob and needs no change. A pattern that used regex syntax
needs rewriting:

```python
# fragment
# Before, on the memory cache: a regex (and the method was public then)
cache.get_all("user_profile:::.*")
```

After:

```python
--8<-- "reference/migration/v0-18/001.py:glob"
```

A literal `.` in a pattern used to match any character on the memory cache and
now matches only a `.`. `BaseCache` is a Provisional API, so this lands in a
minor release with no deprecation period.

## Cache `get_all` is now the private, unpaginated `_get_all`

**Breaking, both cache adapters.** The public `cache.get_all(key_pattern,
last_position, size)` is gone. It is now `cache._get_all(key_pattern)`: private
(the leading underscore), and it returns every matching entry in key order with
no pagination.

A cache is for point reads by key. Enumerating a match set, and paging through
it, is not what a cache is for, and offering offset pagination over it invited
use it cannot support: on a store with no native key order (Redis) every call
scans the whole keyspace, and paging a large set is quadratic. So the method is
marked private and scoped to what it is actually good for, a convenience for
tests and small, bounded stores.

It returns at most 1000 entries (`GET_ALL_MAX`). Past that it truncates to the
first 1000 in key order and logs a warning, so a store that outgrew the cache
surfaces as a warning rather than a silent partial read.

### Who is affected

Anyone calling `cache.get_all(...)`. The method no longer exists under that name,
and it no longer takes `last_position` or `size`.

```python
# fragment
# Before
```

## The IR schema is now v0.2.0

The materialized IR carries a new `method_edges` key on the elements that own
methods, so the schema version moved from `0.1.0` to `0.2.0`. Protean 0.18 then
moved it again, to `0.3.0` (see
[The IR schema is now v0.3.0](#the-ir-schema-is-now-v030)). A baseline written by
Protean 0.17 is at `0.1.0`, so it picks up the changes in both sections when you
regenerate it. Documents and
schemas validate both ways: a `0.1.0` document still passes the `0.2.0` schema
(`method_edges` is optional), and a `0.2.0` document still passes the `0.1.0`
schema. The `v0.1.0` schema stays published, so a pinned `$schema` URL keeps
resolving.

What does change is the checksum. Adding a key changes the canonical bytes, so a
baseline built under `0.1.0` cannot be compared against a live IR built by
Protean 0.18.

### Who is affected

Anyone with a committed `.protean/ir.json`. `protean ir check` now reports a
version mismatch and exits `3` instead of comparing checksums. The
`protean-check-staleness` pre-commit hook prints the same message and fails (it
exits `1` for every failure), so a CI job that gates on the hook goes red until
the baseline is regenerated.

```shell
protean ir show --domain <module> --canonical > .protean/ir.json
```

The pre-commit hook rewrites it for you if you run it with `--fix`.

Your domain code does not change. For this section, the regenerated document
differs only in `$schema`, `ir_version`, the checksum, the new `method_edges`
entries, and the `sanitize` key on String and Text fields. That key now appears
only for a field that passes an explicit `sanitize=True`, so it drops off every
field that left `sanitize` unset (see
[String and Text no longer sanitize by default](#string-and-text-no-longer-sanitize-by-default)).
A domain with a `Decimal` field also picks up the `0.3.0` changes to that field,
and the commit that adds the regenerated baseline needs the step in
[The IR schema is now v0.3.0](#the-ir-schema-is-now-v030).

### What a cross-version diff looks like

`protean ir diff` against a `0.1.0` baseline reports `method_edges` as added on
every element that has one, and `sanitize` as removed on every String/Text field
declared without an explicit `sanitize=`. Compatibility classification does
not read `method_edges` or `sanitize`, so `protean ir diff` and the
`protean-check-compat` hook classify neither as breaking. Regenerate
the baseline and diff two documents built by the same Protean version if you
want the noise gone.

## The IR schema is now v0.3.0

The IR used to record a `Decimal` field as `"type": "String"` and drop its
`precision` and `scale`. It now records `"type": "Decimal"`, plus `precision`
and `scale` when the field sets them:

```json
"total": {"kind": "standard", "type": "Decimal", "precision": 19, "scale": 4}
```

The `type` list in the `v0.2.0` schema is closed, so the new type needed a new
schema version: `ir_version` moved from `0.2.0` to `0.3.0`. Protean 0.17 wrote
`0.1.0`, so a baseline from 0.17 also picks up the `0.2.0` changes in
[The IR schema is now v0.2.0](#the-ir-schema-is-now-v020). A `0.2.0` document
still passes the `0.3.0` schema. A `0.3.0` document that holds a `Decimal` field
fails the `0.2.0` schema. The `v0.2.0` schema stays published.

### Who is affected

Anyone with a committed `.protean/ir.json`. `protean ir check` reports a version
mismatch and exits `3`, and the `protean-check-staleness` hook fails, until you
regenerate the baseline:

```shell
protean ir show --domain <module> --canonical > .protean/ir.json
```

The `0.3.0` IR also records what a save writes. A `Date` or `DateTime` field
declared with `auto_now=True` or `auto_now_add=True` carries that flag, and a
domain that registers enrichers gets a top-level `enrichers` section that lists
them by qualified name. `protean ir diff` reports both as changes, and neither
is breaking. If your domain has no `Decimal` field, no `Custom(decimal.Decimal)`
field, no `auto_now` or `auto_now_add` field and no enricher, the regenerated
baseline differs only in `$schema` and `ir_version`.

If it has one, commit the regenerated baseline. Until you do, `protean ir diff`
compares the old `String` entry with the new `Decimal` entry and reports a
breaking `field_type_changed` for each such field. Your data and your payloads
have not changed. The old baseline recorded each of these fields as `String`,
and the new one records it as `Decimal`.

The `protean-check-compat` hook compares the live IR with the baseline in the
`HEAD` commit, not with the staged file. So it also fails on the commit that
adds the regenerated baseline. Skip the hook for that one commit:

```shell
SKIP=protean-check-compat git commit -m "Regenerate the IR baseline"
```

### What changes in the generated contracts

The contract generators read the IR type, so the output for a `Decimal` field
changes:

| Generator | Before | After |
|-----------|--------|-------|
| JSON Schema | `{"type": "string"}`, plus `minimum` and `maximum` when the field set `min_value` or `max_value` | `{"type": "string", "pattern": ...}`, plus `x-precision` and `x-scale` when set. `minimum` and `maximum` are left off, since they only apply to numbers. |
| Avro | `"string"` | `{"type": "bytes", "logicalType": "decimal", "precision": p, "scale": s}` when `precision` is set (`scale` defaults to `0`); `"string"` when it is not, or when `precision` is `0` or smaller than `scale` |
| Protobuf | `string` | `string` (no change) |

A `Decimal` value is still written as a string in a JSON payload, so the JSON
Schema output matches what Protean sends, and Protobuf keeps `string`. In Avro, a `Decimal` field
with a precision moves from `string` to `bytes` with the `decimal` logical type,
so a consumer that registered the old schema needs the new one.

### How the IR writes `min_value` and `max_value`

A `decimal.Decimal` bound used to stop the IR build with a `TypeError`. It is
now written in a form JSON can hold:

| Field | Declared bound | Written as |
|-------|----------------|------------|
| `Decimal`, or `Custom(decimal.Decimal)` | `decimal.Decimal("0.010")` | `"0.010"`, a string that keeps every digit |
| `Integer` | `decimal.Decimal("10")`, or the string `"10"` | `10` |
| `Float` | `decimal.Decimal("0.5")` | `0.5` |
| any field | an `int` or a `float` | the same number, as before |

`Integer(min_value="5")` used to write `"5"`, which failed the schema. It now
writes `5`. The `0.3.0` schema accepts a number or a string for `min_value` and
`max_value`, but accepts a string only when the field `type` is `Decimal`. If a
field in your domain declares a bound in one of these forms, regenerate the
baseline as shown above.

### New in `ir diff`: `field_precision_widened`

On a `Decimal` field that stays `Decimal`, `ir diff` now compares `precision`
and `scale`. Raising `precision`, or removing it, with `scale` unchanged is
reported as a safe `field_precision_widened`. Lowering or adding `precision`, or
any change to `scale`, is a breaking `field_type_changed`. See
[Decimal precision and scale](../compatibility/index.md#decimal-precision-and-scale).

## `diff_ir()` checks every field of a published event

`diff_ir()` lists the breaking changes to published events in
`contracts.breaking_changes`, and sets `summary.has_breaking_changes` from that
list. It used to compare a published event's fields only when a field was
removed or renamed. A field that kept its name and changed its type, or changed
its `Decimal` precision or scale in a breaking way, was missed. So was a
required field added without a default. The compatibility report from
`classify_changes()` flagged all three, so the two disagreed.

The published-contract check now applies the same field rules as the
compatibility report. A published event where `amount` goes from
`Decimal(precision=19, scale=2)` to `scale=4` now gives:

```json
{
  "type": "contract_field_type_changed",
  "fqn": "shop.Placed",
  "field": "amount",
  "left": "Decimal",
  "right": "Decimal",
  "message": "Field 'amount' Decimal shape changed (scale from 2 to 4) in published event 'Shop.Placed.v1'"
}
```

and `summary.has_breaking_changes` is `true`. A field that keeps its name has
no `renamed_to` key. A required field added without a default gives a new
`contract_required_field_added` entry with `fqn`, `field` and `message`. Every
other contracts entry keeps its shape and message. See
[Published event contracts](../compatibility/index.md#published-event-contracts).

### Who is affected

- **Code that calls `diff_ir()` directly** and reads
  `contracts.breaking_changes` or `summary.has_breaking_changes`. A diff that
  reported no break can now report one.
- **Readers of `protean ir diff --format json`** that look at
  `contracts.breaking_changes` or `summary.has_breaking_changes`.

The exit codes of `protean ir diff` and the `protean-check-compat` hook do not
change, with one exception. Both already exited `1` on these changes, because
the compatibility report flagged them. An event version bump that an upcaster
covers is not an exception: the report marks the field change safe, but the
bump changes the event's type string, so `contract_type_changed` already made
the run breaking. The exception is a published event
listed in `exclude` in `.protean/config.toml`. `exclude` filters the
compatibility report, and it has never filtered the contract breaks. Take a
field that keeps its name on an excluded published event, and change its type
or its `Decimal` shape in a breaking way, or add a required field without a
default. That change used to exit `2` from `protean ir diff` and pass the hook.
Under `strictness = "strict"` it now exits `1` and fails the hook, as a removed
field on the same event already did. Under `strictness = "warn"`,
`protean ir diff` now exits `0` instead of `2`, and the hook still passes.

Three smaller changes come with this:

- In the JSON `compatibility` block, `field_name` is now filled for
  `field_type_changed` and `required_field_added`. For a rename it holds the
  old name. It used to be `null` for these two change types.
- The text output of `protean ir diff` prints a field break once. It used to
  print a break twice when both lists reported it with different wording, for
  example a renamed `Decimal` field whose scale changed.
- The `protean-check-compat` hook prints the contract breaks as well as the
  report's. A break on an excluded published event used to fail the hook with
  no break named.

### Why it was not put behind a flag

`diff_ir()` gave the wrong answer: it reported no breaking change on a
published event that had one. `protean ir diff` and the hook already failed on these
changes, so a flag would only preserve the wrong answer for direct `diff_ir()`
callers.

## `protean ir` rejects an unknown format value

`protean ir show`, `protean ir diff`, and `protean ir check` check `--format`
before they load anything. An unknown value prints the accepted ones and aborts:

```shell
$ protean ir diff --left baseline.json --right current.json --format=summary
Error: invalid --format: 'summary'. Choose from: text, json, event-model
Aborted.
```

Each command takes its own set:

| Command | Accepted `--format` values | Default |
|---------|---------------------------|---------|
| `protean ir show` | `json`, `summary` | `json` |
| `protean ir diff` | `text`, `json`, `event-model` | `text` |
| `protean ir check` | `text`, `json` | `text` |

### Who is affected

Anyone whose script passes a value outside that command's set. It used to fall
through to the command's default: `protean ir diff --format=summary` printed the
text diff, and `protean ir show --format=text` printed the full JSON. That was
silent, so a typo in a CI job or a value borrowed from a sibling command read as
success for as long as nobody compared the output to the flag.

The failure exits `1`, the same code every other argument error in these
commands uses. On `protean ir diff` that is also the breaking-changes code, so a
CI gate that branches on the exit code sees a usage error as a break until the
flag is fixed; the `invalid --format` line on stdout is what tells them apart.

The fix is to pass a value from the table. Nothing else about the commands
changed, and a script that already passed a valid value is unaffected.

## `protean new --pretend` is now `--dry-run`, and it writes nothing

**Flag rename and behavioural break, the `protean new` dry run only.** The flag
is `--dry-run` now, and `--pretend` (with its `-p` short form) is gone. Passing
`--pretend` is a usage error. `--pretend` was copier's name for the option; the
rest of the CLI already says `--dry-run`, and so does the `create_project` core
it calls (`dry_run=`).

The dry run also behaves differently. It used to render through copier's own
`pretend` flag, and everything around that render ran for real. So a dry run
reached the target directory before it printed anything: with `--force` it
cleared the target, and without `--force` on a non-empty target it raised
`FileExistsError`. Neither is something a preview should do.

`--dry-run` renders into a system temp directory and prints the
project-relative path of each file it would create, one per line, sorted. The
target directory is left alone whether or not it already has files in it, and
`--force` no longer clears anything under a dry run. The list it prints is the
same set of files an apply produces from the same inputs.

The preview is also complete now. `.protean/project.json`, `AGENTS.md`, the
`CLAUDE.md` bridge, and `.protean/dx-state.json` are written after the copier
render, so the old dry run never listed them even though an apply creates all
four.

### Who is affected

Anyone passing `--pretend` or `-p` to `protean new`. Pass `--dry-run` instead.

Anyone parsing the output of the dry run. It used to be copier's coloured
`create <path>` log, in copier's render order; it is now a plain list of
relative paths, sorted.

```shell
# Before: copier's own log, no manifest, no AGENTS.md
$ protean new myproject --pretend
Copying from template version None
    create  .gitignore
    create  docker-compose.override.yml
    ...

# After: one project-relative path per line, sorted, and the full set
$ protean new myproject --dry-run
.copier-answers.yml
.dockerignore
.env.example
...
.protean/dx-state.json
.protean/project.json
AGENTS.md
CLAUDE.md
...
src/myproject/domain.py
```

Anyone who used `--pretend --force` to clear a directory is also affected. That
was a side effect of how the dry run was wired, not a documented feature, but it
did delete files. Use `protean new <name> --force` without `--dry-run` if
clearing the target is what you want.

### Why it was not put behind a flag

A flag defaulting to the old behaviour would default to a preview that deletes
your files. There is no reading of a dry run under which that is the contract a
user asked for, so there is nothing to preserve.

## `protean new .` and `protean new ..` are rejected

**Input break.** A project name has to be a single directory segment now: a
non-empty string, not `.` or `..`, and with no `<>:"/\|?*` or whitespace. The
first two used to pass validation. Passing one raises `ValueError` before any
file is touched.

### Who is affected

Anyone calling `protean new .` expecting it to scaffold in place. It never did
that. `project_name` feeds the template, so `.` produced a project with no
package directory (`src/domain.py` instead of `src/<name>/domain.py`) and
`name = "."` in `pyproject.toml`, which no installer accepts. The generated tree
did not build.

```shell
# Before: rendered a tree that could not be installed
mkdir myproject && cd myproject && protean new .

# After: name the project, then work inside it
protean new myproject && cd myproject
```

The rule also closes a hole in `--force`. The clear removes the contents of
`<output_folder>/<project_name>`, so a name that escaped its segment (`.` or
`..`) pointed the clear at the output folder or its parent. Requiring a single
segment means the clear can only ever reach the project directory.

## `protean new` refuses a target symlinked out of the output directory

**Behavioural break, symlinked targets only.** `protean new <name>` writes to
`<output-dir>/<name>`. If something already at that path was a symlink, every
step followed it: `--force` cleared the directory the link pointed at, and the
render wrote its files there. A link pointing outside the output directory meant
files outside the output directory were deleted and written.

The command now resolves the target first. If it does not sit directly inside
the resolved output directory, the command stops with a `ValueError` before it
clears or writes anything. `protean.scaffold.create_project` raises the same
error, on apply and under `dry_run`.

### Who is affected

Anyone who symlinked a project directory to another disk or another checkout and
then re-ran `protean new` over it. Render into the real location and symlink to
it afterwards, or point `--output-dir` at the directory that actually holds the
project:

```shell
# Before: followed the link and wrote (or cleared) at /mnt/work/myproject
ln -s /mnt/work/myproject myproject
protean new myproject --force

# After: name the real location
protean new myproject --output-dir /mnt/work --force
```

A symlink is still fine when it resolves to a path directly inside the output
directory, say `<output-dir>/other-name`. One that resolves deeper, like
`<output-dir>/nested/other-name`, is refused too: the check is that the target's
resolved parent is the resolved output directory.

## `DAO.update()` and `QuerySet.update()` are deprecated

**A deprecation, not a break.** Both methods still work in 0.18. They now emit a
`RemovedInProtean10Warning` (a `DeprecationWarning` subclass) and are removed in
1.0.0. Nothing else about their behaviour changes.

`DAO.update()` and `QuerySet.update()` take a field patch and write it straight
to the store. That skips the aggregate: the change does not go through a
behaviour method, so the rule that owns the change and the events it should raise
never run. The replacement is to load the aggregate, call a method on it that
applies the change, and persist it with `repository.add()`.

### Single aggregate

```python
# fragment
# Before: patch-and-persist through the DAO
repo = domain.repository_for(Order)
dao = repo._dao
order = dao.get(order_id)
dao.update(order, status="shipped")
```

After:

```python
--8<-- "reference/migration/v0-18/002.py:single"
```

A child entity has no repository of its own. Load the aggregate root, change the
child through the root, and `repo.add()` the root.

### Many aggregates

`QuerySet.update()` patched every matched row in one call, but it was never one
transaction: it looped and persisted each row on its own. Load the matched
aggregates, invoke the behaviour method on each, and `repo.add()` each one.

```python
# fragment
# Before: bulk patch through the query set
repo = domain.repository_for(Order)
repo._dao.query.filter(status="pending").update(status="cancelled")
```

After:

```python
--8<-- "reference/migration/v0-18/002.py:many"
```

Each `add()` commits in its own transaction, which is the same granularity
`QuerySet.update()` gave you. Do not wrap the loop in one `UnitOfWork` to make
the batch atomic: every `Order` is its own consistency boundary, and
[one transaction, one aggregate](../../guides/change-state/unit-of-work.md#one-transaction-one-aggregate)
is the rule. If the whole sweep has to land or fail together, it is a backfill,
not domain behaviour.

### Large backfills

A one-off migration that rewrites a column across a whole table is an
infrastructure job, not domain behaviour, the same way a hard delete is. Do it at
the adapter or database level (a SQL `UPDATE`, an adapter-specific bulk write)
rather than reaching for the deprecated domain-level path.

## String and Text no longer sanitize by default

**Behavioural break, String and Text fields.** An ordinary String or Text field
that left `sanitize` unset used to run `bleach.clean()` on every value, so the
stored value was HTML-escaped. The default is now `False`: an unset field stores
the raw input. `sanitize=True` and `sanitize=False` still mean exactly what they
did.

Two shapes were never sanitized and so do not change: a field with a real
`choices=` value, and a String or Text used as a container content spec such as
`List(String(max_length=50))`. `upgrade-check` skips both, as listed below.

This is a fail-open change: where a field silently escaped its input before, it
now stores it verbatim. That matters because sanitization is a display-layer
concern. Escaping on write bakes one encoding (HTML) into stored data, corrupts
values rendered in any other context (a plain-text email, a JSON API, a CSV
export), and is not a substitute for encoding output where it is actually
rendered. The default now matches that: store the real value, encode at the
point of display.

### Who is affected

Anyone who relied on the old default to escape stored values, on a String or
Text field with no explicit `sanitize=`. After the upgrade that field stores the
raw input, and nothing tells you at runtime: the write succeeds.

`protean upgrade-check --opportunities` finds these sites for you once you are on
0.18.0. It reports each String/Text field that leaves `sanitize` unset, by
`module:line`, listing every one so the report works as a checklist. Unset means
either not passing `sanitize` at all or passing `None`, which the field layer
reads the same way.

What it skips, because none of these changed behaviour:

- A field that gives `sanitize` a real value either way, by keyword
  (`sanitize=True`) or positionally (`Text(True)`, `String(255, None, True)`).
  It declared its intent.
- A field with a real `choices=` value. Choice values were never sanitized.
  (`choices=None` is not a choices field, so it is still reported.)
- A `String`/`Text` used as a container content spec, as in
  `List(String(max_length=50))`. A container reads the inner spec's type and
  choices and never applies its sanitization, so the inner field was not
  sanitized before the flip either.
- A `String` or `Text` that is not Protean's. The scan resolves the name back to
  a `protean.fields` import, so `from sqlalchemy import String` is not reported
  and `from protean.fields import String as StringField` still is.
- Every field, if the domain sets `[field_defaults] sanitize = true`. That opts
  the whole domain back into the old behaviour, so there is nothing to migrate.

A field whose arguments are hidden behind a splat (`String(**opts)`) is also
skipped, because `sanitize` could be inside and a static scan cannot see it.
Check those by hand.

### The fix

Encode output where these values are rendered as HTML. That is the durable fix,
and it protects the values a write-time escape never could (a template that
renders the same field in an email or a CSV).

To restore the old behaviour instead, opt back in. For one field:

```python
# fragment
name = String(max_length=100, sanitize=True)
```

For a whole domain, set the domain-level default:

```toml
[field_defaults]
sanitize = true
```

Precedence is field kwarg > domain default > framework default, so a domain
default of `true` sanitizes every unset String/Text field, and a field can still
opt out with `sanitize=False`.

### Why it was not put behind a flag defaulting to the old behaviour

This is a deliberate deviation from the standard Tier-2 transition in
[ADR-0004](../../adr/0004-release-workflow-and-breaking-change-policy.md#tier-2-behavioral-breaks),
which is opt-in flag → warning window → default flip, with the flag defaulting
to the old behaviour. Here the default flips in a single release, there is no
per-field runtime warning, and the `[field_defaults] sanitize` flag defaults to
the **new** behaviour (you set it to `true` to opt back in). It is silent at
runtime: the write succeeds and nothing warns.

That deviation is intentional. Storing an HTML-escaped value is the wrong
default for a domain model, and `bleach` on write is not the security control it
looks like, so the old default was not a contract worth a multi-release
transition to preserve. A per-field runtime warning was rejected as noise on a
path that is usually harmless. The migration net is static instead:
`protean upgrade-check --opportunities` enumerates the exact sites (see above),
so the flip is discoverable at upgrade time even though it is silent at runtime.
This is not one of the two narrow single-release exceptions ADR-0004 already
lists (operational defaults, silent correctness bugs); it is a security-relevant
default flip settled on its own merits.

### Reloading data written under a different default

The `sanitize` decision is read from the active domain at validation time, and a
DB load, event-sourced replay, or serialization round-trip re-runs the
validator. So a value written while sanitization was off, then reloaded after
`[field_defaults] sanitize` is flipped to `true`, is cleaned on the way back in.
Because `bleach` can lengthen a string (`&` becomes `&amp;`), a value that fit
`max_length` on write can grow past it on reload and fail to load with
`... characters after sanitization, exceeding max_length`. Flip the domain
default with this in mind: it changes how already-stored values validate, not
just new writes. An explicit `sanitize=True` field does not have this hazard,
because it cleaned on write too, so its stored value already satisfies the bound
(see [ADR-0026](../../adr/0026-max-length-bounds-the-sanitized-value.md)).

## `choices` fields map to their declared column type

**The SQLAlchemy adapter builds a different column for a field with `choices`.**
Before 0.18 such a field got the adapter's fallback column, an unsized string
column. The adapter now builds the column from the type the choice values
share, the same column a field of that Python type gets without `choices`:

- String choices give `VARCHAR(n)`, where `n` is the field's `max_length`. This
  covers a `String` with `choices`, a `Status` over an Enum of strings, and a
  `String` whose `choices` is such an Enum.
- Integer choices give `INTEGER`. This covers an `Integer` with `choices`, an
  `IntEnum` class passed as `choices`, and a `Status` over an `IntEnum`.
- Float, boolean, `Decimal`, `date` and `datetime` choices give the float,
  boolean, numeric, date and date-time column of that database.

The rule follows the values, not the field. A `Float(choices=[1, 2])` has
integer values, so its column is `INTEGER`.

The old column was `TEXT` on MySQL and MariaDB, `VARCHAR(max)` on SQL Server,
and an unsized `VARCHAR` on PostgreSQL and SQLite. With a non-string column
there, an `Integer` with `choices` saved `2` and loaded back the string `"2"`,
which the field then rejected.

Two kinds of choices keep the old column: choices of more than one type, such
as `["a", 1]` or `[True, 1]`, and choices of one type that has no column
mapping, such as `bytes` values or a list of Enum members. An annotation that
starts with a `Literal` and joins another type, such as `Literal[1] | str`,
keeps the old column too. A union that starts with another type, such as
`int | Literal[1, 2]`, gets that type's column, as it did before 0.18. The Elasticsearch adapter does not change.

```python
# fragment
class Article(BaseAggregate):
    status: String(max_length=20, choices=["draft", "published"])  # VARCHAR(20)
    level: Integer(choices=[1, 2, 3], required=True)  # INTEGER NOT NULL
```

### Who is affected

New tables get the new columns. Protean never alters an existing table, so a
table created before 0.18 keeps its old columns until you change them. The
string columns work as they are. A non-string choices column (integer, float,
boolean, decimal, date or date-time values) holding text does not load back, so
change it.

The MySQL and MariaDB index check now measures these columns. A declared `Index`
over a `String` with `choices` counts its `max_length`:

- When Protean builds the table, the column used to be `TEXT`, so the index was
  rejected as unindexable. It now builds when the key fits.
- `protean schema render --indexes` used to count the field as zero bytes. An
  index that only fitted because of that is now rejected with
  `IncorrectUsageError`.

A `String(choices=...)` gets `max_length=255` by default, so its column is
`VARCHAR(255)`. Three string choices fields have no length: a `String`
declared with `max_length=None`, a `Text` with `choices`, and a `Status` that
sets no `max_length`. Their column is `TEXT` on MySQL and MariaDB, which MySQL
cannot index. An index over any of them is rejected when Protean builds the
table, and is now also rejected by `protean schema render --indexes`, which
passed it before.

### How to change an existing table

For a table named `article` with the two fields above, where `level` is
required:

=== "PostgreSQL"

    ```sql
    ALTER TABLE article ALTER COLUMN status TYPE VARCHAR(20);
    ALTER TABLE article ALTER COLUMN level TYPE INTEGER USING level::integer;
    ```

    PostgreSQL keeps `NOT NULL` when it changes the type.

=== "MySQL and MariaDB"

    ```sql
    ALTER TABLE article MODIFY status VARCHAR(20);
    ALTER TABLE article MODIFY level INTEGER NOT NULL;
    ```

    `MODIFY` replaces the whole column definition. Leave out `NOT NULL` and the
    column becomes nullable without an error.

=== "SQL Server"

    ```sql
    ALTER TABLE article ALTER COLUMN status VARCHAR(20);
    ALTER TABLE article ALTER COLUMN level INTEGER NOT NULL;
    ```

    `ALTER COLUMN` replaces the nullability too. Leave out `NOT NULL` and the
    column becomes nullable without an error.

=== "SQLite"

    SQLite ignores the length of a `VARCHAR`, so `status` needs no change.
    SQLite cannot change a column's type in place, so rebuild the table for
    `level`:

    1. Create `article_new` with the new column types.
    2. Copy the rows across with `INSERT INTO article_new SELECT ... FROM article`,
       using `CAST(level AS INTEGER)` for the integer column.
    3. Drop `article` and rename `article_new` to `article`.
    4. Create the old table's indexes again. Dropping a table drops its indexes.

For any other type, use the column the field's Python type gets without
`choices`, and add `NOT NULL` when the field is `required=True`.

Check first that every stored value fits the new type. A `status` longer than
20 characters makes the `ALTER TABLE` fail. A `level` that is not a whole
number makes it fail on PostgreSQL, MariaDB and SQL Server. MySQL 8 does not
fail: it rounds `'2.5'` to `3`.

## The InlineBroker no longer dead-letters a message its subscription owns

On the InlineBroker, a stream consumed by a `BrokerSubscription` or a
`StreamSubscription` now has one dead-letter destination: the `{stream}:dlq`
stream the subscription publishes. The broker's own nack ceiling and its native
dead-letter queue no longer apply to that stream. A nacked message is held and
redelivered instead, which is what Redis Streams already did. See
[ADR-0042](https://github.com/proteanhq/protean/blob/main/docs/adr/0042-subscription-owns-retry-and-dead-lettering.md).

### Who is affected

Almost nobody, and there is nothing to change in your code. The old behaviour
needed a `{stream}:dlq` publish that kept failing inside the same process, on an
in-memory test double. If you had that, a message the subscription was holding
eventually landed in the broker's native DLQ and showed up under the
`{stream}:dlq` name in `protean dlq list`. It no longer does: it stays held and
is redelivered until the DLQ publish succeeds.

A test that asserted such a message reaches `protean dlq list` (or
`broker.get_dlq_messages`) has to assert the hold instead. Drive the DLQ outage
with `retry_delay=0` so the held message comes back on the next read.

A stream consumed straight off the broker with no subscription is unchanged: it
still hits the InlineBroker's ceiling and lands in the native DLQ. Production
adapters are unchanged too. Redis Streams holds a nacked message pending and
Redis PubSub does not support nack, so neither had a second dead-letter
destination to reconcile.

### Why it was not put behind a flag

Two layers counting the same failure was the bug, and a flag that kept the old
path alive would keep the broker dead-lettering underneath the subscription.
This takes the silent-correctness-bug exception in
[ADR-0004](../../adr/0004-release-workflow-and-breaking-change-policy.md#tier-2-behavioral-breaks).

## Replay hazards on an event-sourced aggregate are now breaking

`protean ir diff` reports four changes it previously passed clean. Each one stops
an existing event-sourced aggregate being rebuilt from its events, and none of
them is a field change, so nothing in the checker had anything to say about them:

| Change | Reported as |
|--------|-------------|
| `is_event_sourced` turned on or off | `event_sourcing_changed` |
| An aggregate's `stream_category` moved | `stream_category_changed` |
| The aggregate's identity moved to another field | `identity_field_changed` |
| An `@apply` handler dropped while its event survives | `apply_handler_removed` |

### Who is affected

A domain that makes one of these changes and runs `protean ir diff` in a check or
a pre-commit hook. The command passed before and now exits non-zero.

If your domains make none of these changes, nothing about your diff output moves.

### What to do

Treat the report as correct and roll the change back, because each one strands
data that already exists:

- An aggregate writes to `f"{stream_category}-{identifier}"`, so **moving the
  stream category** leaves the whole history under the old name and a load of an
  existing aggregate finds an empty stream. Keep the old category. If the rename
  is genuinely wanted, copy or replay the existing streams under the new name
  first, as a data migration, outside the compatibility checker.
- **Moving the identity to another field** asks for a stream keyed by a value no
  writer ever used, with the same result. Keep the identity where it is.
- **Turning event sourcing on** leaves the aggregate's existing state as table
  rows that replay cannot rebuild; **turning it off** leaves it as a stream the
  table-backed loader never reads. Either direction needs a data migration
  first.
- **Dropping an `@apply` handler** leaves stored events of that type with nothing
  to apply them, and `BaseAggregate._apply_handler` raises on one with no
  handler. Keep the handler for as long as events of that type are in the store,
  even after you stop raising the event.

Where the change is deliberate and the data has been migrated by hand, the
config-level `exclude` list is the escape hatch, as it is for any break the
checker cannot verify:

```toml
[compatibility]
exclude = ["ordering.order.order.Order"]
```

### Why it was not put behind a flag

The checker's purpose is to report a change that strands stored data, and these
four do. Passing them clean was the bug. A flag that kept the old behaviour alive
would keep the checker silent about a domain whose aggregates can no longer load,
which is the case it exists to catch. This takes the silent-correctness-bug
exception in [ADR-0004](../../adr/0004-release-workflow-and-breaking-change-policy.md#tier-2-behavioral-breaks).

## Removing a field from an event-sourced aggregate needs `reserved`

`protean ir diff` reports removing a field from an event-sourced aggregate as
breaking, the same as for any persisted element. For an event-sourced aggregate
that removal is usually safe: its authoritative state is a stream of events, and
the snapshot is a rebuildable cache Protean discards and replays past when it no
longer constructs. But the removal is not safe on its own. A retained `@apply`
handler kept for a retired event can still assign the removed field, or call
its `add_<name>`/`remove_<name>` helper, and replay would raise on it.

Declare the removed name in `reserved` on the aggregate to earn the downgrade:

```python
--8<-- "reference/migration/v0-18/004.py:reserved"
```

`reserved` is a declaration the author adds to control how the removal is
handled, like `renamed_from` and `deprecated`. Like `renamed_from`, it also
carries a runtime effect; `deprecated` only changes the checker verdict:

- During replay only, an assignment to a reserved name is dropped instead of
  raising, so a retained handler for a retired event still rebuilds the
  aggregate. The live `raise_` path never takes this relaxation, so a write to a
  removed field on a new event still raises.
- For a removed association such as a `HasMany`, a retained handler may call the
  generated `add_<name>` or `remove_<name>` helper instead of assigning. During
  replay those calls are dropped too and return `None`. The child entities they
  would have added are dropped with them: the rebuilt aggregate does not have
  them. `get_one_from_<name>` and `filter_<name>` still raise, because a handler
  that reads the removed collection depends on it. On the live `raise_` path the
  helpers still raise `AttributeError`.
- A retained handler that calls such a helper has two more needs. The child
  entity class it builds has to stay in the domain, because deleting it breaks
  the handler and is itself a breaking `element_removed`. And the helper call
  needs `# type: ignore[attr-defined]`: type checkers do not know about
  `reserved`, so `mypy --strict` reports the helper as missing once the
  association is gone:

    ```python
    # fragment
    @apply
    def item_added(self, event: ItemAdded):
        self.add_items(OrderItem(name=event.name))  # type: ignore[attr-defined]
    ```

- The drop keys on the name alone. With a plain field such as `total` reserved,
  a call to `add_total` is dropped during replay too.
- `protean ir diff` downgrades the `field_removed` change to safe, cited
  `reserved`, when the aggregate is event-sourced on both sides and the removed
  name is reserved in the new snapshot. The rating assumes the retained
  handlers only write the removed name. A handler that reads the removed
  collection still breaks replay, and the diff cannot see that.
- The declaration has to stay. Taking a name back out of `reserved` on an
  event-sourced aggregate is reported as `reservation_removed`, breaking:
  replay stops dropping an assignment to the name and a call to its helpers, so
  a retained handler that still makes either raises again.
- Reusing a reserved name for a live field raises `IncorrectUsageError` at
  registration.
- A reserved name has to be a field name. An empty or private (`_`-prefixed)
  name raises `IncorrectUsageError` at registration.

Only the field removal is earned this way. A type change or a newly required
field on an event-sourced aggregate stays breaking, and the replay hazards above
(a moved stream category, a moved identity, a dropped handler whose event
survives) stay their own breaking changes.

## A RawIndex with an unknown dialect now raises

**Behavioural break, `Index.from_sql` and index DDL rendering.**
`Index.from_sql(dialect, ddl)` takes the dialect as a free string. A value the
framework does not render index DDL for used to be accepted at registration and
then dropped at every call site that matched the dialect by name. The aggregate
looked indexed and never got the index, on any dialect, with nothing said.

`Domain.init()` now rejects it. A `RawIndex` whose `dialect` is not one the
framework renders for raises `IncorrectUsageError`, naming the element, the index
(its name, or the DDL when it has no name), and the bad dialect. The dialect is
matched by exact string, so `"postgres"`, `"PostgreSQL"`, and `" postgresql"` are
all rejected: only `"postgresql"` renders.

The dialects the framework renders for are `postgresql`, `sqlite`, `mssql`,
`mysql`, and `mariadb`.

### Who is affected

Anyone who called `Index.from_sql` with a dialect name outside that set, most
often a typo. That declaration never produced an index, so the fix is to correct
the name:

```python
# fragment
# Before: accepted, then silently dropped, so no index on any dialect
Index.from_sql("postgres", "CREATE INDEX ix_data_gin ON outbox USING gin (data)")
```

After:

```python
--8<-- "reference/migration/v0-18/005.py:from_sql"
```

If you targeted a dialect Protean has no provider for, that DDL was never emitted
either. Remove the declaration, or wait for the provider.

### Why it was not put behind a flag

The old behaviour was a silent failure: the index the author declared was never
created. There is no reading under which accepting a name that renders nothing is
a contract worth preserving. The change moves the existing failure to the
declaration point, where the author finds it, and introduces no new one. This
takes the silent-correctness-bug exception in
[ADR-0004](../../adr/0004-release-workflow-and-breaking-change-policy.md#tier-2-behavioral-breaks).

## `protean schema render --indexes` rejects an unknown dialect

`--dialects` takes a comma-separated list, and an unrecognised name used to fall
through to the SQLite dialect. The command wrote a `.sql` file that looked
right, said the requested dialect in its header comment, and held DDL compiled
for a different database. It now raises:

```shell
$ protean schema render --indexes --dialects postgres
Error: Unknown index DDL dialect 'postgres'. Supported: mariadb, mssql, mysql, postgresql, sqlite.
```

`postgres` is the spelling that catches people: the dialect is `postgresql`.
The accepted set is the same one `Domain.init()` checks a `RawIndex` dialect
against, so a dialect you can declare is always one you can render.

### Who is affected

Anyone passing `--dialects` explicitly with a name outside that list. The
default (`postgresql,sqlite,mssql,mysql`) is unaffected, and so is every name
that was already valid. If a script has been silently producing SQLite DDL under
another name, it now fails instead, which is the point.

### Why it was not put behind a flag

The old behaviour had no correct use: there is no case where rendering SQLite
DDL under another dialect's filename is what the caller wanted. This takes the
silent-correctness-bug exception in
[ADR-0004](../../adr/0004-release-workflow-and-breaking-change-policy.md#tier-2-behavioral-breaks).

## The test-mode engine stops as soon as it is idle

`Engine(domain, test_mode=True).run()` and `protean server --test-mode` used to
run eleven 0.1-second cycles every time, so each run took at least 1.1 seconds.
Test mode now stops as soon as every subscription has run out of work. A run
with little to process finishes in a few milliseconds.

Test mode also pauses at most 10 milliseconds between a subscription's ticks,
whatever its `tick_interval`. A broker subscription used to wait a full second
before it saw the messages a handler had just raised.

The limits are unchanged. Test mode still stops after about a second when a
subscription keeps finding work, and it still waits up to five seconds for a
subscription to start. An event handler that failed counts as work while its
position waits for a retry, so a test with a failing handler still runs for
the full second.

### Who is affected

A test that relied on the engine running for a fixed time while nothing was
left to process. For example, a test that counted on an outbox message whose
publish failed being retried at its scheduled time within that second. Test
mode now stops before that time arrives. Assert on what the engine processed,
and run the retry path directly if the test is about retries.

### Why it was not put behind a flag

Test mode is for tests, and its documented job is to process the pending
messages and stop. How long it runs was never part of that contract, and
nothing a production engine does has changed.

## `protean server` and `protean observatory` apply `[logging]`

Single-worker `protean server` and `protean observatory` used to ignore the
`[logging]` section of `domain.toml`. The commands set up console logging
before the domain loaded, at the `PROTEAN_LOG_LEVEL` level or INFO.
`Domain.init()` then saw handlers on the root logger and skipped its own setup.
Both commands now call `Domain.configure_logging()` once the domain loads, the
way `--reload` and each multi-worker process already did. Your `level`,
`format`, `redact`, `per_logger`, `log_dir`, and sampling settings now take
effect, and engine logs carry `correlation_id`.

`--log-level` and `--log-format` now override only the level and the format.
The rest of `[logging]` still applies. `--log-config` still replaces the
section.

With several `--domain` values, `protean observatory` applies the first
domain's `[logging]` section.

### Who is affected

Anyone who runs single-worker `protean server` or `protean observatory`. Log
output changes on upgrade in these cases:

- **You have a `[logging]` section.** Its settings now apply: a JSON `format`,
  a different `level`, redacted fields, and rotating log files when `log_dir`
  is set.
- **You have no `level` setting.** With no `[logging].level`, no
  `PROTEAN_LOG_LEVEL`, and no `--log-level`, the level now comes from the
  environment: `PROTEAN_ENV`, then `ENV`, then `ENVIRONMENT`. When none is set,
  a plain `protean server` or `protean observatory` logs at INFO with colored
  console output, as it did in 0.17. Under `PROTEAN_ENV=development` it now
  logs at DEBUG, and under `PROTEAN_ENV=test` at WARNING. See
  [A domain with no environment set logs at INFO](#a-domain-with-no-environment-set-logs-at-info).
- **You have no `redact` setting.** The default redaction keys (`password`,
  `token`, `secret`, `api_key`, and others) now mask those fields in log
  records.
- **Your domain module sets up logging when it is imported.** The `[logging]`
  setup now replaces it. Set `PROTEAN_NO_AUTO_LOGGING=1` to keep your own setup.
- **A `[logging]` value is invalid.** A bad value, such as a numeric `level`
  or an unwritable `log_dir`, now stops the command with an error. It used to
  be ignored, because `Domain.init()` catches errors in its own logging setup.
  Multi-worker and `--reload` workers already failed this way.

A multi-worker run without `--log-level` also changes: the supervisor now
forwards worker records at the `[logging]` level, so `level = "DEBUG"` shows
DEBUG records it used to drop.

### Why it was not put behind a flag

Applying `[logging]` is the documented behaviour, and `--reload` and the
workers already did it. The old single-worker result was a bug.

## `protean server` workers apply the logging flags

`--log-level`, `--log-format` and `--log-config` now reach the worker processes
of `protean server --workers N` and `protean server --reload`. Each worker
applies them the way the parent does: `--log-level` and `--log-format` override
the level and the format of `[logging]`, and `--log-config` replaces
`[logging]`. A worker started after a reload gets the same flags.

Before this, the workers ignored the flags. Once the domain loaded, each worker
applied `[logging]` and `PROTEAN_LOG_LEVEL` only.

### Who is affected

Anyone who passes a logging flag to a multi-worker or `--reload` run, or sets
`PROTEAN_LOG_LEVEL` for one. The workers' log output now follows the flags. For example,
`protean --log-level DEBUG server --workers 4` used to drop worker DEBUG records
when `[logging]` set a higher level, and now shows them. With `--reload`, the
worker's level, format and `dictConfig` all follow the flags now.

Before the domain loads, a worker now sets up its logging the same way the
parent does. With no logging flag, it logs at `PROTEAN_LOG_LEVEL` from the
moment it starts. Before, it logged at INFO until the domain loaded, so it
dropped the DEBUG lines it wrote while loading the domain. With no logging
flag and no `PROTEAN_LOG_LEVEL`, the worker starts at INFO. With
`--log-format` alone, the worker uses that format from the start, and takes its
level from `PROTEAN_LOG_LEVEL` and then `PROTEAN_ENV`, as the parent does. With
`--log-config`, the worker applies only that `dictConfig`, and
`PROTEAN_LOG_LEVEL` does not override it.

### Why it was not put behind a flag

The flags are documented to set the log level, the format, and the
configuration of `protean server`. Ignoring them in the workers was a bug.

## `[lint]` and `[observatory]` tables now load

The config loader keeps only the top-level sections listed in its defaults, and
`lint` and `observatory` were not in that list. A top-level `[lint]` or
`[observatory]` table in `domain.toml`, a `[tool.protean.lint]` or
`[tool.protean.observatory]` table in `pyproject.toml`, or a `lint` or
`observatory` key in a `Domain(config=...)` dict was dropped without a warning.
Both sections are now loaded, so their settings take effect.

### Who is affected

- **You have a `[lint]` table.** `level`, `suppressions`, `rules` and the other
  `[lint]` keys now apply to `protean check` and `protean verify`, and every key
  except `level` applies to the IR builder too. A project that passed
  `protean check` can start failing, for example when `level = "info"` makes
  info findings gate, or when a custom rule listed in `rules` reports findings.
  Run `protean check` and adjust `[lint]`.
- **Your `[lint]` table has a malformed value.** A value that used to be
  ignored is now checked. These values are rejected:

    - a `[lint]` that is not a table
    - a bad `level`
    - a `suppressions` value that is not a table, or a suppression count that
      is not a non-negative integer
    - a `rules` value that is not a list of strings
    - a limit that is not a non-negative integer
    - a `check_*` flag that is not `true` or `false`

  `protean check` exits `2` and `protean verify` exits `4`. Building the IR
  raises `ConfigurationError` for the same values, except a bad `level`: the IR
  builder does not use `level`, so it does not check it. `protean ir show`, the
  MCP `check`, `validate` and `introspect` tools and the pre-commit hooks each
  report that error. `Domain.check()` raises it, even when the domain has
  validation errors. Code that calls `Domain.check()` directly and expects a
  result dict should catch `ConfigurationError`. Fix the value the error
  message names.
- **You commit a materialized IR.** `[lint]` settings change the IR's
  diagnostics, and the diagnostics are part of the IR checksum. `protean ir
  check` can report the committed IR as stale. Regenerate it.
- **You have an `[observatory]` table.** `trace_retention_days` now applies to
  trace persistence. The value goes through Python's `int()`: `3.9` becomes 3
  days, and `0` or a negative number turns trace persistence off. An
  `[observatory]` that is not a table, or a retention `int()` cannot convert
  (such as `"abc"` or `inf`), falls back to the default of 7 days.

Environment overlays such as `[test.lint]` were already loaded when
`PROTEAN_ENV` named that environment. The base table now loads too, and the
overlay is merged over it. If you have both `[lint]` and `[test.lint]`, the
effective settings under `PROTEAN_ENV=test` now include the `[lint]` keys the
overlay does not set.

### Why it was not put behind a flag

These tables are the documented way to configure `protean check` and trace
retention. Ignoring them was a bug.

## Logging filters now run for records from child loggers

Protean attached `ProteanCorrelationFilter`, `OTelTraceContextFilter` and
`ProteanRedactionFilter` to the root logger only. A
logger's filters run only for records logged on that logger. They do not run
for records that propagate up from a child logger such as
`logging.getLogger("myapp.orders")`. So those records did not get
`correlation_id` or `causation_id`, did not get the trace ids when telemetry
was on, and were not masked by `[logging].redact`.

Protean now also attaches each filter to every handler the root logger holds
when logging is configured. Handler filters run for every record the handler
writes, so records from child loggers that reach those handlers now get the
same fields and the same masking as records logged on the root logger. With
`protean server --workers N`, each worker's queue handler gets the filters
too, and the supervisor keeps the ids a worker set on its records.

### Who is affected

- **You log through child loggers.** Their records now carry
  `correlation_id` and `causation_id`, and the trace ids when telemetry is on.
  A format string that uses `%(correlation_id)s` now works for them.
- **You rely on `[logging].redact` for stdlib records.** Values of the listed
  keys are now masked on records from child loggers too. Log output that used
  to show those values now shows the mask.
- **You list `correlation_id`, `causation_id`, `trace_id` or `span_id` in
  `[logging].redact` and read them from the log record.** The redaction
  filter now runs after the correlation and trace-context filters on the root
  logger and each of its handlers. Before, those filters wrote the real ids
  onto the record after redaction had run. Protean's JSON and console output
  masked them anyway, but a formatter or filter that reads record attributes
  (a `%(correlation_id)s` format string, `caplog`) saw the real ids. It now
  sees the mask.
- **Your `dict_config` puts `ProteanRedactionFilter` or
  `OTelTraceContextFilter` on the root logger only.** Protean now copies each
  to every root handler, so records from child loggers are masked, or carry
  trace ids, too.
- **You set `correlation_id` or `causation_id` yourself through `extra=`.**
  The filter now overwrites them on records from child loggers, as it already
  did on records logged on the root logger. Outside a domain context both
  become `""`. Set `g.correlation_id` and `g.causation_id` in the domain
  context instead, and the filter picks them up.
- **You add a handler to the root logger after logging is configured.** That
  handler does not get the filters. Attach them to it yourself, for example
  `handler.addFilter(ProteanCorrelationFilter())` from
  `protean.integrations.logging`. The same applies to handlers on named
  loggers and to child loggers that set `propagate = False`, because their
  records never reach the root logger's handlers.
- **You call `configure_logging()` more than once with different `redact`
  keys.** Each logger and handler keeps the first `ProteanRedactionFilter` it
  got. The root logger keeps the keys from the first call, while handlers
  created by a later call get the keys from that call. With `dict_config`,
  those handlers also get the root logger's redaction filters, so they mask
  the keys from both calls. Under `protean server --workers N`, each worker
  sends its records through one queue handler. That handler masks every key
  set the worker's root logger or its handlers held, so a worker can mask more
  keys than a single-process run does. This covers stdlib record attributes.
  Fields logged through `get_logger()` are masked by the structlog processor
  that the last call built, so they use only that call's keys. Pass the full
  list of keys on every call.

### Why it was not put behind a flag

The fields and the redaction are documented to apply to every stdlib record.
Skipping records from child loggers was a bug.

## A zero read timeout on Redis no longer waits

On the Redis broker, `read_blocking(timeout_ms=0)` sent `XREADGROUP ... BLOCK 0`,
which Redis reads as "wait until a message arrives". The subscription engine
calls it with `0` to check the primary stream without waiting when priority
lanes are on. That check hung on an idle stream, logged
`broker.redis.read_blocking_failed` when the socket timed out, and held up the
backfill lane.

`read_blocking(timeout_ms=0)` now returns at once, as the broker contract
describes. A negative `timeout_ms` is rejected and logged as
`broker.redis.read_blocking_failed`, and the call returns `[]`.

The `blocking_timeout_ms` subscription setting must now be positive. A value
of `0` raises `ConfigurationError` when the server starts. With the new
meaning, `0` would make the poll loop query Redis with no pause.

### Who is affected

- **You set `blocking_timeout_ms = 0` on a stream subscription.** The server
  now refuses to start. Before this release the setting logged
  `broker.redis.read_blocking_failed` every few seconds. Remove the setting to
  get the default, or set a positive value such as `1000`.
- **You call `broker.read_blocking(..., timeout_ms=0)` yourself to wait for
  a message.** Call it in a loop with a positive timeout instead. Values above
  1000 ms are capped at 1000 ms.
- **You run with priority lanes on.** An idle subscription now waits on the
  primary and the backfill stream in one read. Before, it waited on the
  primary stream only, which delivered production messages at once and held
  up the backfill lane. Now a message on either stream ends the wait, so a
  production message that arrives while the subscription is idle is picked up
  at once, and backfill messages are no longer held up. No setting change is
  needed.

### Why it was not put behind a flag

The broker contract gives `0` no wait, and the engine's priority-lane check
depends on that. Waiting forever on `0` was a bug. There is no setting that
waits forever. The read runs in a worker thread that shutdown cannot
interrupt, and a client `socket_timeout` cuts the wait short with an error.

## The memory provider's `raw()` raises `DatabaseError`, and some error logs drop the exception text

Two small changes came with the upgrade to ruff 0.16.

The memory provider's `raw()` raises `DatabaseError` when the query is not
valid JSON. It used to raise a bare `Exception`. The `json.JSONDecodeError`
is kept as the cause.

Error logs in the observatory API, the server subscriptions and the worker
supervisor no longer put the exception text in the message. They are logged
with `logger.exception`, so the record still carries the exception and its
traceback in `exc_info`. For example, a worker that fails on start now logs
`Worker 3 failed` with the traceback, where it logged
`Worker 3 failed: db unreachable`. The subscription retry log is now
`Error in subscription <name> (attempt <n>)`, and the DLQ log is
`Failed to move message <id> to DLQ`.

### Who is affected

- **You catch the error from the memory provider's `raw()`.** An
  `except Exception` handler still catches it. An `except DatabaseError` or
  `except ProteanException` handler now catches it too, where it did not
  before. Check that such a handler is meant to see a malformed query.
- **You match exception text in log messages.** A log filter, an alert rule or
  a search that looks for the exception text in the message line of these
  records no longer finds it. Match on the exception in `exc_info` instead,
  or on the traceback in the formatted output. A JSON formatter writes the
  traceback to its own field, so search that field.

### Why it was not put behind a flag

`DatabaseError` is a subclass of `Exception`, so no handler that caught the
error before stops catching it. The exception text was printed twice before:
once in the message and once in the traceback. It is still printed once.

## A failed post-invariant rolls back the change

**Behavioural fix.** When an `@invariant.post` check failed after a change,
Protean raised the error but left the new value on the object. Now the change
is undone: the object keeps its previous state, and its changed flag goes
back to what it was before the change.

The rollback covers:

- field assignments of every kind (plain, value object, `Reference`, `HasOne`
  and `HasMany`), on the aggregate and on its child entities
- `add_<field>()` and `remove_<field>()` calls
- `atomic_change` blocks: when the check at the end of the block fails, every
  change made in the block is undone, including child entities and
  associations, and the events raised inside the block are discarded
- events raised on event-sourced aggregates: when a check fails after the
  `@apply` handler, `raise_()` undoes the handler's field changes and leaves
  the event out of `_events`

It also runs when the invariant fails with an error other than
`ValidationError`.

## A `ValueError` at commit is no longer reported as a version conflict

The unit of work turned almost every `ValueError` raised during commit into
`ExpectedVersionError`, with the outbox on or off. The one exception was a
`ValueError` from saving the outbox rows, which raised `TransactionError`. A
handler's version retry then ran the handler again, even when the failure had
nothing to do with a version conflict.

Now only a real version conflict raises `ExpectedVersionError` at commit:

- Message DB reports a wrong expected version as an error with the `P0001`
  code. The Message DB event store's `append` and `_write` now raise
  `ExpectedVersionError` for that error itself, inside or outside a unit of
  work. It raised `ValueError` before. Other Message DB errors still raise
  `ValueError`.
- The memory event store raises `ExpectedVersionError` itself on a wrong
  expected version. It raised `ValueError` before. The message text is the
  same: `Wrong expected version: 0 (Stream: ..., Stream Version: 1)`.
- Any other `ValueError` raised during commit becomes `TransactionError`, with
  or without the outbox. Its `extra_info["original_exception"]` is
  `"ValueError"`, its `__cause__` is the `ValueError`, and the version retry
  does not run the handler again.

### Who is affected

- Code under `event_processing = "sync"` where an event handler raises a
  `ValueError` (a pydantic `ValidationError` is one). The handler runs inside
  the commit, so the caller used to see `ExpectedVersionError`, and the
  enclosing command handler's version retry ran a command whose events were
  already stored. The caller now sees `TransactionError` with the
  `ValueError` as its `__cause__`, and the command runs once. The 0.17 guide
  describes the old behavior under
  [A failing handler method no longer stops its siblings](v0-17.md#a-failing-handler-method-no-longer-stops-its-siblings)
  and
  [Sibling handler classes are independent in failure under synchronous dispatch](v0-17.md#sibling-handler-classes-are-independent-in-failure-under-synchronous-dispatch).
  A single failing handler raising `ValueError` now surfaces the same way as
  any other single failure.
- Code that catches `ExpectedVersionError` around a commit and expects it for
  a `ValueError` that is not a version conflict. Catch `TransactionError` for
  those failures.
- Code that catches `ValueError` from the memory or Message DB event store's
  `append` or `_write` on a wrong expected version. Catch
  `ExpectedVersionError` instead.

At commit, version conflicts on Message DB, on the memory event store and on
relational providers still raise `ExpectedVersionError` and are still retried.

### Why it was not put behind a flag

Both changes are corrections. Retrying a failure that is not a version
conflict runs the handler again for no reason. The memory and Message DB
event stores now report a conflict with the error the unit of work reports for
the relational providers.

## A domain with no environment set logs at INFO

**Behavioural break, log output only.** In 0.17, `Domain.init()` treated an
unset environment as `development` and logged at DEBUG. With `PROTEAN_ENV`,
`ENV` and `ENVIRONMENT` all unset, a script or a REPL session that called
`domain.init()` printed a DEBUG line for every provider and broker it
registered. Protean now logs at INFO when no environment is set. The output
stays colored console. Only an explicit `PROTEAN_ENV=development` (or `ENV` or
`ENVIRONMENT`) selects DEBUG.

Three related changes go with it:

- **The `Exception::` debug line is gone.** Creating any Protean exception
  with messages, such as a `ValidationError` your code catches, used to log
  `Exception:: {messages}` at DEBUG. It now logs nothing.
- **A broken plugin logs a WARNING.** A provider or broker plugin whose load
  or registration raises an error other than `ImportError` now logs
  `Failed to load provider plugin` (or `broker plugin`) at WARNING, so you see
  it at the default level.
- **An `ImportError` is a DEBUG skip.** A plugin whose load or registration
  raises any `ImportError` logs `Skipping provider plugin` (or
  `broker plugin`) at DEBUG with the error text. The usual cause is a missing
  optional extra, such as the Redis brokers without `protean[redis]`, and the
  text then names the missing module. An `ImportError` from a bug inside a
  plugin, such as `cannot import name ...`, takes the same path, so set the
  level to DEBUG when a plugin you expect does not register.

### Who is affected

Anyone who runs a domain with no environment variable set and reads its DEBUG
output, or the INFO lines from `protean.core` and `protean.adapters`: a script, a REPL, `protean shell`, or a FastAPI app that calls
`domain.init()`. A plain `protean server` or `protean observatory` logged at
INFO in 0.17 and still does. To get the DEBUG lines back, set one of these:

```shell
export PROTEAN_ENV=development
# or
export PROTEAN_LOG_LEVEL=DEBUG
```

`protean --log-level DEBUG <command>` and `level = "DEBUG"` under `[logging]`
in `domain.toml` work too. The `Exception::` line does not come back at any
level.

### Why it was not put behind a flag

The change lowers what a default run prints. At INFO, Protean holds
`protean.core` and `protean.adapters` at WARNING, as it already did for an
explicit INFO level. Their INFO lines, such as `Executing use case` and the
broker INFO lines, stop printing along with the DEBUG lines. The one line
added at the default level is the WARNING for a plugin that fails with an
error other than `ImportError`, and that line reports a real fault. One
environment variable brings back all of these lines except `Exception::`,
which carried the same messages the exception already holds.

## An event or command rebuilt from a stored message keeps its trace IDs and origin stream

`Message.to_domain_object()` rebuilds an event from a stored message. The
rebuilt event used to drop the stored `correlation_id` and `causation_id`.
Outside a handler both came back as `None`. Inside a handler they were
replaced with the IDs of the message being handled. The rebuilt event now
keeps the IDs it was stored with. A stored ID that is empty stays empty, even
inside a handler. A rebuilt command works the same way: an empty stored
`causation_id` is no longer filled with the ID of the message being handled.

`origin_stream` follows the same rule for both. The stored value used to be
ignored. A rebuilt event took the `origin_stream` of the command being
handled, if that command had one. A rebuilt command took the stream of the
event being handled. In every other case, including an event or command
delivered to its own handler, it came back as `None`. The rebuilt event or
command now keeps the `origin_stream` it was stored with, and an empty one
stays empty.

### Who is affected

Code that reads `_metadata.domain.correlation_id`, `causation_id` or
`origin_stream` on a rebuilt event or command and relies on the old values.
Most code read these values from the `Message` instead, and that still works.
Nothing needs to change unless your code expected `None` or the values of the
current handler's message.

### Why it was not put behind a flag

The stored values are the correct ones. The old values were wrong for anyone
who read them from the event or command, and no code was meant to depend on
them.

## `sequential_by` on a handler or projector must be a field name

On an event handler, command handler or projector, `sequential_by` names a field
on the handled messages. `domain.init()` now raises `IncorrectUsageError` when
the value is not a non-empty string. The message says these handlers take a
field name and that the boolean form is for process managers.

Before, on an event handler or command handler, `sequential_by=True` failed
with an error about a missing field named `True`. `sequential_by=False` and
`sequential_by=""` were silently ignored, so the handler ran without
partitioning. Projectors did not accept `sequential_by` at all before 0.18.

### Who is affected

A domain that sets `sequential_by=False` or `sequential_by=""` on an event
handler or command handler. Remove the option, or set it to `None`,
to keep the handler unpartitioned:

```python
# fragment
# Before: accepted and ignored
@domain.event_handler(part_of=Order, sequential_by=False)
class OrderEventHandler(BaseEventHandler): ...


# After
@domain.event_handler(part_of=Order)
class OrderEventHandler(BaseEventHandler): ...
```

A process manager still opts in with `sequential_by=True`. Any other

## A non-boolean `sequential_by` on a process manager is deprecated

**A deprecation, not a break.** On a process manager, `sequential_by` is a
boolean opt-in. The partition key comes from each handler's `correlate`
setting. Before, any truthy value turned partitioning on and any falsy value
left it off. A field name such as `sequential_by="order_id"`, copied from an
event handler, worked like `True`, and the IR carried the string.

That still works in 0.18. `domain.init()` now emits a
`RemovedInProtean020Warning` (a `DeprecationWarning` subclass) for any value
other than `True`, `False` or `None`, and stores the value back as a boolean,
so the IR carries `true` or `false`. In 0.20.0 a non-boolean value raises
`IncorrectUsageError`.

### Who is affected

A domain that sets `sequential_by` on a process manager to anything other than
a boolean. Replace a truthy value with `True` and a falsy one with nothing:

```python
# fragment
# Before: treated as True; warns in 0.18
@domain.process_manager(stream_categories=["shop::order"], sequential_by="order_id")
class OrderFulfillment(BaseProcessManager): ...


# After
@domain.process_manager(stream_categories=["shop::order"], sequential_by=True)
class OrderFulfillment(BaseProcessManager): ...
```

## An integer identity under the `uuid` strategy is refused on SQL

The `uuid` identity strategy makes an integer identity from `uuid4().int`, a
128-bit number. No SQL integer column holds it. `Domain.init()` now raises
`ConfigurationError` when an aggregate, entity or projection on a SQL provider
(SQLite, PostgreSQL, MySQL/MariaDB or MSSQL) gets an integer identity under
that strategy. The message names the element and the provider.

The check reads the identifier's own `identity_type` and `identity_strategy`
arguments first, then the domain configuration. It skips an element whose
custom database model declares the identity column itself, because that
column's type is the model's choice.

### Who is affected

On a domain whose `identity_type` is `"integer"`, a SQL model for an
element with a generated identifier could not be built before this release:
building it raised `TypeError: Integer() takes no arguments`. That now builds,
and the uuid case fails at `Domain.init()` with a clear message. Two cases
built before and are unchanged: an identifier declared with
`Auto(increment=True)`, and an event-sourced aggregate, which has no SQL
table.

The change that breaks working code is narrower. An identifier that sets
`identity_type="integer"` itself, on a domain whose `identity_type` is
`"string"`, used to save. Its column follows the domain's `identity_type`, so it
was a text column, and the 128-bit number went into it as text. That identifier
is now refused:

```python
# fragment
# Before: saved the 128-bit number into the text column
@domain.aggregate
class Order:
    order_id: Auto(identifier=True, identity_type="integer")
```

Pick one of the two paths the error names:

- Set `identity_strategy="function"` with an `identity_function` that returns
  integers. The id is set when the aggregate is created, and the column stays a
  text column.
- Declare the identifier as `Auto(increment=True)`. The database assigns the id
  on the first save, and the column becomes an integer column, so the table
  needs a schema change. Existing rows keep their 128-bit ids, which do not
  fit the integer column, so this path suits a new table. Columns in other
  tables that reference the aggregate follow the domain's `identity_type` and
  stay text columns.

The memory provider holds the 128-bit value. Elasticsearch stores it as a
string. Neither is affected.

## Saving the same aggregate instance again writes a new version

Saving an aggregate instance, changing it, and saving it again in a later
transaction without reloading it now writes a new version. Before, the second
save wrote the version the instance already had. Its events reused the ids of
the first save's events (`<stream>-0.1` twice), so an event handler that
deduplicates by event id dropped the second event. A copy loaded before the
second save could also overwrite it without an `ExpectedVersionError`.

Now each committed transaction advances the instance the way a reload would.
After the commit, `_version` is the version just written and `_next_version`
is one more. Events raised after it are numbered from the next version
(`<stream>-1.1`). If the transaction rolls back, `_version` goes back to the
version the instance had before the transaction. On a provider without
transactions, such as Elasticsearch, the rollback does not undo the write, so
the instance keeps the version it wrote. Unless another writer saved the
aggregate in the meantime, the instance can be changed and saved again without
a reload.

Event-sourced aggregates track their versions from their events, so none of
this applies to them.

Adding one instance several times inside a single `UnitOfWork` still writes
one version for that transaction. The events raised between those adds are
numbered within it (`<stream>-0.1`, `<stream>-0.2`).

Inside a `UnitOfWork`, a `get()` or query of an aggregate that the transaction
has already loaded or saved returns that same instance, with any changes made
to it since. Before, each read built a new copy. Each copy counted its version
and event position from the store, which had not seen the other copies'
pending changes, so events raised on an earlier copy were lost and saving a
later copy could raise `ExpectedVersionError`. This holds for event-sourced
aggregates too: before, a `get()` returned the tracked instance only after
`add()` had saved it with new events.

### Who is affected

Code that keeps an aggregate instance across transactions and saves it more
than once. Two things change for it:

- `_version` on the stored record and on the instance goes up by one for each
  committed transaction that saves it.
- A copy loaded before one of those saves now raises `ExpectedVersionError`
  when you save it. Before, it silently overwrote the newer record. Reload the
  aggregate and apply the change again, as you would for any version conflict.

Code that reads the same aggregate more than once inside one `UnitOfWork` now
gets one instance back. This is how the identity map in SQLAlchemy's session
and in Hibernate behaves. Look for code that changes an aggregate, decides to
abandon the change, and calls `get()` again to start over. The second `get()`
returns the changed instance. If the code then saves it with `add()`, the
abandoned change is written too. Events raised before the second `get()` are
saved at commit even without `add()` on a state-based aggregate. On an
event-sourced aggregate they are saved only through `add()`. Before, the
second `get()` returned a copy of the stored record, and the events raised on
the first copy were dropped.

To abandon a change, raise an exception so the `UnitOfWork` rolls back. To
read the stored state, read the aggregate in a new `UnitOfWork`. A change that
breaks an invariant needs neither, because Protean undoes the assignment when
the check fails.

Code that loads an aggregate once per transaction sees no difference.

### Why it was not put behind a flag

The old behaviour lost events for handlers that deduplicate by id and let a
stale copy overwrite newer data. Reading a new copy inside a transaction lost
events or raised a conflict with no other writer. No correct program could rely
on any of these.

## A failed IR build now fails `check`

`Domain.check()` used to log a failure to build the IR, with its traceback,
and return the result without IR diagnostics. The status could be `pass`, and
`protean check` printed "All checks passed".

Now the failure is one entry in `errors`. Its `element` is `"to_ir"` and its
`code` is the exception class name, such as `AttributeError`. The status is
`fail`. `protean check` exits `1`, `protean verify` fails its check stage and
exits `4`, and the MCP `check` tool reports the error. The log keeps one
warning line without the traceback.

### Who is affected

- Code that calls `Domain.check()` directly and treats a `pass` status as
  success. A domain whose IR cannot be built now returns `fail`.
- A CI job that runs `protean check` or `protean verify` on such a domain. It
  passed before and fails now. Fix the element the error message names.

### Why it was not put behind a flag

A check that could not build the IR did not run the IR rules, so a `pass` was
not true. Reporting the failure is a correction.

## Domain traversal loads modules in name order

When `Domain.init()` traverses the domain's folder, it now loads the root
directory's files first, then each subdirectory in name order, with the files
in each directory sorted by name. It used to load them in the order
`os.listdir` returned, which depends on the filesystem.

### Who is affected

A domain that registers enrichers from more than one traversed module, when
the result depends on the order they run in. Enrichers run in registration
order, and a module's enrichers register when the module loads, so the new
load order can change that order. Two cases depend on it:

- Two enrichers write the same field or the same metadata key. The one that
  runs last wins.
- An aggregate enricher reads a value that another one sets. Aggregate
  enrichers change the same aggregate one after another, so swapping their
  order can change what is saved even when they write different fields.

Enrichers that each set their own fields and read nothing another one sets are
not affected.

To keep a fixed order of your own, register the enrichers from one module,
such as the module that creates the `Domain`, in the order you want.

### Why it was not put behind a flag

The old order was not a contract. Two machines with different filesystems
could already run the same enrichers in different orders. The IR now records
enricher order, so it has to be the same on every machine.

## A missing MySQL or MSSQL driver fails `domain.init()` with `ConfigurationError`

The MySQL and MSSQL providers now check for their driver when `domain.init()`
builds them. When the driver cannot be imported, `domain.init()` raises a
`ConfigurationError`. The message names the database's configured name, the
driver and the extra to install:

```text
Database 'default' uses a 'mysql+pymysql://' URL, but the 'pymysql' driver cannot be imported (No module named 'pymysql'). Install it with `pip install "protean[mysql]"`.
```

It used to raise the driver's own `ModuleNotFoundError`, from inside
SQLAlchemy.

Which driver is checked depends on the `database_uri`:

- `mysql+pymysql://` and `mariadb+pymysql://` are checked for PyMySQL, the
  driver the `protean[mysql]` extra installs.
- A plain `mysql://` or `mariadb://` is checked for mysqlclient (`MySQLdb`),
  because SQLAlchemy connects through mysqlclient for those URLs. When
  mysqlclient is missing, the message asks you to add `+pymysql` to the URL
  and install `protean[mysql]`. When mysqlclient is installed, the URL works as
  before.
- `mssql+pyodbc://` and a plain `mssql://` are checked for pyodbc. pyodbc
  installed without the unixODBC system library fails to import, so it raises
  `ConfigurationError` the same way.
- A `database_uri` that names another driver, such as `mysql+mysqldb://` or
  `mssql+pymssql://`, is not checked. It goes to SQLAlchemy as written, and a
  missing driver there still raises SQLAlchemy's error.

### Who is affected

Code that catches `ModuleNotFoundError` or `ImportError` around
`domain.init()` to detect a missing MySQL or MSSQL driver. Catch
`ConfigurationError` instead. The original import error is on its
`__cause__`.

If the driver SQLAlchemy uses for your URL is installed, nothing changes.

### Why it was not put behind a flag

The old error came from deep inside SQLAlchemy and did not say which extra
installs the driver. The MySQL and MSSQL providers now report a missing driver
the way the PostgreSQL provider does.

## The `database_model` element option is removed

`@domain.aggregate`, `@domain.entity` and `@domain.projection` no longer take a
`database_model` option. The same goes for `domain.register()` on those
elements. The option never had any effect. Protean accepted it, stored it and
then built its own database model anyway, so a custom model passed this way was
never used.

Passing the option now fails at registration:

```python
# fragment
# Before
@domain.aggregate(database_model=UserModel)
class User:
    email: String(max_length=255, required=True)
```

```text
ConfigurationError: Unknown option(s) {'database_model'}
```

Register the custom model with `@domain.database_model` instead, and name the
element it belongs to with `part_of`:

```python
--8<-- "reference/migration/v0-18/010.py:setup"
--8<-- "reference/migration/v0-18/010.py:fix"
```

See [Database Models](../../guides/change-state/database-models.md) for how a
custom model maps columns to fields.

### Who is affected

Code that passes `database_model=` to `@domain.aggregate`, `@domain.entity`,
`@domain.projection`, or to `domain.register()` for one of those elements. Code
that reads `meta_.database_model` on an element also breaks, since the key is
gone from `meta_`.

If you already register custom models with `@domain.database_model`, nothing
changes.

### Why it was not put behind a flag

The option did nothing, so there is no old behaviour to keep. A flag would
only keep a setting that looks like it works and does not.

## `protean test -c FULL` runs its service-free tests in parallel

`protean test -c FULL` and `protean test -c COVERAGE` start with a pass over
the whole suite. That pass now runs in two parts. The tests that need no
service run on pytest-xdist, as `CORE` does. The tests that need a database,
broker or other service run in one process, as before. The adapter suites
that follow are unchanged.

`--workers` and `PROTEAN_TEST_WORKERS` now set the worker count for the first
part. To keep the whole pass in one process, run either of these:

```shell
protean test -c FULL --workers 0
protean test -c FULL --sequential
```

`--workers 0` changes only that first pass. `--sequential` also runs the
adapter suites one at a time.

### Who is affected

Only people who run Protean's own test suite. `protean test` drives the
framework's test suite and does not run an application's tests, so nothing
changes for code that uses Protean.

A test in Protean's suite that passes alone but fails in this pass depends on
state another test left behind. See
[Parallel runs](../../community/contributing/testing.md#parallel-runs).
