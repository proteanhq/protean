# Migrating to 0.18

!!! abstract "From 0.17 to 0.18"

Protean 0.18 cuts the set of packages that a plain install pulls in. A plain
`pip install protean` no longer forces a web server, an ASGI stack, an
interactive REPL, and a project scaffolder onto every install. You now get
those packages through install extras, the same way you have always installed
the database and broker adapters. See the runtime dependency boundary decision
([ADR-0029](https://github.com/proteanhq/protean/blob/main/docs/adr/0029-runtime-dependency-boundary-and-extras.md))
for where the boundary sits and why.

**This is a Tier-1 breaking change**, a surface break in Protean's
breaking-change policy, but a small one. Your code does not change, and the fix
is to add a one-word extra to your install. If a feature you use now needs an
extra, the CLI or the import tells you exactly which one.

## What moved behind extras

Five packages that used to be hard runtime dependencies are now install extras:

| Package(s) | Extra | Feature it gates |
|------------|-------|------------------|
| `fastapi`, `uvicorn`, `jinja2` | `protean[server]` | `protean observatory`, `protean.integrations.fastapi` |
| `ipython` | `protean[shell]` | `protean shell` |
| `copier` | `protean[scaffold]` | `protean new` |

Two convenience bundles are also available:

- `protean[cli]`: The full interactive CLI experience (`shell` + `scaffold` +
  `mcp`). The `mcp` extra is new in 0.18. It installs `mcp`, the package
  behind `protean mcp`, the MCP (Model Context Protocol) server that coding
  agents connect to.
- `protean[all]`: `server` + `cli`. It installs every package the commands and
  integrations above need.

You need **none** of these packages to run `import protean`, define a domain,
persist through the memory adapter, or run `protean server` (the async engine).
Those paths already loaded the packages lazily, and they stay in the lean core.

## Install `all` to restore every 0.17 feature

If your project relied on the old full install and you do not want to choose
extras, install `all`:

```shell
pip install "protean[all]"
```

That brings back every feature the 0.17 core install supported, and adds `mcp`.
It does not bring back `werkzeug`, `cffi` or `greenlet`, which also left the
core install (see [cffi and greenlet left the core
install](#cffi-and-greenlet-left-the-core-install) and [werkzeug left the core
install](#werkzeug-left-the-core-install)). Later, you can trim the install to
the extras you use.

## Install the extra for each feature you use

When you install a trimmed set of dependencies (for example in a production
image that installs `protean` without `[all]`), act only for the features below
that you use:

- **Running the Observatory** (`protean observatory`) or using the FastAPI
  integration (`from protean.integrations.fastapi import ...`):

  ```shell
  pip install "protean[server]"
  ```

- **Opening the domain shell** (`protean shell`):

  ```shell
  pip install "protean[shell]"
  ```

- **Scaffolding a project** (`protean new`):

  ```shell
  pip install "protean[scaffold]"
  ```

If you run one of these without its extra, the command fails with a clear
message naming the extra to install, not a raw `ModuleNotFoundError`:

```text
Error: 'protean observatory' requires the 'fastapi' package. Install it with 'pip install "protean[server]"'.
```

`bleach` stays in the core install. String and Text fields no longer sanitize
by default (see
[String and Text no longer sanitize by default](#string-and-text-no-longer-sanitize-by-default)),
but `bleach` still backs the opt-in `sanitize=True` path.

## cffi and greenlet left the core install

0.17 installed `cffi` and `greenlet` as hard dependencies, but nothing in
Protean imports either package. They only ever arrived as transitive
dependencies: SQLAlchemy 2.0 (the `postgresql`, `postgresql-psycopg2`,
`sqlite`, `mssql` and `mysql` extras) requires `greenlet` on common platforms, and `cryptography` requires
`cffi` (`sendgrid` pulls it directly, and `mysql` through `pymysql[rsa]`).

In 0.18 both are out of the core install. Their version floors moved onto the
extras that pull them (`greenlet>=3.2.3,<4` on the SQLAlchemy extras,
`cffi>=2.0.0` on `sendgrid` and `mysql`). Each of those extras still resolves a
version with wheels for the newest supported Python. SQLAlchemy 2.1 no longer
requires `greenlet`. The SQL extras keep it so that an install at the
SQLAlchemy 2.0 floor still works.

You only need to act if your own code imports `cffi` or `greenlet` and relied
on Protean to provide it. Declare the package in your own project instead.

## PostgreSQL defaults to psycopg 3

0.17 capped SQLAlchemy at `<2.1`, and `protean[postgresql]` installed
`psycopg2-binary`. In 0.18:

- The SQL extras accept SQLAlchemy `>=2.0.36,<2.2`. An application that needs
  SQLAlchemy 2.1 can now install them. The 2.0.36 floor is unchanged.
- `protean[postgresql]` installs psycopg 3 (`psycopg[binary]`).
- The new `protean[postgresql-psycopg2]` extra installs `psycopg2-binary`.

The driver follows `database_uri`:

| `database_uri` | Driver |
|----------------|--------|
| `postgresql+psycopg://...` | psycopg 3 |
| `postgresql+psycopg2://...` | psycopg2 |
| `postgresql://...` | psycopg 3 if it is installed, otherwise psycopg2 |

Protean resolves the plain `postgresql://` form itself. SQLAlchemy 2.0 reads
the plain form as psycopg2, and SQLAlchemy 2.1 reads it as psycopg 3. If
Protean left the choice to SQLAlchemy, the driver would depend on the installed
SQLAlchemy version. When the driver a URL needs cannot be imported,
`domain.init()` raises a `ConfigurationError` that names the extra to install.

### Who is affected

- **You install `protean[postgresql]` and use a plain `postgresql://` URL.**
  A fresh install (a new Docker image, a CI run) now gets psycopg 3, and your
  application runs on it. Protean's own queries behave the same on psycopg2 and
  psycopg 3. When you run raw SQL yourself through the session, you can see
  psycopg 3's differences, for example in how it adapts some Python types. See
  the [psycopg 3
  differences](https://www.psycopg.org/psycopg3/docs/basic/from_pg2.html)
  guide.
- **You want to stay on psycopg2.** Install `protean[postgresql-psycopg2]`
  and write `postgresql+psycopg2://` in `database_uri`. The explicit URL keeps
  psycopg2 even when psycopg 3 is also installed.
- **You upgrade in place with both drivers installed.** A plain URL switches to
  psycopg 3, because Protean tries psycopg 3 first. If you want to control when
  the driver changes, pin the driver in the URL.

### Why it was not put behind a flag

The `postgresql-psycopg2` extra and the `postgresql+psycopg2://` URL already
select the old behaviour, so a flag would be a third way to say the same
thing.

## werkzeug left the core install

0.17 used Werkzeug's `LocalProxy`/`LocalStack` to back `current_domain`,
`current_uow`, and `g`. In 0.18, stdlib `contextvars` backs these context
locals. `werkzeug` is no longer a core dependency.

Nearly all code sees no change. The push/pop nesting, the proxy behavior and
the async support stay the same, and `contextvars` follows asyncio tasks and
`await` boundaries natively. The public API of `current_domain`, `current_uow`,
and `g` is unchanged.

You only need to act if your own code depends on Werkzeug-specific details of
the proxy or stack, such as inspecting the underlying `LocalStack` directly.
Internal helpers like `_domain_context_stack` and `_uow_context_stack` stay
private. Their implementation type has changed.

## `check` and `verify` machine output changed shape and exit codes

`protean check --format json` and `protean verify --json` now emit one shared,
versioned [result envelope](../cli/conventions.md). Both also follow one
exit-code convention, which other commands can adopt later. `check`'s JSON
output has shipped since 0.15.0, and the diagnostic schema and `[lint].level`
gating came in 0.17.0. `verify` is new in this cycle. Protean is still pre-1.0
and neither output has a stability guarantee yet, so this release corrects both
directly with no deprecation period. If you already parse `check --format json`
or `verify --json` output, or branch on their exit codes, act on this section.

**See how the JSON shape changed.** `check --format json` was the raw
`Domain.check()` document (`domain`, `status`, `errors`, `diagnostics`,
`counts` at the top level). It is now the envelope:

```json
{
  "version": "0.1.0",
  "status": "fail",
  "data": { "domain": "...", "status": "warn", "errors": [], "counts": {} },
  "diagnostics": [ "..." ]
}
```

The check report moved under `data`; `diagnostics` is at the top level. A
consumer that read `counts` now reads `data.counts`. A consumer that read
`diagnostics` still reads the top-level `diagnostics`. `verify --json` now uses
the same envelope: its old `{verdict, stages}` is now under `data`.

The `sarif` and `github-annotations` formats are unchanged: they are external
standard schemas and are not wrapped.

**`--level` no longer filters the JSON envelope.** `--level` now filters only
the human `rich`/`--quiet` views. The JSON, SARIF, and github-annotations
machine formats carry every finding the run produced, and a machine consumer
can filter for itself. `diagnostics` can still be empty on a `status="fail"`
envelope. A validation error, such as two handlers for one command, skips the
diagnostics; check `data.errors` for those. A malformed `[lint]` config or an
unresolved reference stops the run before any check. It gives `status="error"`,
the message under `data.error`, and exit `2`. If you relied on `check --format
json --level error` to pre-filter diagnostics, filter the output with `jq`
instead.

**Compare the old and new exit codes.**

`check`:

| Case | Old | New |
|------|-----|-----|
| Clean | `0` | `0` |
| Validator errors | `1` | `1` |
| Gating warning/info at the floor | `2` | `1` |
| Bad option, unloadable domain, malformed `[lint]` config | `1` | `2` |

`check` now uses one findings-failure code (`1`) where it used `1` for errors
and `2` for warnings. The envelope now carries the severity. Load and config
errors became usage errors (`2`).

`verify` shifted its codes up so `2` is reserved for usage:

| Case | Old | New |
|------|-----|-----|
| All green | `0` | `0` |
| Usage (bad/missing `--domain`, `--path` not a directory) | `1` | `2` |
| Init failed | `2` | `3` |
| Check failed | `3` | `4` |
| Tests failed | `4` | `5` |

**Read only the envelope on stdout.** Under machine output, stdout now carries
only the envelope, exactly one JSON object. Logs and error lines go to stderr,
so `protean check --format json | jq` and `protean verify --json | jq` stay
parseable.

## `events catalog`, `subscriptions status`, and `projection status` JSON moved onto the envelope

`protean events catalog --json`, `protean subscriptions status --json`, and
`protean projection status --json` each printed a bare JSON array. They now
emit the same [result envelope](../cli/conventions.md) that `check` and
`verify` use. One parser reads the output of every one of these commands. The
array moves under `data`, keyed by the command:

| Command | Old top level | New location |
|---------|---------------|-------------|
| `events catalog --json` | array of events | `data.events` |
| `subscriptions status --json` | array of subscriptions | `data.subscriptions` |
| `projection status --json` | array of projections | `data.projections` |

If your script read the array at the top level, read it under the `data` key
now:

```json
{
  "version": "0.1.0",
  "status": "pass",
  "data": { "events": [] },
  "diagnostics": []
}
```

All three are pre-1.0 with no stability guarantee, so this is a direct
correction with no deprecation window. If you already parse one of these
`--json` outputs, read `data.events`, `data.subscriptions`, or
`data.projections` in place of the top-level array.

All three also adopt the shared exit codes under `--json`. On their error
paths, stdout carries only the envelope. Under `--json`, any usage or load
failure now prints the error envelope (`status="error"`, the message under
`data.error`) on stdout and exits `2`, so `| jq` stays parseable. The failures
are an unloadable `--domain`, a missing/unreadable `--ir` file, and, for
`events catalog`, neither `--domain` nor `--ir` or both at once.

Two things change without `--json` as well. `events catalog` now prints its
usage errors (neither `--domain` nor `--ir`, or both at once) to stderr and
exits `2`, where it exited `1` before. A domain or `--ir` **load** failure
without `--json` is unchanged: it prints a human message and exits `1`.

## The memory cache no longer raises on an absent key

**This breaks behaviour on the memory cache only.** `remove(projection)`,
`remove_by_key(key)` and `set_ttl(key, ttl)` raised `KeyError` when the key was
not in the cache. They now do nothing, as the Redis cache has always done.
Redis' `DEL` and `PEXPIRE` are no-ops on a missing key. The port documents the
silent behaviour as the contract, so the two adapters answer alike.

An expired entry counts as absent. A key whose TTL has run out is treated the
same as one that was never written, on both adapters.

### Who is affected

Anyone who used the `KeyError` as a presence check on a memory-backed cache.
That code no longer takes its `except` branch, and Protean gives no warning:
the call succeeds quietly. Only a presence check through the `KeyError` breaks.

```python
# fragment
# Before: worked on the memory cache, never fired on Redis
try:
    cache.remove_by_key(key)
except KeyError:
    log.info("nothing cached for %s", key)
```

After:

```python
--8<-- "reference/migration/v0-18/001.py:remove_by_key"
```

Nothing inside Protean relied on the `KeyError`, so the change can break only
your own code.

### What did not change

`set_ttl` still rejects an invalid TTL when the key is absent. `set_ttl` raises
`ConfigurationError` for a TTL that is not a positive, finite number of
seconds, whether or not the key exists. A malformed TTL still fails on a
missing key.

`get_ttl` now answers alike on both adapters too; see
[get_ttl returns None or math.inf instead of a raw sentinel](#get_ttl-returns-none-or-mathinf-instead-of-a-raw-sentinel).

### Why it was not put behind a flag

The two adapters of the same port behaved differently by accident, and neither
behaviour was a contract. No program that runs on both adapters could have
depended on the `KeyError`. A flag that kept the `KeyError` would have kept the
two adapters different. The memory adapter is the one documented for
development and testing, where that difference costs the most.

## `get_ttl` returns `None` or `math.inf` instead of a raw sentinel

**This breaks behaviour on both cache adapters.** `get_ttl(key)` used to answer
differently on each adapter. Neither answer was easy to use. The memory cache
raised `KeyError` for a missing key. It could never report a never-expiring
key. Redis returned its raw `PTTL` sentinels: `-2` for a missing key, `-1` for
a key with no expiry. If you wanted code that worked on both adapters, you had
to catch an exception and check two magic negatives.

Both adapters now answer the same three cases:

- `None` when there is no such key.
- `math.inf` when the key exists and never expires.
- the seconds remaining otherwise (unchanged).

An expired entry counts as absent, so `get_ttl` returns `None` for it, the same
way `get` does. `math.inf` only ever comes from Redis: the memory cache writes
every entry with a concrete TTL, so it has no never-expiring keys to report.

### Who is affected

Anyone who read `get_ttl`'s old return value directly.

```python
# fragment
# Before: two shapes, one per adapter
try:
    ttl = cache.get_ttl(key)          # memory: raises KeyError if absent
except KeyError:
    ttl = None
if ttl is not None and ttl < 0:       # redis: -2 absent, -1 no expiry
    ttl = None
```

After:

```python
--8<-- "reference/migration/v0-18/001.py:ttl_imports"
--8<-- "reference/migration/v0-18/001.py:get_ttl"
```

A `ttl < 0` check on the old Redis return no longer fires, because the negative
sentinels are gone. A `ttl < math.inf` check is the way to ask "does this key
expire".

### Why it was not put behind a flag

Like the absent-key change above, this was a divergence between two adapters of
the same port, not an intentional contract. `BaseCache` is a Provisional API, so
its signatures can still change without a deprecation period. Nothing inside
Protean read `get_ttl`, so only your own callers are affected.

## Cache key patterns are a glob on every adapter

**This breaks behaviour on the memory cache.** `_get_all`, `count`, and
`remove_by_key_pattern` take a `key_pattern`. The memory cache used to compile
it as a Python regular expression, while Redis passed it to `SCAN ... MATCH` as
a glob. The same string selected different keys on each adapter. A pattern that
relied on regex behaviour matched nothing once you switched to Redis.

The memory cache now matches with `fnmatchcase`, the same glob language Redis
uses. Like Redis, it is case-sensitive on every platform. `*` matches any run
of characters, `?` matches one, `[...]` is a character class, and other
characters, including `.`, are literal. The adapters agree on `*`, `?`, and
literal characters. Bracket negation and escaping can differ, so keep patterns
to the `name:::*` shape.

### Who is affected

Anyone who passed a regex-flavoured `key_pattern` to the memory cache. Cache
keys are `name:::identifier`, so most patterns are already a name and a `*`,
which is a valid glob and needs no change. A pattern that used regex syntax
needs rewriting:

```python
# fragment
# Before, on the memory cache: a regex (and the method was public then)
cache.get_all("user_profile:::.*")
```

After:

```python
--8<-- "reference/migration/v0-18/001.py:glob"
```

A literal `.` in a pattern used to match any character on the memory cache and
now matches only a `.`. `BaseCache` is a Provisional API, so this change ships in a minor release with no deprecation period.

## Cache `get_all` is now the private, unpaginated `_get_all`

**Breaking, both cache adapters.** The public `cache.get_all(key_pattern,
last_position, size)` is gone. It is now `cache._get_all(key_pattern)`, private
by its leading underscore. It returns every matching entry in key order with no
pagination.

A cache is for point reads by key. Enumerating a match set, and paging through
it, is not what a cache is for, and offering offset pagination over it invited
use it cannot support: on a store with no native key order (Redis) every call
scans the whole keyspace, and paging a large set is quadratic. So the method is
marked private and scoped to what it is actually good for, a convenience for
tests and small, bounded stores.

It returns at most 1000 entries (`GET_ALL_MAX`). Past that it truncates to the
first 1000 in key order and logs a warning, so a store that outgrew the cache
surfaces as a warning rather than a silent partial read.

### Who is affected

Anyone calling `cache.get_all(...)`. The method no longer exists under that name,
and it no longer takes `last_position` or `size`.

```python
# fragment
# Before
for start in range(0, total, 50):
    for entry in cache.get_all(pattern, last_position=start, size=50):
        process(entry)
```

After:

```python
--8<-- "reference/migration/v0-18/001.py:get_all"
```

If you need to page a large projection set, that belongs in the projection's
repository, not the cache. Query `repository_for(Projection).query`, which has
real indexes and native pagination. The cache stays for hot point lookups by key.

### Why it was renamed rather than deprecated

`BaseCache` is a Provisional API, so it can change without a deprecation
period, like the other cache changes above. `_get_all` is private and
unpaginated for one reason: you should not build production reads on it.
`count` and `remove_by_key_pattern` stay public and take the same `key_pattern`
glob. On Redis, `count` also scans the whole keyspace.

## `flush_all()` on a Redis cache clears only its database

**This breaks behaviour on the Redis cache.** `RedisCache.flush_all()` used to
send `FLUSHALL`, which empties every database on the Redis server. It now sends
`FLUSHDB`, which empties only the database in the cache's `URI` (the `/4` in
`redis://localhost:6379/4`). The Redis and Redis PubSub brokers' test reset,
`_data_reset()`, changed the same way.

`flush_all()` still deletes every key in that one database. `RedisCache` adds
no cache-specific namespace to its keys, so `flush_all()` also removes any
other data stored in the cache's database. Give the cache a database of its
own.

### Who is affected

Anyone who relied on `flush_all()` on a Redis cache, or on a Redis broker's
reset between tests, to also clear other databases on the same server. Clear
those databases yourself now, for example with `FLUSHDB` on a client connected
to each one. `BaseCache` is a Provisional API, so the `flush_all()` change ships in a minor release with no deprecation period.

## The IR schema is now v0.2.0

The materialized IR carries a new `method_edges` key on the elements that own
methods, so the schema version moved from `0.1.0` to `0.2.0`. Protean 0.18 then
moved it again, to `0.3.0` (see [The IR schema is now
v0.3.0](#the-ir-schema-is-now-v030)). A baseline written by Protean 0.17 is at
`0.1.0`. When you regenerate it, it picks up the changes in both sections.
Documents and schemas validate both ways: a `0.1.0` document still passes the
`0.2.0` schema (`method_edges` is optional), and a `0.2.0` document still
passes the `0.1.0` schema. The `v0.1.0` schema stays published at
`https://docs.proteanhq.com/assets/ir/v0.1.0/schema.json`. The `$schema` URL
that Protean 0.18 writes into the IR,
`https://protean.dev/ir/v{X}/schema.json`, does not resolve. 0.19 writes the
docs site URL instead (see [The IR's `$schema` URL
moved](v0-19.md#the-irs-schema-url-moved)).

What does change is the checksum. Adding a key changes the canonical bytes, so a
baseline built under `0.1.0` cannot be compared against a live IR built by
Protean 0.18.

### Who is affected

Anyone with a committed `.protean/ir.json`. `protean ir check` now reports a
version mismatch and exits `3` instead of comparing checksums. The
`protean-check-staleness` pre-commit hook prints the same message and fails (it
exits `1` for every failure). A CI job that gates on the hook fails until you
regenerate the baseline.

```shell
protean ir show --domain <module> --canonical > .protean/ir.json
```

If you run the pre-commit hook with `--fix`, it rewrites `.protean/ir.json` for
you.

Your domain code does not change. For this section, the regenerated document
differs only in `$schema`, `ir_version`, the checksum, the new `method_edges`
entries, and the `sanitize` key on String and Text fields. The `sanitize` key
now appears only on a field that passes an explicit `sanitize=True`. Every
field that left `sanitize` unset loses the key (see [String and Text no longer
sanitize by default](#string-and-text-no-longer-sanitize-by-default)). A domain
with a `Decimal` field also picks up the `0.3.0` changes to that field. For the
commit that adds the regenerated baseline, follow the step in [The IR schema is
now v0.3.0](#the-ir-schema-is-now-v030).

### What a cross-version diff looks like

`protean ir diff` against a `0.1.0` baseline reports `method_edges` as added on
every element that has one, and `sanitize` as removed on every String/Text
field declared without an explicit `sanitize=`. Compatibility classification
does not read `method_edges` or `sanitize`, so `protean ir diff` and the
`protean-check-compat` hook classify neither as breaking. If you want a diff
without these non-breaking changes, regenerate the baseline. Then diff two
documents built by the same Protean version.

## The IR schema is now v0.3.0

The IR used to record a `Decimal` field as `"type": "String"` and drop its
`precision` and `scale`. It now records `"type": "Decimal"`, plus `precision`
and `scale` when the field sets them:

```json
"total": {"kind": "standard", "type": "Decimal", "precision": 19, "scale": 4}
```

The `type` list in the `v0.2.0` schema is closed, so the new type needed a new
schema version: `ir_version` moved from `0.2.0` to `0.3.0`. Protean 0.17 wrote
`0.1.0`, so a baseline from 0.17 also picks up the `0.2.0` changes in
[The IR schema is now v0.2.0](#the-ir-schema-is-now-v020). A `0.2.0` document
still passes the `0.3.0` schema. A `0.3.0` document that holds a `Decimal` field
fails the `0.2.0` schema. The `v0.2.0` schema stays published.

### Who is affected

Anyone with a committed `.protean/ir.json`. `protean ir check` reports a version
mismatch and exits `3`, and the `protean-check-staleness` hook fails, until you
regenerate the baseline:

```shell
protean ir show --domain <module> --canonical > .protean/ir.json
```

The `0.3.0` IR also records what a save writes. A `Date` or `DateTime` field
declared with `auto_now=True` or `auto_now_add=True` carries that flag. A
domain that registers enrichers gets a top-level `enrichers` section, with each
enricher listed by qualified name. `protean ir diff` reports both as changes,
and neither is breaking. If your domain has no `Decimal` field, no
`Custom(decimal.Decimal)` field, no `auto_now` or `auto_now_add` field, no
enricher and no `Integer` or `Float` field with a bound written as a string,
the regenerated baseline differs only in `$schema` and `ir_version`. For a
string bound, see [How the IR writes `min_value` and
`max_value`](#how-the-ir-writes-min_value-and-max_value). If your domain raises
one of the three diagnostics in [Diagnostic and CLI messages no longer contain
em-dashes](#diagnostic-and-cli-messages-no-longer-contain-em-dashes), the
regenerated baseline also holds that diagnostic's new text.

If your domain has a `Decimal` field, commit the regenerated baseline. Until
you do, `protean ir diff` compares the old `String` entry with the new
`Decimal` entry and reports a breaking `field_type_changed` for each such
field. Your data and your payloads have not changed. The old baseline recorded
each `Decimal` field as `String`, and the new baseline records it as `Decimal`.

The `protean-check-compat` hook compares the live IR with the baseline in the
`HEAD` commit, not with the staged file. So it also fails on the commit that
adds the regenerated baseline. Skip the hook for that one commit:

```shell
SKIP=protean-check-compat git commit -m "Regenerate the IR baseline"
```

### What changes in the generated contracts

The contract generators read the IR type, so the output for a `Decimal` field
changes:

| Generator | Before | After |
|-----------|--------|-------|
| JSON Schema | `{"type": "string"}`, plus `minimum` and `maximum` when the field set `min_value` or `max_value` | `{"type": "string", "pattern": ...}`, plus `x-precision` and `x-scale` when set. `minimum` and `maximum` are left off, since they only apply to numbers. |
| Avro | `"string"` | `{"type": "bytes", "logicalType": "decimal", "precision": p, "scale": s}` when `precision` is set (`scale` defaults to `0`); `"string"` when it is not, or when `precision` is `0` or smaller than `scale` |
| Protobuf | `string` | `string` (no change) |

A JSON payload still carries a `Decimal` value as a string, so the JSON Schema
output matches what Protean sends. Protobuf keeps `string`. In Avro, a
`Decimal` field with a precision moves from `string` to `bytes` with the
`decimal` logical type. A consumer that registered the old schema needs the new
one.

### How the IR writes `min_value` and `max_value`

A `decimal.Decimal` bound used to stop the IR build with a `TypeError`. It is
now written in a form JSON can hold:

| Field | Declared bound | Written as |
|-------|----------------|------------|
| `Decimal`, or `Custom(decimal.Decimal)` | `decimal.Decimal("0.010")` | `"0.010"`, a string that keeps every digit |
| `Integer` | `decimal.Decimal("10")`, or the string `"10"` | `10` |
| `Float` | `decimal.Decimal("0.5")` | `0.5` |
| any field | an `int` or a `float` | the same number, as before |

`Integer(min_value="5")` used to write `"5"`, which failed the schema. It now
writes `5`. The `0.3.0` schema accepts a number or a string for `min_value` and
`max_value`, but accepts a string only when the field `type` is `Decimal`. If a
field in your domain declares a bound in one of these forms, regenerate the
baseline as shown above.

### New in `ir diff`: `field_precision_widened`

On a `Decimal` field that stays `Decimal`, `ir diff` now compares `precision`
and `scale`. `ir diff` reports a safe `field_precision_widened` when you raise
or remove `precision` and leave `scale` unchanged. `ir diff` reports a breaking
`field_type_changed` when you lower or add `precision`, or change `scale`. See
[Decimal precision and
scale](../compatibility/index.md#decimal-precision-and-scale).

## `diff_ir()` checks every field of a published event

`diff_ir()` lists the breaking changes to published events in
`contracts.breaking_changes`, and sets `summary.has_breaking_changes` from that
list. It used to compare a published event's fields only when a field was
removed or renamed. It missed a field that kept its name and changed its type,
or changed its `Decimal` precision or scale in a breaking way. So was a
required field added without a default. The compatibility report from
`classify_changes()` flagged all three, so the two disagreed.

The published-contract check now applies the same field rules as the
compatibility report. When `amount` on a published event goes from
`Decimal(precision=19, scale=2)` to `scale=4`, the check now gives:

```json
{
  "type": "contract_field_type_changed",
  "fqn": "shop.Placed",
  "field": "amount",
  "left": "Decimal",
  "right": "Decimal",
  "message": "Field 'amount' Decimal shape changed (scale from 2 to 4) in published event 'Shop.Placed.v1'"
}
```

and `summary.has_breaking_changes` is `true`. A field that keeps its name has
no `renamed_to` key. When you add a required field without a default, the check
gives a new `contract_required_field_added` entry with `fqn`, `field` and
`message`. Every other contracts entry keeps its shape and message. See
[Published event
contracts](../compatibility/index.md#published-event-contracts).

### Who is affected

- **Code that calls `diff_ir()` directly** and reads
  `contracts.breaking_changes` or `summary.has_breaking_changes`. A diff that
  reported no break can now report one.
- **Readers of `protean ir diff --format json`** that look at
  `contracts.breaking_changes` or `summary.has_breaking_changes`.

The exit codes of `protean ir diff` and the `protean-check-compat` hook do not
change, with one exception. Both already exited `1` on these changes, because
the compatibility report flagged them. An event version bump that an upcaster
covers is not the exception. The report marks the field change safe. The bump
changes the event's type string, though, and `contract_type_changed` already
made that run breaking. The exception is a published event listed in `exclude`
in `.protean/config.toml`. `exclude` filters the compatibility report. It has
never filtered the contract breaks. Take a field on an excluded published
event, keep its name, and change its type or its `Decimal` shape in a breaking
way. Adding a required field without a default to that event has the same
result. That change used to exit `2` from `protean ir diff` and pass the hook.
Under `strictness = "strict"` it now exits `1` and fails the hook, as a removed
field on the same event already did. Under `strictness = "warn"`, `protean ir
diff` now exits `0` instead of `2`, and the hook still passes.

Three smaller changes come with this:

- In the JSON `compatibility` block, `field_name` is now filled for
  `field_type_changed` and `required_field_added`. For a rename it holds the
  old name. `field_name` used to be `null` for these two change types.
- The text output of `protean ir diff` prints a field break once. `protean ir
  diff` used to print a break twice when both lists reported it with different
  wording. A renamed `Decimal` field whose scale changed is one example.
- The `protean-check-compat` hook prints the contract breaks as well as the
  compatibility report's breaks. A break on an excluded published event used to
  fail the hook with no break named.

### Why it was not put behind a flag

`diff_ir()` gave the wrong answer: it reported no breaking change on a
published event that had one. `protean ir diff` and the hook already failed on these
changes, so a flag would only preserve the wrong answer for direct `diff_ir()`
callers.

## Diagnostic and CLI messages no longer contain em-dashes

Protean replaced each em-dash in a message it prints, raises or logs with a
colon, a comma or a full stop. The meaning of each message is the same. Three
diagnostics change the text the IR records:

| Code | What changed |
|------|--------------|
| `AGGREGATE_WITHOUT_COMMAND_HANDLER` | `message` and `rationale` |
| `PROJECTOR_HANDLES_ORPHANED_EVENT` | `rationale` |
| `QUERY_HANDLER_WITHOUT_QUERY` | `rationale` |

The rest are CLI output (`protean dx`, `protean ir`, the git hooks and the
table titles of `subscriptions`, `projection` and `eventstore dlq`), some
exception messages, and some log lines.

### Who is affected

Anyone with a committed `.protean/ir.json` whose domain raises one of the three
codes. The IR checksum covers each diagnostic's text, so `protean ir check`
reports the baseline as stale even though the domain did not change. A baseline
from 0.17 needs regenerating for the schema change in [The IR schema is now
v0.3.0](#the-ir-schema-is-now-v030). The same command picks up the new text:

```shell
protean ir show --domain <module> --canonical > .protean/ir.json
```

`protean ir diff` matches diagnostics by code and element and does not compare
their text, so it reports no change for these three.

If your script or test matches one of these messages by its exact text, update
it to the new wording. A script that matches on the diagnostic code, the exit
code or the JSON shape still works.

## `protean ir` rejects an unknown format value

`protean ir show`, `protean ir diff`, and `protean ir check` check `--format`
before they load anything. An unknown value prints the accepted ones and aborts:

```shell
$ protean ir diff --left baseline.json --right current.json --format=summary
Error: invalid --format: 'summary'. Choose from: text, json, event-model
Aborted.
```

Each `protean ir` command accepts its own set of `--format` values:

| Command | Accepted `--format` values | Default |
|---------|---------------------------|---------|
| `protean ir show` | `json`, `summary` | `json` |
| `protean ir diff` | `text`, `json`, `event-model` | `text` |
| `protean ir check` | `text`, `json` | `text` |

### Who is affected

Any script that passes a `--format` value outside that command's set. It used
to fall through to the command's default: `protean ir diff --format=summary`
printed the text diff, and `protean ir show --format=text` printed the full
JSON. That was silent, so a typo in a CI job or a value borrowed from a sibling
command read as success for as long as nobody compared the output to the flag.

An unknown `--format` value exits `1`, the same code as the other argument
checks that `protean ir show` and `protean ir diff` make themselves. Other
usage errors exit `2`: an option the command does not have, and, under `protean
ir check`, an invalid `.protean/config.toml`. On `protean ir diff`, `1` is also
the breaking-changes code. A CI gate that branches on the exit code reads the
usage error as a break until you fix the flag. The `invalid --format` line on
stdout tells the two apart.

To fix the failure, pass a `--format` value from the table. Nothing else about
the commands changed. A script that already passed a valid value still works.

## `protean new --pretend` is now `--dry-run`, and it writes nothing

**The `protean new` dry run flag is renamed, and its behaviour changes.** The
flag is `--dry-run` now. `--pretend` (with its `-p` short form) is gone.
Passing `--pretend` is a usage error. `--pretend` was copier's name for the
option. The rest of the CLI already says `--dry-run`, and so does the
`create_project` core it calls (`dry_run=`).

The dry run also behaves differently. It used to render through copier's own
`pretend` flag. Every step around that render made real changes. So a dry run
reached the target directory before it printed anything: with `--force` it
cleared the target, and without `--force` on a non-empty target it raised
`FileExistsError`. Neither is something a preview should do.

`--dry-run` renders into a system temp directory and prints the
project-relative path of each file it would create, one per line, sorted. The
dry run leaves the target directory alone whether or not it already has files
in it. `--force` no longer clears anything under a dry run. The list it prints
is the same set of files an apply produces from the same inputs.

The preview is also complete now. Protean writes `.protean/project.json`,
`AGENTS.md`, the `CLAUDE.md` bridge, and `.protean/dx-state.json` after the
copier render. The old dry run never listed these four files, though an apply
creates all of them.

### Who is affected

Anyone passing `--pretend` or `-p` to `protean new`. Pass `--dry-run` instead.

Anyone parsing the output of the dry run. It used to be copier's coloured
`create <path>` log, in copier's render order; it is now a plain list of
relative paths, sorted.

```shell
# Before: copier's own log, no manifest, no AGENTS.md
$ protean new myproject --pretend
Copying from template version None
    create  .gitignore
    create  docker-compose.override.yml
    ...

# After: one project-relative path per line, sorted, and the full set
$ protean new myproject --dry-run
.copier-answers.yml
.dockerignore
.env.example
...
.protean/dx-state.json
.protean/project.json
AGENTS.md
CLAUDE.md
...
src/myproject/domain.py
...
```

Anyone who used `--pretend --force` to clear a directory is also affected. That
clearing was a side effect of how the dry run was wired, and Protean never
documented it. It did delete files. If you want to clear the target, use
`protean new <name> --force` without `--dry-run`.

### Why it was not put behind a flag

A flag defaulting to the old behaviour would default to a preview that deletes
your files. No user asks a dry run to delete files, so there is no old
behaviour to preserve.

## `protean new .` and `protean new ..` are rejected

**Name the project with a single directory segment.** A project name has to be
a single directory segment now: a non-empty string, not `.` or `..`, and with
no `<>:"/\|?*` or whitespace. The first two used to pass validation. Passing
one raises `ValueError` before any file is touched.

### Who is affected

Anyone calling `protean new .` expecting it to scaffold in place. It never did
that. `project_name` feeds the template, so `.` produced a project with no
package directory (`src/domain.py` instead of `src/<name>/domain.py`). It also
wrote `name = "."` in `pyproject.toml`, and no installer accepts that name. The
generated tree did not build.

```shell
# Before: rendered a tree that could not be installed
mkdir myproject && cd myproject && protean new .

# After: name the project, then work inside it
protean new myproject && cd myproject
```

The single-segment rule also fixes a flaw in `--force`. `--force` removes the
contents of `<output_folder>/<project_name>`. A name of `.` or `..` pointed
that removal at the output folder or its parent. With a single-segment name,
`--force` can only clear the project directory.

## `protean new` refuses a target symlinked out of the output directory

**This breaks behaviour for symlinked targets only.** `protean new <name>`
writes to `<output-dir>/<name>`. If a symlink already sat at that path, every
step followed it. `--force` cleared the directory the link pointed at, and the
render wrote its files there. When the link pointed outside the output
directory, `protean new` deleted and wrote files outside the output directory.

The command now resolves the target first. If it does not sit directly inside
the resolved output directory, the command stops with a `ValueError` before it
clears or writes anything. `protean.scaffold.create_project` raises the same
error, on apply and under `dry_run`.

### Who is affected

Anyone who symlinked a project directory to another disk or another checkout and
then re-ran `protean new` over it. Render into the real location and symlink to
it afterwards, or point `--output-dir` at the directory that actually holds the
project:

```shell
# Before: followed the link and wrote (or cleared) at /mnt/work/myproject
ln -s /mnt/work/myproject myproject
protean new myproject --force

# After: name the real location
protean new myproject --output-dir /mnt/work --force
```

A symlink is still fine when it resolves to a path directly inside the output
directory, say `<output-dir>/other-name`. The command also refuses a symlink
that resolves deeper, like `<output-dir>/nested/other-name`. It checks that the
target's resolved parent is the resolved output directory.

## `DAO.update()` and `QuerySet.update()` are deprecated

**A deprecation, not a break.** Both methods still work in 0.18. They now emit a
`RemovedInProtean020Warning` (a `DeprecationWarning` subclass) and are removed in
0.20.0. Nothing else about their behaviour changes.

`DAO.update()` and `QuerySet.update()` take a field patch and write it straight
to the store. That skips the aggregate: the change does not go through a
behaviour method, so the rule that owns the change and the events it should raise
never run. The replacement is to load the aggregate, call a method on it that
applies the change, and persist it with `repository.add()`.

### Update a single aggregate

```python
# fragment
# Before: patch-and-persist through the DAO
repo = domain.repository_for(Order)
dao = repo._dao
order = dao.get(order_id)
dao.update(order, status="shipped")
```

After:

```python
--8<-- "reference/migration/v0-18/002.py:single"
```

A child entity has no repository of its own. Load the aggregate root, change the
child through the root, and `repo.add()` the root.

### Update many aggregates

`QuerySet.update()` patched every matched row in one call, but it was never one
transaction: it looped and persisted each row on its own. Load the matched
aggregates, invoke the behaviour method on each, and `repo.add()` each one.

```python
# fragment
# Before: bulk patch through the query set
repo = domain.repository_for(Order)
repo._dao.query.filter(status="pending").update(status="cancelled")
```

After:

```python
--8<-- "reference/migration/v0-18/002.py:many"
```

Each `add()` commits in its own transaction. `QuerySet.update()` gave you the
same granularity. Do not wrap the loop in one `UnitOfWork` to make the batch
atomic. Every `Order` is its own consistency boundary, and the rule is [one
transaction, one
aggregate](../../guides/change-state/unit-of-work.md#one-transaction-one-aggregate).
If every update in the batch has to succeed or fail together, the job is a
backfill and belongs outside domain behaviour.

### Run large backfills at the database level

A one-off migration that rewrites a column across a whole table is an
infrastructure job, not domain behaviour, the same way a hard delete is. Run it
at the adapter or database level, with a SQL `UPDATE` or an adapter-specific
bulk write. Do not use the deprecated domain-level path.

## String and Text no longer sanitize by default

**String and Text fields no longer sanitize by default.** An ordinary String or
Text field that left `sanitize` unset used to run `bleach.clean()` on every
value. The field stored the value HTML-escaped. The default is now `False`: an
unset field stores the raw input. `sanitize=True` and `sanitize=False` still
mean exactly what they did.

Two shapes were never sanitized and so do not change: a field with a real
`choices=` value, and a String or Text used as a container content spec such as
`List(String(max_length=50))`. `upgrade-check` skips both, as listed below.

This is a fail-open change: where a field silently escaped its input before, it
now stores it verbatim. That matters because sanitization is a display-layer
concern. Escaping on write bakes one encoding (HTML) into stored data, corrupts
values rendered in any other context (a plain-text email, a JSON API, a CSV
export), and is not a substitute for encoding output where it is actually
rendered. The default now matches that: store the real value, encode at the
point of display.

### Who is affected

Anyone who relied on the old default to escape stored values, on a String or
Text field with no explicit `sanitize=`. After the upgrade, that field stores
the raw input. Protean gives no warning at runtime, and the write succeeds.

`protean upgrade-check --opportunities` finds these sites for you once you are
on 0.18.0. It reports each String/Text field that leaves `sanitize` unset by
`module:line`. It lists every one, so you can use the report as a checklist.
Unset means either not passing `sanitize` at all or passing `None`, which the
field layer reads the same way.

`upgrade-check` skips these fields, because none of them changed behaviour:

- A field that gives `sanitize` a real value either way, by keyword
  (`sanitize=True`) or positionally (`Text(True)`, `String(255, None, True)`).
  It declared its intent.
- A field with a real `choices=` value. Choice values were never sanitized.
  (`choices=None` is not a choices field, so it is still reported.)
- A `String`/`Text` used as a container content spec, as in
  `List(String(max_length=50))`. A container reads the inner field's type and
  choices and never applies the inner field's sanitization. The inner field was
  not sanitized before the flip either.
- A `String` or `Text` that is not Protean's. The scan resolves the name back to
  a `protean.fields` import, so `from sqlalchemy import String` is not reported
  and `from protean.fields import String as StringField` still is.
- Every field, if the domain sets `[field_defaults] sanitize = true`. That opts
  the whole domain back into the old behaviour, so there is nothing to migrate.

The scan also skips a field whose arguments are hidden behind a splat
(`String(**opts)`). `sanitize` could be inside the splat, and a static scan
cannot see it. Check those by hand.

### Fix the fields that relied on escaping

Encode these String and Text values at each place that renders them as HTML.
Encoding at output is the lasting fix. It protects the values that a write-time
escape never could, such as a template that renders the same field in an email
or a CSV.

To restore the old behaviour instead, opt back in. For one field:

```python
# fragment
name = String(max_length=100, sanitize=True)
```

For a whole domain, set the domain-level default:

```toml
[field_defaults]
sanitize = true
```

Precedence is field kwarg > domain default > framework default, so a domain
default of `true` sanitizes every unset String/Text field, and a field can still
opt out with `sanitize=False`.

### Why it was not put behind a flag defaulting to the old behaviour

This change deliberately departs from the standard Tier-2 transition in the
breaking-change policy
([ADR-0004](../../adr/0004-release-workflow-and-breaking-change-policy.md#tier-2-behavioral-breaks)),
which is opt-in flag → warning window → default flip, with the flag defaulting
to the old behaviour. Here the default flips in a single release, with no
per-field runtime warning. The `[field_defaults] sanitize` flag defaults to the
**new** behaviour, and you set it to `true` to opt back in. It is silent at
runtime: the write succeeds and nothing warns.

That deviation is intentional. Storing an HTML-escaped value is the wrong
default for a domain model. `bleach` on write is also not the security control
it looks like. The old default did not deserve a transition across several
releases. A per-field runtime warning was rejected as noise on a path that is
usually harmless. A static check takes the place of the warning. `protean
upgrade-check --opportunities` lists the exact sites (see above), so you can
find every affected field at upgrade time, though the write gives no warning at
runtime. This change is not one of the two narrow single-release exceptions
that the breaking-change policy (ADR-0004) already lists, operational defaults
and silent correctness bugs. It is a security-relevant default flip, decided on
its own case.

### Reloading data written under a different default

The field reads the `sanitize` setting from the active domain at validation
time. A DB load, an event-sourced replay, or a serialization round-trip runs
the validator again. Say you wrote a value while sanitization was off, then
flipped `[field_defaults] sanitize` to `true`. The field cleans that value when
it loads again. `bleach` can lengthen a string (`&` becomes `&amp;`). A value
that fit `max_length` on write can then exceed it on reload and fail with `...
characters after sanitization, exceeding max_length`. Flip the domain default
with this in mind: it changes how already-stored values validate, not just new
writes. An explicit `sanitize=True` field does not have this problem. It
cleaned the value on write too, so the stored value already fits the bound (see
[ADR-0026](../../adr/0026-max-length-bounds-the-sanitized-value.md)).

## `choices` fields map to their declared column type

**The SQLAlchemy adapter builds a different column for a field with
`choices`.** Before 0.18 such a field got the adapter's fallback column, an
unsized string column. The adapter now builds the column from the type the
choice values share. That column is the same one a field of that Python type
gets without `choices`:

- String choices give `VARCHAR(n)`, where `n` is the field's `max_length`. This
  covers a `String` with `choices`, a `Status` over an Enum of strings, and a
  `String` whose `choices` is such an Enum.
- Integer choices give `INTEGER`. This covers an `Integer` with `choices`, an
  `IntEnum` class passed as `choices`, and a `Status` over an `IntEnum`.
- Float, boolean, `Decimal`, `date` and `datetime` choices give the float,
  boolean, numeric, date and date-time column of that database.

The adapter picks the column from the type of the choice values. The field
class does not decide it. A `Float(choices=[1, 2])` has integer values, so its
column is `INTEGER`.

The old column was `TEXT` on MySQL and MariaDB, `VARCHAR(max)` on SQL Server,
and an unsized `VARCHAR` on PostgreSQL and SQLite. With a non-string column
there, an `Integer` with `choices` saved `2` and loaded back the string `"2"`,
which the field then rejected.

Two kinds of choices keep the old column. The first is choices of more than one
type, such as `["a", 1]` or `[True, 1]`. The second is choices of one type that
has no column mapping, such as `bytes` values or a list of Enum members. An
annotation that starts with a `Literal` and joins another type, such as
`Literal[1] | str`, keeps the old column too. A union that starts with another
type, such as `int | Literal[1, 2]`, gets that type's column, as it did before
0.18. The Elasticsearch adapter does not change.

```python
# fragment
class Article(BaseAggregate):
    status: String(max_length=20, choices=["draft", "published"])  # VARCHAR(20)
    level: Integer(choices=[1, 2, 3], required=True)  # INTEGER NOT NULL
```

### Who is affected

New tables get the new columns. Protean never alters an existing table, so a
table created before 0.18 keeps its old columns until you change them. The
string columns work as they are. When a non-string choices column (integer,
float, boolean, decimal, date or date-time values) holds text, the field cannot
load it back, so change that column.

The MySQL and MariaDB index check now measures the columns of `choices` fields.
A declared `Index` over a `String` with `choices` counts its `max_length`:

- When Protean builds the table, the column used to be `TEXT`, so the index was
  rejected as unindexable. It now builds when the key fits.
- `protean schema render --indexes` used to count the field as zero bytes.
  `protean schema render --indexes` now rejects, with `IncorrectUsageError`, an
  index that fitted only because of that zero count.

A `String(choices=...)` gets `max_length=255` by default, so its column is
`VARCHAR(255)`. Three string choices fields have no length: a `String` declared
with `max_length=None`, a `Text` with `choices`, and a `Status` that sets no
`max_length`. Their column is `TEXT` on MySQL and MariaDB, which MySQL cannot
index. Protean rejects an index over any of these fields when it builds the
table. `protean schema render --indexes` used to pass such an index and now
rejects it too.

### How to change an existing table

For a table named `article` with the two fields above, where `level` is
required:

=== "PostgreSQL"

    ```sql
    ALTER TABLE article ALTER COLUMN status TYPE VARCHAR(20);
    ALTER TABLE article ALTER COLUMN level TYPE INTEGER USING level::integer;
    ```

    PostgreSQL keeps `NOT NULL` when it changes the type.

=== "MySQL and MariaDB"

    ```sql
    ALTER TABLE article MODIFY status VARCHAR(20);
    ALTER TABLE article MODIFY level INTEGER NOT NULL;
    ```

    `MODIFY` replaces the whole column definition. Leave out `NOT NULL` and the
    column becomes nullable without an error.

=== "SQL Server"

    ```sql
    ALTER TABLE article ALTER COLUMN status VARCHAR(20);
    ALTER TABLE article ALTER COLUMN level INTEGER NOT NULL;
    ```

    `ALTER COLUMN` replaces the nullability too. Leave out `NOT NULL` and the
    column becomes nullable without an error.

=== "SQLite"

    SQLite ignores the length of a `VARCHAR`, so `status` needs no change.
    SQLite cannot change a column's type in place, so rebuild the table for
    `level`:

    1. Create `article_new` with the new column types.
    2. Copy the rows across with `INSERT INTO article_new SELECT ... FROM article`,
       using `CAST(level AS INTEGER)` for the integer column.
    3. Drop `article` and rename `article_new` to `article`.
    4. Create the old table's indexes again. Dropping a table drops its indexes.

For any other type, use the column that the field's Python type gets without
`choices`. When the field is `required=True`, add `NOT NULL`.

Check first that every stored value fits the new type. A `status` longer than
20 characters makes the `ALTER TABLE` fail. A `level` that is not a whole
number makes it fail on PostgreSQL, MariaDB and SQL Server. MySQL 8 does not
fail: it rounds `'2.5'` to `3`.

## The InlineBroker no longer dead-letters a message its subscription owns

On the InlineBroker, when a `BrokerSubscription` or a `StreamSubscription`
consumes a stream, that stream now has one dead-letter destination: the
`{stream}:dlq` stream the subscription publishes. The broker's own nack ceiling
and its native dead-letter queue no longer apply to that stream. The
InlineBroker now holds a nacked message and redelivers it, as Redis Streams
already did. See the decision that the subscription owns retry and
dead-lettering
([ADR-0042](https://github.com/proteanhq/protean/blob/main/docs/adr/0042-subscription-owns-retry-and-dead-lettering.md)).

### Who is affected

Almost no code is affected. You have nothing to change in your code. The old
behaviour needed a `{stream}:dlq` publish that kept failing inside the same
process, on an in-memory test double. If your setup did that, the broker
eventually moved a message the subscription was holding to its native DLQ.
`protean dlq list` then showed the message under the `{stream}:dlq` name. It no
longer does: it stays held and is redelivered until the DLQ publish succeeds.

A test that asserted such a message reaches `protean dlq list` (or
`broker.get_dlq_messages`) has to assert the hold instead. Drive the DLQ outage
with `retry_delay=0` so the held message comes back on the next read.

A stream that you consume directly from the broker, with no subscription,
behaves as before. It still reaches the InlineBroker's nack ceiling, and the
broker moves the message to the native DLQ. Production adapters are unchanged
too. Redis Streams holds a nacked message pending, and Redis PubSub does not
support nack. Neither adapter had a second dead-letter destination that could
conflict with the subscription's.

### Why it was not put behind a flag

The bug was that the broker and the subscription both counted the same failure.
A flag that kept the old path would let the broker keep dead-lettering messages
that the subscription also tracks. This change uses the silent-correctness-bug exception in the breaking-change policy ([ADR-0004](../../adr/0004-release-workflow-and-breaking-change-policy.md#tier-2-behavioral-breaks)).

## Replay hazards on an event-sourced aggregate are now breaking

`protean ir diff` now classes four changes as breaking. It used to list them as
ordinary changes. Each of these changes stops Protean from rebuilding an
existing event-sourced aggregate from its events. None of them is a field
change, so the checker did not class them before:

| Change | Reported as |
|--------|-------------|
| `is_event_sourced` turned on or off | `event_sourcing_changed` |
| An aggregate's `stream_category` moved | `stream_category_changed` |
| The aggregate's identity moved to another field | `identity_field_changed` |
| An `@apply` handler dropped while its event survives | `apply_handler_removed` |

### Who is affected

A domain that makes one of these changes and runs `protean ir diff` in a check or
a pre-commit hook. The command used to exit `2`, the code for changes with none
breaking, and now exits `1`. A check that fails on any non-zero exit was already
failing. A check that fails only on exit `1` now fails too.

If your domains make none of these changes, your diff output stays the same.

### What to do

Treat the report as correct and revert the change. Each of these changes leaves
existing data that the aggregate can no longer load:

- An aggregate writes to `f"{stream_category}-{identifier}"`. When you **move
  the stream category**, the whole history stays under the old name, and a load
  of an existing aggregate finds an empty stream. Keep the old category. If the
  rename is genuinely wanted, copy or replay the existing streams under the new
  name first, as a data migration, outside the compatibility checker.
- When you **move the identity to another field**, a load asks for a stream
  keyed by a value that no writer ever used, with the same result. Keep the
  identity where it is.
- When you **turn event sourcing on**, the aggregate's existing state stays as
  table rows, and replay cannot rebuild from them. When you **turn it off**,
  the state stays as a stream, and the table-backed loader never reads it.
  Either direction needs a data migration first.
- When you **drop an `@apply` handler**, no handler applies the stored events
  of that type. `BaseAggregate._apply_handler` raises on an event with no
  handler. Keep the handler for as long as events of that type are in the
  store, even after you stop raising the event.

If you made the change on purpose and migrated the data by hand, add the
aggregate to the config-level `exclude` list, as for any break that the checker
cannot verify:

```toml
[compatibility]
exclude = ["ordering.order.order.Order"]
```

### Why it was not put behind a flag

The checker exists to report a change that leaves stored data unloadable, and
these four changes do that. Passing them clean was the bug. A flag that kept
the old behaviour would keep the checker silent about a domain whose aggregates
can no longer load. Catching that domain is the checker's job. This change uses the silent-correctness-bug exception in the breaking-change policy ([ADR-0004](../../adr/0004-release-workflow-and-breaking-change-policy.md#tier-2-behavioral-breaks)).

## Removing a field from an event-sourced aggregate needs `reserved`

`protean ir diff` reports removing a field from an event-sourced aggregate as
breaking, the same as for any persisted element. For an event-sourced aggregate
that removal is usually safe: its authoritative state is a stream of events, and
the snapshot is a rebuildable cache Protean discards and replays past when it no
longer constructs. But the removal is not safe on its own. A retained `@apply`
handler kept for a retired event can still assign the removed field, or call
its `add_<name>`/`remove_<name>` helper, and replay would raise on it.

To make `protean ir diff` rate the removal as safe, declare the removed name in
`reserved` on the aggregate:

```python
--8<-- "reference/migration/v0-18/004.py:reserved"
```

`reserved` is a declaration you add to tell the checker how to rate the
removal, like `renamed_from` and `deprecated`. Like `renamed_from`, `reserved`
also changes runtime behaviour. `deprecated` only changes the checker verdict:

- During replay only, an assignment to a reserved name is dropped instead of
  raising, so a retained handler for a retired event still rebuilds the
  aggregate. The live `raise_` path never takes this relaxation, so a write to a
  removed field on a new event still raises.
- For a removed association such as a `HasMany`, a retained handler may call the
  generated `add_<name>` or `remove_<name>` helper instead of assigning. During
  replay those calls are dropped too and return `None`. Replay also drops the
  child entities those calls would have added. The rebuilt aggregate does not
  have them. `get_one_from_<name>` and `filter_<name>` still raise, because a
  handler that reads the removed collection depends on it. On the live `raise_`
  path the helpers still raise `AttributeError`.
- A retained handler that calls such a helper has two more needs. The child
  entity class it builds has to stay in the domain, because deleting it breaks
  the handler and is itself a breaking `element_removed`. And the helper call
  needs `# type: ignore[attr-defined]`: type checkers do not know about
  `reserved`, so `mypy --strict` reports the helper as missing once the
  association is gone:

    ```python
    # fragment
    @apply
    def item_added(self, event: ItemAdded):
        self.add_items(OrderItem(name=event.name))  # type: ignore[attr-defined]
    ```

- Replay drops a call by the name alone. With a plain field such as `total`
  reserved, a call to `add_total` is dropped during replay too.
- `protean ir diff` rates the `field_removed` change as safe, citing
  `reserved`, in one case. The aggregate is event-sourced on both sides, and
  the new snapshot reserves the removed name. `protean ir diff` gives this
  rating on the assumption that the retained handlers only write the removed
  name. A handler that reads the removed collection still breaks replay, and
  the diff cannot see that.
- The declaration has to stay. When you take a name back out of `reserved` on
  an event-sourced aggregate, `protean ir diff` reports a breaking
  `reservation_removed`. Replay then stops dropping an assignment to the name
  or a call to its helpers, and a retained handler that still makes one raises
  again.
- Reusing a reserved name for a live field raises `IncorrectUsageError` at
  registration.
- A reserved name has to be a field name. An empty or private (`_`-prefixed)
  name raises `IncorrectUsageError` at registration.

`reserved` makes only a field removal safe. A type change or a newly required
field on an event-sourced aggregate stays breaking. The replay hazards above (a
moved stream category, a moved identity, a dropped handler whose event
survives) stay their own breaking changes.

## A RawIndex with an unknown dialect now raises

**Behavioural break, `Index.from_sql` and index DDL rendering.**
`Index.from_sql(dialect, ddl)` takes the dialect as a free string. Protean used
to accept, at registration, a dialect it does not render index DDL for. Every
call site that matched the dialect by name then dropped the index. The
aggregate looked indexed but never got the index on any database, and Protean
gave no warning.

`Domain.init()` now rejects it. A `RawIndex` with a `dialect` that Protean does
not render raises `IncorrectUsageError`. The error names the element, the index
(its name, or the DDL when it has no name), and the bad dialect. The dialect is
matched by exact string, so `"postgres"`, `"PostgreSQL"`, and `" postgresql"`
are all rejected: only `"postgresql"` renders.

The dialects the framework renders for are `postgresql`, `sqlite`, `mssql`,
`mysql`, and `mariadb`.

### Who is affected

Anyone who called `Index.from_sql` with a dialect name outside that set, most
often a typo. That declaration never produced an index, so the fix is to correct
the name:

```python
# fragment
# Before: accepted, then silently dropped, so no index on any dialect
Index.from_sql("postgres", "CREATE INDEX ix_data_gin ON outbox USING gin (data)")
```

After:

```python
--8<-- "reference/migration/v0-18/005.py:from_sql"
```

If you targeted a dialect Protean has no provider for, that DDL was never emitted
either. Remove the declaration, or wait for the provider.

### Why it was not put behind a flag

The old behaviour was a silent failure: the index the author declared was never
created. Accepting a dialect name that renders nothing is not a contract worth
preserving. The change raises the existing failure where you declare the index,
so you see it there. It adds no new failure. This change uses the silent-correctness-bug exception in the breaking-change policy ([ADR-0004](../../adr/0004-release-workflow-and-breaking-change-policy.md#tier-2-behavioral-breaks)).

## `protean schema render --indexes` rejects an unknown dialect

`--dialects` takes a comma-separated list. The command used to treat an
unrecognised name as the SQLite dialect. The command wrote a `.sql` file that
looked right, said the requested dialect in its header comment, and held DDL
compiled for a different database. It now raises:

```shell
$ protean schema render --domain my_package.domain --indexes --dialects postgres
Error: Unknown index DDL dialect 'postgres'. Supported: mariadb, mssql, mysql, postgresql, sqlite.
```

`postgres` is the spelling that catches people: the dialect is `postgresql`.
The command accepts the same set that `Domain.init()` checks a `RawIndex`
dialect against. Any dialect you can declare, you can also render.

### Who is affected

Anyone passing `--dialects` explicitly with a name outside that list. The
default (`postgresql,sqlite,mssql,mysql`) is unaffected, and so is every name
that was already valid. A script that silently produced SQLite DDL under
another dialect name now fails, and that failure is the intended fix.

### Why it was not put behind a flag

The old behaviour had no correct use. No caller wanted SQLite DDL under another
dialect's filename. This change uses the silent-correctness-bug exception in the breaking-change policy ([ADR-0004](../../adr/0004-release-workflow-and-breaking-change-policy.md#tier-2-behavioral-breaks)).

## The test-mode engine stops as soon as it is idle

`Engine(domain, test_mode=True).run()` and `protean server --test-mode` used to
run eleven 0.1-second cycles every time, so each run took at least 1.1 seconds.
Test mode now stops as soon as every subscription has run out of work. A run
with little to process finishes in a few milliseconds.

Test mode also pauses at most 10 milliseconds between a subscription's ticks,
whatever its `tick_interval`. A broker subscription used to wait a full second
before it saw the messages a handler had just raised.

Test mode keeps its time limits. Test mode still stops after about a second
when a subscription keeps finding work. It still waits up to five seconds for a
subscription to start. Test mode counts a failed event handler as work while
the handler's position waits for a retry. A test with a failing handler still
runs for the full second.

### Who is affected

A test that relied on the engine running for a fixed time while nothing was
left to process. For example, a test that expected the engine to retry a failed
outbox publish at its scheduled time within that second. Test mode now stops
before that time arrives. Assert on what the engine processed. If the test is
about retries, run the retry path directly.

### Why it was not put behind a flag

Test mode is for tests. Its documented job is to process the pending messages
and stop. The run time was never part of that contract. A production engine
behaves exactly as before.

## `protean server` and `protean observatory` apply `[logging]`

Single-worker `protean server` and `protean observatory` used to ignore the
`[logging]` section of `domain.toml`. The commands set up console logging
before the domain loaded, at the `PROTEAN_LOG_LEVEL` level or INFO.
`Domain.init()` then saw handlers on the root logger and skipped its own setup.
Both commands now call `Domain.configure_logging()` once the domain loads, the
way `--reload` and each multi-worker process already did. Your `level`,
`format`, `redact`, `per_logger`, `log_dir`, and sampling settings now take
effect. Engine logs now carry `correlation_id`.

`--log-level` and `--log-format` now override only the level and the format.
The rest of `[logging]` still applies. `--log-config` still replaces the
section.

With several `--domain` values, `protean observatory` applies the first
domain's `[logging]` section.

### Who is affected

Anyone who runs single-worker `protean server` or `protean observatory`. Log
output changes on upgrade in these cases:

- **You have a `[logging]` section.** Its settings now apply: a JSON `format`,
  a different `level`, redacted fields, and rotating log files when `log_dir`
  is set.
- **You have no `level` setting.** With no `[logging].level`, no
  `PROTEAN_LOG_LEVEL`, and no `--log-level`, the level now comes from the
  environment: `PROTEAN_ENV`, then `ENV`, then `ENVIRONMENT`. When none of
  these is set, a plain `protean server` or `protean observatory` logs at INFO
  with colored console output, as in 0.17. Under `PROTEAN_ENV=development` it
  now logs at DEBUG, and under `PROTEAN_ENV=test` at WARNING. See [A domain
  with no environment set logs at
  INFO](#a-domain-with-no-environment-set-logs-at-info).
- **You have no `redact` setting.** The default redaction keys (`password`,
  `token`, `secret`, `api_key`, and others) now mask those fields in log
  records.
- **Your domain module sets up logging when it is imported.** The `[logging]`
  setup now replaces it. Set `PROTEAN_NO_AUTO_LOGGING=1` to keep your own setup.
- **A `[logging]` value is invalid.** A bad value, such as a numeric `level`
  or an unwritable `log_dir`, now stops the command with an error. It used to
  be ignored, because `Domain.init()` catches errors in its own logging setup.
  Multi-worker and `--reload` workers already failed this way.

A multi-worker run without `--log-level` also changes: the supervisor now
forwards worker records at the `[logging]` level, so `level = "DEBUG"` shows
DEBUG records it used to drop.

### Why it was not put behind a flag

The documented behaviour is that the command applies `[logging]`. `--reload`
and the workers already applied it. The old single-worker result was a bug.

## `protean server` workers apply the logging flags

`--log-level`, `--log-format` and `--log-config` now reach the worker processes
of `protean server --workers N` and `protean server --reload`. Each worker
applies them the way the parent does: `--log-level` and `--log-format` override
the level and the format of `[logging]`, and `--log-config` replaces
`[logging]`. A worker started after a reload gets the same flags.

Before this, the workers ignored the flags. Once the domain loaded, each worker
applied `[logging]` and `PROTEAN_LOG_LEVEL` only.

### Who is affected

Anyone who passes a logging flag to a multi-worker or `--reload` run, or sets
`PROTEAN_LOG_LEVEL` for one. The workers' log output now follows the flags. For example,
`protean --log-level DEBUG server --workers 4` used to drop worker DEBUG records
when `[logging]` set a higher level, and now shows them. With `--reload`, the
worker's level, format and `dictConfig` all follow the flags now.

Before the domain loads, a worker now sets up its logging the same way the
parent does. With no logging flag, it logs at `PROTEAN_LOG_LEVEL` from the
moment it starts. Before, it logged at INFO until the domain loaded, so it
dropped the DEBUG lines it wrote while loading the domain. With no logging flag
and no `PROTEAN_LOG_LEVEL`, the worker starts at INFO. With `--log-format`
alone, the worker uses that format from the start. It takes its level from
`PROTEAN_LOG_LEVEL` and then `PROTEAN_ENV`, as the parent does. With
`--log-config`, the worker applies only that `dictConfig`, and
`PROTEAN_LOG_LEVEL` does not override it.

### Why it was not put behind a flag

The flags are documented to set the log level, the format, and the
configuration of `protean server`. Ignoring them in the workers was a bug.

## `[lint]` and `[observatory]` tables now load

The config loader keeps only the top-level sections listed in its defaults, and
`lint` and `observatory` were not in that list. The loader dropped, with no
warning, a `lint` or `observatory` section from any source. The sources are a
top-level table in `domain.toml`, a `[tool.protean.lint]` or
`[tool.protean.observatory]` table in `pyproject.toml`, and a key in a
`Domain(config=...)` dict. Both sections are now loaded, so their settings take
effect.

### Who is affected

- **You have a `[lint]` table.** `level`, `suppressions`, `rules` and the other
  `[lint]` keys now apply to `protean check` and `protean verify`. Every key
  except `level` also applies to the IR builder. A project that passed `protean
  check` can start failing. For example, `level = "info"` makes info findings
  gate, and a custom rule in `rules` can report findings. Run `protean check`
  and adjust `[lint]`.
- **Your `[lint]` table has a malformed value.** Protean used to ignore the
  values in `[lint]` and now checks them. These values are rejected:

    - a `[lint]` that is not a table
    - a bad `level`
    - a `suppressions` value that is not a table, or a suppression count that
      is not a non-negative integer
    - a `rules` value that is not a list of strings
    - a limit that is not a non-negative integer
    - a `check_*` flag that is not `true` or `false`

  `protean check` exits `2` and `protean verify` exits `4`. Building the IR
  raises `ConfigurationError` for the same values, except a bad `level`: the IR
  builder does not use `level`, so it does not check it. `protean ir show`, the
  MCP `check`, `validate` and `introspect` tools and the pre-commit hooks each
  report that error. `Domain.check()` raises it, even when the domain has
  validation errors. If your code calls `Domain.check()` directly and expects a
  result dict, catch `ConfigurationError`. Fix the value the error message
  names.
- **You commit a materialized IR.** `[lint]` settings change the IR's
  diagnostics, and the diagnostics are part of the IR checksum. `protean ir
  check` can report the committed IR as stale. Regenerate it.
- **You have an `[observatory]` table.** `trace_retention_days` now applies to
  trace persistence. The value goes through Python's `int()`: `3.9` becomes 3
  days, and `0` or a negative number turns trace persistence off. Protean uses
  the default of 7 days when `[observatory]` is not a table. It also uses the
  default when `int()` cannot convert the retention value (such as `"abc"` or
  `inf`).

Environment overlays such as `[test.lint]` were already loaded when
`PROTEAN_ENV` named that environment. The base `[lint]` table now loads too,
and Protean merges the overlay over it. Say you have both `[lint]` and
`[test.lint]`. Under `PROTEAN_ENV=test`, the effective settings now include the
`[lint]` keys that the overlay does not set.

### Why it was not put behind a flag

The `[lint]` and `[observatory]` tables are the documented way to configure
`protean check` and trace retention. Ignoring them was a bug.

## Logging filters now run for records from child loggers

Protean attached `ProteanCorrelationFilter`, `OTelTraceContextFilter` and
`ProteanRedactionFilter` to the root logger only. A
logger's filters run only for records logged on that logger. They do not run
for records that propagate up from a child logger such as
`logging.getLogger("myapp.orders")`. So those records did not get
`correlation_id` or `causation_id`, did not get the trace ids when telemetry
was on, and were not masked by `[logging].redact`.

When Protean configures logging, it now also attaches each filter to every
handler on the root logger. A handler filter runs for every record the handler
writes. Records from child loggers that reach those handlers now get the same
fields and the same masking as records logged on the root logger. With `protean
server --workers N`, each worker's queue handler gets the filters too. The
supervisor keeps the ids that a worker set on its records.

### Who is affected

- **You log through child loggers.** Their records now carry
  `correlation_id` and `causation_id`, and the trace ids when telemetry is on.
  A format string that uses `%(correlation_id)s` now works for them.
- **You rely on `[logging].redact` for stdlib records.** Values of the listed
  keys are now masked on records from child loggers too. Your log output now
  shows the mask where it used to show those values.
- **You list `correlation_id`, `causation_id`, `trace_id` or `span_id` in
  `[logging].redact` and read them from the log record.** The redaction filter
  now runs after the correlation and trace-context filters on the root logger
  and each of its handlers. Before, those filters wrote the real ids onto the
  record after redaction had run. Protean's JSON and console output masked the
  ids anyway. A formatter or filter that reads record attributes (a
  `%(correlation_id)s` format string, `caplog`) saw the real ids. It now sees
  the mask.
- **Your `dict_config` puts `ProteanRedactionFilter` or
  `OTelTraceContextFilter` on the root logger only.** Protean now copies each
  to every root handler, so records from child loggers are masked, or carry
  trace ids, too.
- **You set `correlation_id` or `causation_id` yourself through `extra=`.**
  The filter now overwrites them on records from child loggers, as it already
  did on records logged on the root logger. Outside a domain context both
  become `""`. Set `g.correlation_id` and `g.causation_id` in the domain
  context instead, and the filter picks them up.
- **You add a handler to the root logger after logging is configured.** That
  handler does not get the filters. Attach them to it yourself, for example
  `handler.addFilter(ProteanCorrelationFilter())` from
  `protean.integrations.logging`. Do the same for handlers on named loggers and
  for child loggers that set `propagate = False`. Their records never reach the
  root logger's handlers.
- **You call `configure_logging()` more than once with different `redact`
  keys.** Each logger and handler keeps the first `ProteanRedactionFilter` it
  got. The root logger keeps the keys from the first call. Handlers that a
  later call creates get the keys from that later call. With `dict_config`,
  those handlers also get the root logger's redaction filters, so they mask the
  keys from both calls. Under `protean server --workers N`, each worker sends
  its records through one queue handler. That queue handler masks every key set
  that the worker's root logger or its handlers held. A worker can then mask
  more keys than a single-process run does. This covers stdlib record
  attributes. The structlog processor that the last call built masks the fields
  logged through `get_logger()`. Those fields use only that call's keys. Pass
  the full list of keys on every call.

### Why it was not put behind a flag

The fields and the redaction are documented to apply to every stdlib record.
Protean skipped records from child loggers, and that was a bug.

## A zero read timeout on Redis no longer waits

On the Redis broker, `read_blocking(timeout_ms=0)` sent `XREADGROUP ... BLOCK
0`, which Redis reads as "wait until a message arrives". The subscription
engine calls it with `0` to check the primary stream without waiting when
priority lanes are on. That check hung on an idle stream. It logged
`broker.redis.read_blocking_failed` when the socket timed out, and it held up
the backfill lane.

`read_blocking(timeout_ms=0)` now returns at once, as the broker contract
describes. The broker rejects a negative `timeout_ms` and logs it as
`broker.redis.read_blocking_failed`. The call returns `[]`.

The `blocking_timeout_ms` subscription setting must now be positive. A value
of `0` raises `ConfigurationError` when the server starts. With the new
meaning, `0` would make the poll loop query Redis with no pause.

### Who is affected

- **You set `blocking_timeout_ms = 0` on a stream subscription.** The server
  now refuses to start. Before this release the setting logged
  `broker.redis.read_blocking_failed` every few seconds. Remove the setting to
  get the default, or set a positive value such as `1000`.
- **You call `broker.read_blocking(..., timeout_ms=0)` yourself to wait for
  a message.** Call it in a loop with a positive timeout instead. Values above
  1000 ms are capped at 1000 ms.
- **You run with priority lanes on.** An idle subscription now waits on the
  primary and the backfill stream in one read. Before, it waited on the primary
  stream only, which delivered production messages at once and held up the
  backfill lane. Now a message on either stream ends the wait. The subscription
  reads a production message at once when it arrives during an idle wait, and
  backfill messages are no longer held up. No setting change is needed.

### Why it was not put behind a flag

The broker contract says `0` means no wait, and the engine's priority-lane
check depends on that. Waiting forever on `0` was a bug. There is no setting
that waits forever. The read runs in a worker thread that shutdown cannot
interrupt. A client `socket_timeout` ends the wait early with an error.

## The memory provider's `raw()` raises `DatabaseError`, and some error logs drop the exception text

Two small changes came with the upgrade to ruff 0.16.

The memory provider's `raw()` raises `DatabaseError` when the query is not
valid JSON. It used to raise a bare `Exception`. The `json.JSONDecodeError` is
kept as the cause. Before it parses the query, `raw()` replaces every `'` with
`"`. A query written with single quotes still parses. Until something has been
saved to the store, `raw()` returns `[]` without parsing the query.

Error logs in the observatory API, the server subscriptions and the worker
supervisor no longer put the exception text in the message. They are logged
with `logger.exception`, so the record still carries the exception and its
traceback in `exc_info`. For example, a worker that fails on start now logs
`Worker 3 failed` with the traceback, where it logged `Worker 3 failed: db
unreachable`. The subscription retry log is now `Error in subscription <name>
(attempt <n>)`. The DLQ log is now `Failed to move message <id> to DLQ`.

### Who is affected

- **You catch the error from the memory provider's `raw()`.** An
  `except Exception` handler still catches it. An `except DatabaseError` or
  `except ProteanException` handler now catches it too, where it did not
  before. Check that such a handler is meant to see a malformed query.
- **You match exception text in log messages.** If a log filter, an alert rule
  or a search looks for the exception text in the message line of these
  records, it no longer finds it. Match on the exception in `exc_info` instead,
  or on the traceback in the formatted output. A JSON formatter writes the
  traceback to its own field, so search that field.

### Why it was not put behind a flag

`DatabaseError` is a subclass of `Exception`, so no handler that caught the
error before stops catching it. The exception text was printed twice before:
once in the message and once in the traceback. It is still printed once.

The IR diff also accepts a removal version written as a number, such as

Only code where one of these paths raised some other exception. In 0.17 that

### Why it was not put behind a flag

Each fallback was written for one known case. When a fallback also caught every

## A failed post-invariant rolls back the change

**A failed post-invariant now undoes the change.** When an `@invariant.post`
check failed after a change, Protean raised the error but left the new value on
the object. Now the change is undone: the object keeps its previous state, and
its changed flag goes back to what it was before the change.

The rollback covers:

- field assignments of every kind (plain, value object, `Reference`, `HasOne`
  and `HasMany`), on the aggregate and on its child entities
- `add_<field>()` and `remove_<field>()` calls
- `atomic_change` blocks: when the check at the end of the block fails, Protean
  undoes every change in the block, child entities and associations included.
  It also discards the events raised inside the block
- events raised on event-sourced aggregates: when a check fails after the
  `@apply` handler, `raise_()` undoes the handler's field changes. It also
  leaves the event out of `_events`

The rollback also runs when the invariant fails with an error other than
`ValidationError`.

## A `ValueError` at commit is no longer reported as a version conflict

The unit of work turned almost every `ValueError` raised during commit into
`ExpectedVersionError`, with the outbox on or off. The one exception was a
`ValueError` from saving the outbox rows, which raised `TransactionError`. A
handler's version retry then ran the handler again, even when the failure had
nothing to do with a version conflict.

Now only a real version conflict raises `ExpectedVersionError` at commit:

- Message DB reports a wrong expected version as an error with the `P0001`
  code. The Message DB event store's `append` and `_write` now raise
  `ExpectedVersionError` for that error itself, inside or outside a unit of
  work. It raised `ValueError` before. Other Message DB errors still raise
  `ValueError`.
- The memory event store raises `ExpectedVersionError` itself on a wrong
  expected version. It raised `ValueError` before. The message text is the
  same: `Wrong expected version: 0 (Stream: ..., Stream Version: 1)`.
- Any other `ValueError` raised during commit becomes `TransactionError`, with
  or without the outbox. Its `extra_info["original_exception"]` is
  `"ValueError"`, and its `__cause__` is the `ValueError`. The version retry
  does not run the handler again.

### Who is affected

- Code under `event_processing = "sync"` where an event handler raises a
  `ValueError` (a pydantic `ValidationError` is one). The handler runs inside
  the commit, so the caller used to see `ExpectedVersionError`. The enclosing
  command handler's version retry then ran a command whose events were already
  stored. The caller now sees `TransactionError`, with the `ValueError` as its
  `__cause__`. The command runs once. The 0.17 guide describes the old behavior
  under [A failing handler method no longer stops its
  siblings](v0-17.md#a-failing-handler-method-no-longer-stops-its-siblings) and
  [Sibling handler classes are independent in failure under synchronous
  dispatch](v0-17.md#sibling-handler-classes-are-independent-in-failure-under-synchronous-dispatch).
  A single failing handler raising `ValueError` now surfaces the same way as
  any other single failure.
- Code that catches `ExpectedVersionError` around a commit and expects it for
  a `ValueError` that is not a version conflict. Catch `TransactionError` for
  those failures.
- Code that catches `ValueError` from the memory or Message DB event store's
  `append` or `_write` on a wrong expected version. Catch
  `ExpectedVersionError` instead.

At commit, version conflicts on the commit's own writes (Message DB, the memory
event store, relational providers) still raise `ExpectedVersionError` and are
still retried. Protean reports a conflict from a synchronous event handler in a
different way; see the next section.

### Why it was not put behind a flag

Both the `TransactionError` change and the event store change correct a bug.
Retrying a failure that is not a version conflict runs the handler again for no
reason. The memory and Message DB event stores now report a conflict with the
error the unit of work reports for the relational providers.

## A synchronous event handler's version conflict no longer reruns the command

Under `event_processing = "sync"`, event handlers run inside the command's
commit, after the command's writes are saved. When a handler raised
`ExpectedVersionError`, the commit passed it to the caller unchanged. The
command handler's version retry then ran the command again, and the command
saved its writes a second time. On an event-sourced aggregate the second run
appended the command's events again.

Now any `Exception` from a synchronous event handler, `ExpectedVersionError`
included, reaches the caller as `TransactionError`. A `BaseException` that is
not an `Exception`, such as `KeyboardInterrupt`, still passes through
unchanged.

- The `TransactionError`'s `__cause__` is the handler's `ExpectedVersionError`.
  When only this handler fails, its `extra_info["original_exception"]` is
  `"ExpectedVersionError"`.
- Under `command_processing = "sync"`, the command runs once. Under
  `command_processing = "async"`, the command's subscription redelivers the
  failed command and it runs again, as it does for any handler failure.
- When version retry is enabled, the retry inside `@handle` on an event handler
  or a projector still retries the conflict. When a handler conflicts once and
  then succeeds, the command succeeds. A process manager has no such retry, so
  Protean reports its conflict at once.
- A conflict in one handler class no longer stops the other handler classes
  for the same event. All the handler classes run. When more than one fails,
  the `__cause__` is an `ExceptionGroup` that holds every failure.
- A conflict on the command's own writes still raises `ExpectedVersionError`,
  and the command's version retry still retries it.

### Who is affected

Code under `event_processing = "sync"` that catches `ExpectedVersionError`
from `domain.process()` and expects it for a conflict in an event handler.
Catch `TransactionError` and read its `__cause__`:

```python
# fragment
from protean.exceptions import ExpectedVersionError, TransactionError

try:
    domain.process(PlaceOrder(order_id=order_id))
except TransactionError as exc:
    if isinstance(exc.__cause__, ExpectedVersionError):
        ...  # an event handler conflicted; the order is already placed
    raise
```

The same holds for a `ConfigurationError` raised by a synchronous event
handler. It used to reach the caller unchanged and now arrives as the
`__cause__` of a `TransactionError`. A `ConfigurationError` raised by the
commit itself, outside the event handlers, still reaches the caller unchanged.

Some `protean.testing` helpers run handlers synchronously: `given(Aggregate,
*events)`, `given(event, ...).then()`, `given(event, ...).results_in()` and
`given(ProcessManager, *events)`. They call the same dispatch outside any
commit, so they raise no `TransactionError`. A lone failing handler still
raises its own exception, `ExpectedVersionError` included. In these helpers,
the change is that the conflict no longer stops the other handler classes. When
another one also fails, the test gets an `ExceptionGroup` holding both, where
it used to get the `ExpectedVersionError`.

Code under `event_processing = "async"` sees no change. There, each handler
runs in its own subscription and retries on its own.

### Why it was not put behind a flag

Running the command twice saves its writes twice, so the old behaviour was a
bug.

## A domain with no environment set logs at INFO

**Log output changes when no environment is set.** In 0.17, `Domain.init()`
treated an unset environment as `development` and logged at DEBUG. With
`PROTEAN_ENV`, `ENV` and `ENVIRONMENT` all unset, `domain.init()` in a script
or a REPL session printed a DEBUG line for every provider and broker it
registered. Protean now logs at INFO when no environment is set. The output
stays colored console. Only an explicit `PROTEAN_ENV=development` (or `ENV` or
`ENVIRONMENT`) selects DEBUG.

Three related changes go with it:

- **Protean no longer logs the `Exception::` debug line.** When you created a
  Protean exception with messages, such as a `ValidationError` that your code
  catches, Protean used to log `Exception:: {messages}` at DEBUG. It now logs
  nothing.
- **A broken plugin logs a WARNING.** When loading or registering a provider or
  broker plugin raises an error other than `ImportError`, Protean logs `Failed
  to load provider plugin` (or `broker plugin`) at WARNING. You see that line
  at the default level.
- **An `ImportError` is a DEBUG skip.** When loading or registering a plugin
  raises any `ImportError`, Protean logs `Skipping provider plugin` (or `broker
  plugin`) at DEBUG with the error text. The usual cause is a missing optional
  extra, such as the Redis brokers without `protean[redis]`. The error text
  then names the missing module. Protean also skips at DEBUG on an
  `ImportError` from a bug inside a plugin, such as `cannot import name ...`.
  When a plugin you expect does not register, set the level to DEBUG.

### Who is affected

Anyone who runs a domain with no environment variable set and reads its DEBUG
output, or the INFO lines from `protean.core` and `protean.adapters`. This
covers a script, a REPL, `protean shell`, and a FastAPI app that calls
`domain.init()`. A plain `protean server` or `protean observatory` logged at
INFO in 0.17 and still does. To get the DEBUG lines back, set one of these:

```shell
export PROTEAN_ENV=development
# or
export PROTEAN_LOG_LEVEL=DEBUG
```

`protean --log-level DEBUG <command>` and `level = "DEBUG"` under `[logging]`
in `domain.toml` work too. The `Exception::` line does not come back at any
level.

### Why it was not put behind a flag

The change lowers what a default run prints. At INFO, Protean holds
`protean.core` and `protean.adapters` at WARNING, as it already did for an
explicit INFO level. Their INFO lines, such as `Executing use case` and the
broker INFO lines, stop printing along with the DEBUG lines. The default level
gains one line: the WARNING for a plugin that fails with an error other than
`ImportError`. That line reports a real fault. One environment variable brings
back all of these lines except `Exception::`. The `Exception::` line repeated
the messages that the exception already holds.

`Message.to_domain_object()` rebuilds an event from a stored message. The
rebuilt event used to drop the stored `correlation_id` and `causation_id`.
Outside a handler both came back as `None`. Inside a handler they were
replaced with the IDs of the message being handled. The rebuilt event now
keeps the IDs it was stored with. A stored ID that is empty stays empty, even
inside a handler. A rebuilt command works the same way: an empty stored
`causation_id` is no longer filled with the ID of the message being handled.

`origin_stream` follows the same rule for both. The stored value used to be
ignored. A rebuilt event took the `origin_stream` of the command being
handled, if that command had one. A rebuilt command took the stream of the

delivered to its own handler, it came back as `None`. The rebuilt event or
command now keeps the `origin_stream` it was stored with, and an empty one
stays empty.

`origin_stream` on a rebuilt event or command and relies on the old values.

current handler's message.

### Why it was not put behind a flag

The stored values are the correct ones. The old values were wrong for any code

## An event or command rebuilt from a stored message keeps its store positions

`Message.to_domain_object()` used to drop the stored message's
`event_store` metadata, so `_metadata.event_store` was always `None` on a
rebuilt event or command. The rebuilt event or command now keeps it, with
`position` (the position in its stream) and `global_position` (the position
across the whole store).

A handler sees the positions only when it is given a message read back from the
event store. That happens with event store subscriptions and during a
projection rebuild. A handler on a stream subscription, or a handler that runs
synchronously, gets the event as it was raised, before the store assigned
positions. `_metadata.event_store` is `None` there. The exception is an event
that the outbox reconciler sends again after a crash. The reconciler rebuilds
the outbox row from the stored message, so that event arrives with its
positions. When you build a new event or command from another one's metadata,
the store has never held it, so it has no positions either.

When you write a rebuilt event or command again, Protean does not copy its old
positions. The store assigns new ones on the write.

### Who is affected

Code that reads `_metadata.event_store` on a rebuilt event or command and
expects `None`. Nothing needs to change unless your code relied on that.

### Why it was not put behind a flag

The positions say where the store holds the message. The `Message` already
carried them. Protean dropped them on the rebuilt object, and that was a bug.
No code was meant to depend on it.

## A non-boolean `sequential_by` on a process manager is deprecated

## An integer identity under the `uuid` strategy is refused on SQL

The `uuid` identity strategy makes an integer identity from `uuid4().int`, a
128-bit number. No SQL integer column holds it. `Domain.init()` now raises
`ConfigurationError` when an aggregate, entity or projection on a SQL provider
(SQLite, PostgreSQL, MySQL/MariaDB or MSSQL) gets an integer identity under
that strategy. The message names the element and the provider.

The check reads the identifier's own `identity_type` and `identity_strategy`
arguments first, then the domain configuration. It skips an element whose
custom database model declares the identity column itself. That model chooses
the column's type.

### Who is affected

Before this release, on a domain whose `identity_type` is `"integer"`, Protean
could not build a SQL model for an element with a generated identifier. The
build raised `TypeError: Integer() takes no arguments`. That SQL model now
builds. The uuid case fails at `Domain.init()` with a clear message. On such a
domain, Protean still cannot build an identifier that sets
`identity_type="string"` itself. Its column is an integer column, so
`Domain.init()` raises `ConfigurationError`. Drop `identity_type` from the
field. Two cases built before and are unchanged: an identifier declared with
`Auto(increment=True)`, and an event-sourced aggregate, which has no SQL table.

The change that breaks working code is narrower. An identifier that sets
`identity_type="integer"` itself, on a domain whose `identity_type` is
`"string"`, used to save. Its column follows the domain's `identity_type`, so it
was a text column, and the 128-bit number went into it as text. That identifier
is now refused:

```python
# fragment
# Before: saved the 128-bit number into the text column
@domain.aggregate
class Order:
    order_id: Auto(identifier=True, identity_type="integer")
```

Pick one of the two paths the error names:

- Set `identity_strategy="function"` with an `identity_function` that returns
  integers. Protean sets the id when it creates the aggregate. The column stays
  a text column.
- Declare the identifier as `Auto(increment=True)`. The database assigns the id
  on the first save. The column becomes an integer column, so the table needs a
  schema change. Existing rows keep their 128-bit ids, and those ids do not fit
  the integer column. Use this path for a new table. Columns in other tables
  that reference the aggregate follow the domain's `identity_type` and stay
  text columns.

The memory provider holds the 128-bit value. Elasticsearch stores it as a
string. The memory provider and Elasticsearch behave as before.

## Saving the same aggregate instance again writes a new version

Say you save an aggregate instance, change it, and save it again in a later
transaction without reloading it. The second save now writes a new version.
Before, the second save wrote the version the instance already had. Its events
reused the ids of the first save's events (`<stream>-0.1` twice). An event
handler that deduplicates by event id dropped the second event. A copy loaded
before the second save could also overwrite it without an
`ExpectedVersionError`.

Now each committed transaction advances the instance the way a reload would.
After the commit, `_version` is the version just written and `_next_version` is
one more. Events raised after it are numbered from the next version
(`<stream>-1.1`). If the transaction rolls back, `_version` goes back to the
version the instance had before the transaction. On a provider without
transactions, such as Elasticsearch, the rollback does not undo the write. The
instance keeps the version it wrote. Unless another writer saved the aggregate
in the meantime, the instance can be changed and saved again without a reload.

Event-sourced aggregates track their versions from their events, so none of
this applies to them.

Adding one instance several times inside a single `UnitOfWork` still writes
one version for that transaction. The events raised between those adds are
numbered within it (`<stream>-0.1`, `<stream>-0.2`).

Inside a `UnitOfWork`, a `get()` or query returns the same instance when the
transaction has already loaded or saved that aggregate. The instance carries
any changes made to it since. Before, each read built a new copy. Each copy
counted its version and event position from the store, and the store had not
seen the other copies' pending changes. Events raised on an earlier copy were
lost, and saving a later copy could raise `ExpectedVersionError`. This holds
for event-sourced aggregates too: before, a `get()` returned the tracked
instance only after `add()` had saved it with new events.

### Who is affected

Code that keeps an aggregate instance across transactions and saves it more
than once. Two things change for it:

- `_version` on the stored record and on the instance goes up by one for each
  committed transaction that saves it.
- When you save a copy loaded before one of those saves, it now raises
  `ExpectedVersionError`. Before, it silently overwrote the newer record.
  Reload the aggregate and apply the change again, as you would for any version
  conflict.

When your code reads the same aggregate more than once inside one `UnitOfWork`,
it now gets one instance back. This is how the identity map in SQLAlchemy's
session and in Hibernate behaves. Look for code that changes an aggregate,
decides to abandon the change, and calls `get()` again to start over. The
second `get()` returns the changed instance. If the code then saves it with
`add()`, the abandoned change is written too. Events raised before the second
`get()` are saved at commit even without `add()` on a state-based aggregate. On
an event-sourced aggregate they are saved only through `add()`. Before, the
second `get()` returned a copy of the stored record. The events raised on the
first copy were dropped.

To abandon a change, raise an exception so the `UnitOfWork` rolls back. To read
the stored state, read the aggregate in a new `UnitOfWork`. A change that
breaks an invariant needs neither step. Protean undoes the assignment when the
check fails.

A QuerySet evaluated in one `UnitOfWork` transaction, or outside any, runs its
query again when it is read in a different transaction. Before, it returned
copies of its cached results. A copy of an aggregate that the transaction
tracked lost the events raised on it. The cached values could also be older
than the stored values.

If your code loads an aggregate once per transaction, it sees no difference.

### Why it was not put behind a flag

The old behaviour lost events for handlers that deduplicate by id. It also let
a stale copy overwrite newer data. When code read a new copy inside a
transaction, it lost events or raised a conflict with no other writer. No
correct program could rely on any of these.

## A failed IR build now fails `check`

`Domain.check()` used to log a failure to build the IR, with its traceback,

corrects the old result.

## Domain traversal loads modules in name order

When `Domain.init()` traverses the domain's folder, it now loads the root
directory's files first, then each subdirectory in name order, with the files
in each directory sorted by name. It used to load them in the order that
`os.listdir` returned. That order depends on the filesystem.

### Who is affected

A domain that registers enrichers from more than one traversed module, when
the result depends on the order they run in. Enrichers run in registration
order, and a module's enrichers register when the module loads, so the new
load order can change that order. Two cases depend on it:

- Two enrichers write the same field or the same metadata key. The one that
  runs last wins.
- An aggregate enricher reads a value that another one sets. Aggregate
  enrichers change the same aggregate one after another, so swapping their
  order can change what is saved even when they write different fields.

Enrichers that each set their own fields and read nothing another one sets are
not affected.

To keep a fixed order of your own, register the enrichers from one module,
such as the module that creates the `Domain`, in the order you want.

### Why it was not put behind a flag

The old order was not a contract. Two machines with different filesystems
could already run the same enrichers in different orders. The IR now records
enricher order, so it has to be the same on every machine.

## A missing MySQL or MSSQL driver fails `domain.init()` with `ConfigurationError`

The MySQL and MSSQL providers now check for their driver when `domain.init()`
builds them. When the driver cannot be imported, `domain.init()` raises a
`ConfigurationError`. The message names the database's configured name, the
driver and the extra to install:

```text
Database 'default' uses a 'mysql+pymysql://' URL, but the 'pymysql' driver cannot be imported (No module named 'pymysql'). Install it with `pip install "protean[mysql]"`.
```

`domain.init()` used to raise the driver's own `ModuleNotFoundError`, from
inside SQLAlchemy.

Which driver is checked depends on the `database_uri`:

- `mysql+pymysql://` and `mariadb+pymysql://` are checked for PyMySQL, the
  driver the `protean[mysql]` extra installs.
- A plain `mysql://` or `mariadb://` is checked for mysqlclient (`MySQLdb`),
  because SQLAlchemy connects through mysqlclient for those URLs. When
  mysqlclient is missing, the message asks you to add `+pymysql` to the URL
  and install `protean[mysql]`. When mysqlclient is installed, the URL works as
  before.
- Protean checks for pyodbc on `mssql+pyodbc://` and a plain `mssql://`. pyodbc
  installed without the unixODBC system library fails to import, so it raises
  `ConfigurationError` the same way.
- Protean does not check a `database_uri` that names another driver, such as
  `mysql+mysqldb://` or `mssql+pymssql://`. Protean passes that URL to
  SQLAlchemy as written. A missing driver there still raises SQLAlchemy's
  error.
- A database config with a `module` key is not checked either. Protean passes
  it to SQLAlchemy's `create_engine()`, which uses that module as the driver.

### Who is affected

Code that catches `ModuleNotFoundError` or `ImportError` around
`domain.init()` to detect a missing MySQL or MSSQL driver. Catch
`ConfigurationError` instead. The original import error is on its
`__cause__`.

If the driver SQLAlchemy uses for your URL is installed, nothing changes.

### Why it was not put behind a flag

The old error came from deep inside SQLAlchemy and did not say which extra
installs the driver. The MySQL and MSSQL providers now report a missing driver
the way the PostgreSQL provider does.

## The `database_model` element option is removed

`@domain.aggregate`, `@domain.entity` and `@domain.projection` no longer take a
`database_model` option. `domain.register()` no longer takes the option on
those elements either. The option never had any effect. Protean accepted it,
stored it and then built its own database model anyway, so a custom model
passed this way was never used.

Passing the option now fails at registration:

```python
# fragment
# Before
@domain.aggregate(database_model=UserModel)
class User:
    email: String(max_length=255, required=True)
```

```text
ConfigurationError: Unknown option(s) {'database_model'}
```

Register the custom model with `@domain.database_model` instead, and name the
element it belongs to with `part_of`:

```python
--8<-- "reference/migration/v0-18/010.py:setup"
--8<-- "reference/migration/v0-18/010.py:fix"
```

See [Database Models](../../guides/change-state/database-models.md) for how a
custom model maps columns to fields.

### Who is affected

Code that passes `database_model=` to `@domain.aggregate`, `@domain.entity`,
`@domain.projection`, or to `domain.register()` for one of those elements. Code
that reads `meta_.database_model` on an element also breaks, since the key is
gone from `meta_`.

If you already register custom models with `@domain.database_model`, nothing
changes.

### Why it was not put behind a flag

The option did nothing, so there is no old behaviour to keep. A flag would
only keep a setting that looks like it works and does not.

## mypy sees decorated elements as subclasses of their base

Under the mypy plugin, mypy treats a class decorated with `@domain.aggregate`,
`@domain.entity` or another element decorator as a subclass of its Protean base
class, as it is at runtime. Before, the plugin copied the base's methods onto
the class, so mypy rejected a decorated element wherever a signature named the
base class.

Nothing changes at runtime.

### Who is affected

Projects that run mypy with `plugins = protean.ext.mypy_plugin`. What can
change in a mypy run:

- mypy now reports an `assignment` error for a field or method that reuses the
  name of a base-class attribute with a different type. It was a `no-redef`
  error before, so a `# type: ignore[no-redef]` on that line no longer covers
  it. pydantic's `BaseModel` defines methods such as `json`, `copy` and
  `schema`. A field with one of those names already shadows the method at
  runtime. Rename the field.
- The decorator rebuilds the class on its Protean base alone, so it drops a
  mixin listed as a base. mypy now reports the mixin's methods as missing,
  which matches the runtime.
- A decorated aggregate, entity, value object, command, event, projection or
  query with no fields now has an `__init__` that takes no keywords. Passing a
  keyword is a `call-arg` error.
- mypy now types a field declared in the annotation-only form (`name:
  String(...)`) as `Any`, and no longer reports `valid-type` on it. Such a line
  no longer needs a `# type: ignore[valid-type]` or `# type: ignore[call-arg]`,
  and `warn_unused_ignores` reports one that remains.

## A value object's string `part_of` must name an aggregate

`@domain.value_object(part_of="Product")` now resolves the string to the
`Product` aggregate class at `domain.init()`, as it already did for entities,
events, commands, command and event handlers, application services and
repositories. Before, the value object's `meta_.part_of` stayed the string
`"Product"`. `protean ir` then failed with an `AttributeError` for a value
object that no `ValueObject` or `ValueObjectList` field embeds. `protean check`
reported that `AttributeError` as an error.

The name is looked up among aggregates only. When no aggregate has that name,
`domain.init()` raises `ConfigurationError`:

```text
Unresolved references in domain `Shop`: `TierPrice` references `Prodct` via part_of
```

### Who is affected

Domains where a value object's string `part_of` is misspelt, or names an
entity instead of an aggregate. Those domains used to initialize and failed
later, or never. Name the aggregate the value object belongs to, or pass the
aggregate class:

```python
# fragment
# Before: initialized, then failed inside the IR builder
@domain.value_object(part_of="Prodct")
class TierPrice:
    amount: Float(required=True)

# After: name the aggregate
@domain.value_object(part_of="Product")
class TierPrice:
    amount: Float(required=True)
```

One case worked before and now fails `domain.init()`. Take a value object that
an entity embeds through a `ValueObject` field, with a string `part_of` that
names that entity. It built without errors, because the IR placed it through
the field. Name the entity's aggregate instead:

```python
# fragment
# Before: initialized and built, though `Line` is an entity
@domain.value_object(part_of="Line")
class Discount:
    percent: Float()

# After: name the aggregate that owns `Line`
@domain.value_object(part_of="Order")
class Discount:
    percent: Float()
```

A string `part_of` that names an aggregate still works. The IR build no longer
fails on it.

### Why it was not put behind a flag

The old behaviour kept an unresolved name with no error or warning. The IR
build then crashed on it. Entities, events, commands, command and event
handlers, application services and repositories already reject a `part_of` they
cannot resolve at `domain.init()`. Value objects now do the same.

## `DomainFixture.setup()` warns about a broker that does not answer

`DomainFixture.setup()` now pings every configured broker once, after
`domain.init()` and before it creates the database schema. For each broker that
does not answer, it emits a `UserWarning`. The warning names the broker and its
URI, with any password shown as `***`:

```text
UserWarning: Broker 'default' at redis://127.0.0.1:6379/15 did not answer a
ping. Tests that publish to it will fail, and the per-test reset cannot clear it.
```

Sometimes the broker has no URI, or Protean cannot show its URI without risking
part of the password. The warning then names the broker's provider instead, as
in `Broker 'default' (redis provider)`.

Before, a suite whose tests never published to a down broker passed with no
visible sign of it. A wrong password or a denied command also makes the ping
fail.

### Who is affected

Suites that turn warnings into errors, with `pytest -W error::UserWarning`, `-W
error`, or `filterwarnings = ["error"]` in the pytest configuration. In those
suites, `setup()` now raises the warning when a broker does not answer. The
session fixture fails before any test runs. The raise comes before the schema
is created, so no tables are left behind.

Start the broker before the run, or point the domain at a broker that answers.
To keep the old behaviour in a suite that runs without a broker, ignore this
one warning:

```toml
[tool.pytest.ini_options]
filterwarnings = [
    "error",
    "ignore:Broker .* did not answer a ping:UserWarning",
]
```

Suites that leave warnings as warnings see one entry per down broker in
pytest's warnings summary. Nothing else changes.

## Outbox processors run only for providers an aggregate is stored in

When the outbox is enabled, the engine used to run an outbox processor, and one
external processor per broker in `outbox.external_brokers`, for every managed
database provider. That included the built-in `memory` provider, which the
default configuration always defines. A domain that stores everything in
`default` on Postgres ran these four:

```text
outbox-processor-default-to-default
outbox-processor-memory-to-default
outbox-processor-default-to-global-external
outbox-processor-memory-to-global-external
```

Nothing writes to the `memory` outbox in that domain, so the two `memory`
processors had nothing to publish. The engine now runs processors only for a
managed provider that at least one concrete aggregate names in its `provider`
option. Event-sourced aggregates count. Abstract aggregates, projections and
internal elements do not.

### Who is affected

Anyone who reads outbox rows in `/readyz` `checks.subscriptions` or in `protean
subscriptions status`. Protean no longer lists rows for providers that no
aggregate uses, so `total` drops by that number of rows. The response shape
does not change. If a dashboard or alert expects a fixed row count, or names a
`memory` processor, update it.

If you move the last aggregate off a provider, rows already pending in that
provider's outbox have no processor to publish them. The engine logs an
`engine.outbox_rows_without_processor` warning at startup that names the
provider and the number of unpublished rows. Publish or clear those rows
before the move, or keep an aggregate on that provider until they drain.

## The multi-worker Supervisor waits for the drain window

`protean server --workers N` runs a Supervisor that stops its workers on
shutdown. It used to send `SIGKILL` to any worker still running 30 seconds
after `SIGTERM`, whatever `server.drain_timeout` said. The Supervisor could
kill a worker with a drain window above 25 seconds before the worker's
in-flight handlers finished.

The Supervisor now reads `server.drain_timeout` from the project config. It
waits for the drain window plus 5 seconds, and never less than 30 seconds. With
the default window of 10, nothing changes. The engine's
`engine.drain_timeout_at_or_above_supervisor_kill_timeout` startup warning is
removed, because no fixed 30-second limit is left to warn about.

### Who is affected

- Anyone with `drain_timeout` above 25 seconds and more than one worker. A
  worker that does not stop now gets `SIGKILL` later: at 50 seconds for a
  window of 45, instead of 30.
- Anyone whose process manager has its own stop deadline, such as systemd's
  `TimeoutStopSec` or Kubernetes' `terminationGracePeriodSeconds`. Set it above
  the Supervisor's wait, or the orchestrator kills the server first. See
  [`server.drain_timeout`](../server/hardening.md#serverdrain_timeout).
- Anyone who alerts on the removed warning. Nothing logs it any more.

## `part_of` must name the right kind of element

Protean now checks the kind of element each `part_of` names. A class target
of the wrong kind raises `IncorrectUsageError` when the element registers. A
string target resolves only against the allowed kinds, so a name of the wrong
kind fails `domain.init()` with the unresolved-reference `ConfigurationError`.
In 0.18 a database model takes only a class target. From 0.19 it also
accepts a string target, resolved the same way.

| Element | Valid `part_of` target |
|---|---|
| value object, application service, repository, event-sourced repository, command handler, event handler | an aggregate |
| entity | an aggregate or an entity (a nested entity) |
| event, command | an aggregate or a process manager |
| database model | an aggregate, an entity or a projection |
| query, query handler | a projection |
| domain service | a list of two or more aggregates (unchanged) |

For every element except a repository, the message names the element, the
target and the kinds it accepts. A repository keeps its existing message,
"Repository `X` can only be associated with an Aggregate". For example:

```text
Event `OrderPlaced` can only be associated with an Aggregate or a Process Manager; `Line` is an Entity
```

An entity whose `part_of` is an abstract aggregate gets the same
`IncorrectUsageError`, ending in "is abstract". The abstract-aggregate error
applies to a class and to a string name. The string form fails at
`domain.init()`. An entity whose `part_of` is a base class such as
`BaseAggregate` gets the same error. These cases used to fail with a bare
`AssertionError`. Other elements may still belong to an abstract aggregate.

Three string forms that failed before now work. An entity's string `part_of`
can name a parent entity, as the class form already allowed. An event's or
command's string `part_of` can name a process manager. An event-sourced
repository's string `part_of` resolves to its aggregate, where it used to
raise `AttributeError`.

When a name belongs to both an aggregate and a process manager, an event's or
command's string `part_of` resolves to the aggregate, as before. An entity
chain that loops back on itself (an entity naming itself, or two entities
naming each other) fails `domain.init()` with a `ConfigurationError` that names
the loop. Before, the string form failed as unresolved. The class form made
`domain.init()` hang.

### Who is affected

Domains that registered an element with an owner of the wrong kind. These
elements registered before. Most of them did not do what the configuration
said:

- An application service tied to an entity, a value object or a projection.
- A database model tied to a value object.
- An event or command tied to an entity. `raise_` on both the entity and its
  aggregate rejected such an event, so it could never be raised.
- A value object tied to anything other than an aggregate. The value object
  belonged to no aggregate's cluster.

Some setups that ran before are now rejected too:

- An event handler tied to a process manager. It subscribed to the process
  manager's stream category.
- A command handler tied to a process manager. It handled commands tied to
  that process manager.
- An application service or a database model tied to a process manager.

Most other wrong targets used to fail later with an `AttributeError`, a
`TypeError` or a bare `AssertionError` that did not mention `part_of`. They
now raise the `IncorrectUsageError` above. A query or query handler tied to a
class that is not a projection already failed cleanly at `domain.init()`. It
now fails earlier, at registration, with the message above.

An event belongs to the aggregate, which owns the stream, or to the process
manager that raises it. To say which entity an event concerns, tie the event
to the aggregate and carry the entity's identity in the payload:

```python
# fragment
# Before: registered, but the event could never be raised
@domain.event(part_of=Line)
class LineDiscounted:
    percent: Float()

# After: the aggregate owns the event; the payload names the entity
@domain.event(part_of=Order)
class LineDiscounted:
    line_id: Identifier(required=True)
    percent: Float()
```

For the other wrong targets, point `part_of` at the aggregate the element works
on. For a database model, point it at the aggregate, entity or projection.

### Why it was not put behind a flag

Most of these configurations were accepted without doing what they said, or
failed later with an error that did not name the cause. The error at
registration names the element and the target. You know which line to fix.

## The `audit-domain` skill reports every finding

The `audit-domain` teaching skill used to tell the agent to drop some signals
as harmless: an aggregate with many cohesive fields, or a short handler that
orchestrates one aggregate. It now tells the agent to report every signal at
its severity. A case it used to drop appears as a LOW finding, with the
context in its description.

### Who is affected

Anyone who compares an audit report from 0.17 with one from 0.18. The newer
report can list more LOW findings for the same code. Those come from the
reporting change, not from a new problem in the domain. The CRITICAL, HIGH and
MEDIUM findings are unchanged.

## The teaching skills store money as `Decimal`

The teaching skills and the pack's rules used to declare most money fields as
`Float`. They now declare a money field as `Decimal(precision=19, scale=4)`,
because a float cannot hold most cents exactly. The examples also pass money as a decimal, so
a method takes `amount: Decimal` and a test compares with `Decimal("45.00")`.

The `refactor-extract-value-object` skill also changes the field's type when it
moves a `Float` amount into a `Money` value object. The `Money` it generates
multiplies by an `int` or a `Decimal`. Write a factor such as a tax rate as
`Decimal("0.08")`.

### Who is affected

Anyone who has an agent add money fields with the skills. Code the skills
wrote before 0.18 is unchanged. New code declares money as `Decimal`, so:

- On a relational database, a field that changes from `Float` to `Decimal`
  needs a migration. The migration changes the column to a numeric type.
- Python does not combine a `Decimal` with a `float`, so `amount * 0.08` and
  `balance += 1.5` raise `TypeError`. Use `Decimal("0.08")` and
  `Decimal("1.5")`.
- A `Decimal` field rejects NaN and infinity, and a value with more than four
  decimal places. A rule that used to catch NaN in an invariant now sees the
  field's `ValidationError` first.
- A `Decimal` does not equal most float literals, so a test that checks
  `total == 59.98` fails. Compare with `Decimal("59.98")`.

## What changed in 0.18.1?

### `eventstore verify` exits 2 when it cannot connect

`protean eventstore verify` used to exit `1` with a logged traceback when it
could not connect to the event store. Under `--json`, stdout stayed empty.

It now exits `2`, the code for a usage or environment error:

- Under `--json`, stdout holds one [result envelope](../cli/conventions.md)
  with `status` set to `error` and the connection error under `data.error`.
- Without `--json`, the connection error is printed as one line on stderr,
  with no traceback.

A script that checked for exit `1` no longer gets it when the command cannot
connect. Other errors during the scan still exit `1` with a traceback. If a CI
job treated any non-zero exit as a failure, nothing changes for it.

### Value objects compare their field values

A value object used to compare and hash its `to_dict()` output, where a
`Decimal` becomes its string. Two value objects holding `Decimal("9.99")` and
`Decimal("9.9900")` were unequal, hashed differently, and took two entries in a
set.

`==` and `hash()` now use the field values as the instance holds them. Those
two value objects are now equal and hash the same, and so is a value object
that nests either of them. The same holds for any field whose values are equal
in Python but render differently, such as aware datetimes at the same instant
with different UTC offsets. A value object of another class, including a
subclass, is still never equal.

`to_dict()` is unchanged and keeps each amount's scale, so the two value
objects above still render as `"9.99"` and `"9.9900"`.

A field's default now goes through the same validation as an assigned value.
`Integer(default="5")` now stores `5` where it stored `"5"`. When you build the
value object, a default that breaks its own field's rules raises
`ValidationError`.

No action is needed unless your code relied on the old inequality. If your code
quantized amounts only to make value objects compare equal, you can drop the
quantize step. Keep it where the stored or serialized form matters.

### `eventstore verify` reports a message whose body is not a JSON object

Message DB allows a NULL `data` column. `protean eventstore verify` used to
raise `TypeError` on such a row against Message DB. The memory store passed the
same row without a report.

Both stores now report the row as a `malformed_message` violation with its
stream and position, and `verify` exits `1`. Message DB also reports a row
whose `data` holds a JSON array, string or number. It used to pass such a row.
A snapshot row keeps its own check and is still reported as
`malformed_snapshot`. `eventstore verify` does not report a message whose body
is an empty object.

The `message-db` extra now requires `message-db-py` 0.3.5 or later. If your
lock file pins an earlier version, upgrade the package.

A CI job that runs `verify` against a store holding a malformed message row now
fails. Find the rows from the stream and position in the report. Then repair or
remove each one.

### A nested handler's conflict reaches the enclosing handler or the caller

`@handle` retries a handler on `ExpectedVersionError`, and on a transient error
when transient retry is on. Before 0.18.1 it did so even when the handler ran
inside a Unit of Work that was already active. A Unit of Work is already active
in two cases. Another handler or a `@use_case` processes a command with
`domain.process(..., asynchronous=False)`, or your code opens a `UnitOfWork`
around the call. The handler's Unit of Work joins the outer one, so the failed
attempt had already marked the whole transaction for rollback. The retry then
succeeded, but the outer commit rolled the transaction back. The caller got a
normal return with no error.

When a handler runs inside an active Unit of Work, it now runs once and lets
the exception propagate:

- Sometimes the outermost caller is a `@handle` handler whose own policy covers
  the exception: version retry is on, or a transient policy lists it. That
  handler then runs the whole chain again in a fresh Unit of Work. The outer
  handler body runs again too, so it must be safe to re-run.
- When a `@use_case`, a process manager or your own `UnitOfWork` encloses the
  call, the caller receives `ExpectedVersionError`, or the transient
  exception, and the transaction is rolled back.
- The nested handler's own `retries` and `retry_exceptions` are not used. Only
  the outermost handler's policy applies.
- When a command with an `idempotency_key` is processed synchronously inside an
  outer Unit of Work, Protean records the key when the outer transaction
  commits. If the transaction rolls back, the key is not recorded, so the outer
  retry runs the command again.

```python
# fragment
@use_case
def record_result(self, notification_id: str) -> None:
    current_domain.process(
        RecordDispatchResult(notification_id=notification_id),
        asynchronous=False,
    )
    # Before 0.18.1, a version conflict in the RecordDispatchResult handler
    # was retried inside this use case's transaction and then lost.
    # It now reaches the caller of record_result().
```

If the caller of a `@use_case` like `record_result()` wants a retry, it calls
the use case again. Handlers that run with no Unit of Work active keep version
retry and transient retry. Event handlers run synchronously after a command
commits keep both retries too.

### Event-store subscriptions report their exhausted positions as DLQ depth

`dlq_depth` used to be zero for every event-store subscription, even when its
`failed-*` stream held exhausted positions. `protean subscriptions status`,
`/readyz`, the observatory and the `protean_subscription_dlq_depth` gauge all
reported it that way.

`dlq_depth` now counts the positions whose latest record in the subscription's
`failed-*` stream is `Exhausted`. These are the positions that [`protean
eventstore dlq list`](../cli/data/eventstore-dlq.md) shows. A position stops
being counted once a replay or purge writes a later record for it. A replay
that finds an expired command writes no record, so that position stays counted.
An alert on `dlq_depth > 0` can start to fire for an event-store subscription.
Clear the positions with `protean eventstore dlq replay` or `purge`.

On the observatory overview, the health banner adds these positions to its
count of DLQ messages. The subscription summary counts an event-store
subscription with exhausted positions under DLQ. The DLQ tab that the banner
links to lists only broker `{stream}:dlq` streams, and so do the `protean dlq`
commands. Use `protean eventstore dlq list` to see and clear the positions
behind an event-store subscription's count.

`protean eventstore dlq inspect` used to show a position that was replayed or
purged after it was exhausted. It now reports such a position as not found,
the same as `replay` and `purge`.

### Outbox reconciliation repairs only event-sourced aggregates' events

The Unit of Work appends events to the event store before it commits the
aggregate's row and its outbox rows. When that commit rolled back, a
state-based aggregate's event stayed in the event store. The aggregate's change
and its outbox rows were not saved. `protean outbox reconcile`, and the
reconcile at server start, rebuilt the outbox rows for such an event. Consumers
and external brokers then received an event for a change that Protean never
saved.

Reconcile now rebuilds outbox rows only for events of event-sourced
aggregates. It skips every state-based aggregate's event, whether or not the
aggregate's row exists. A provider with no event-sourced aggregate is not
read at all.

On a provider that writes without a transaction, such as Elasticsearch, Protean
can save the aggregate row and lose its outbox row. Reconcile used to rebuild
that outbox row. It no longer does, so the event is not published. No code
change is needed for this. If a script or runbook relied on reconcile to
recover lost outbox rows of a state-based aggregate after a crash, reconcile no
longer recovers them.

See [Recover from a crash: reconciliation](../../guides/server/outbox.md#recover-from-a-crash-reconciliation).

### An outer commit after a nested failure raises

A Unit of Work started inside another one joins it. When the nested one fails,
the whole transaction is marked for rollback. Before 0.18.1, if your code caught
the error and let the outer block end normally, the outer commit rolled the
transaction back, logged a warning and returned. The caller saw a normal return,
and nothing was saved.

The outer commit now rolls back and raises:

- When the nested Unit of Work failed with an exception, the commit raises that
  same exception object.
- When a nested Unit of Work called `rollback()` with no exception, the commit
  raises `TransactionError`. Its message says the transaction was marked
  rollback-only.

#### Who is affected

- A handler or a `@use_case` that calls `domain.process(..., asynchronous=False)`,
  catches the exception the inner handler raised, and carries on.
- Code that opens a `UnitOfWork` inside another one, catches the error the inner
  block raised, and carries on.
- Code that calls `rollback()` on a nested `UnitOfWork` and expects the outer
  block to return normally.

```python
# fragment
@handle(PlaceOrder)
def place(self, command: PlaceOrder) -> None:
    current_domain.repository_for(Order).add(Order(id=command.order_id))
    try:
        current_domain.process(
            ReserveStock(order_id=command.order_id), asynchronous=False
        )
    except OutOfStock:
        pass
    # Before 0.18.1: the handler returned, and the order was silently not saved.
    # Now: OutOfStock reaches the caller, and the order is not saved.
```

A `@use_case` that catches a nested `ExpectedVersionError` now gets it again
when its Unit of Work commits. A `@handle` handler retries the whole chain in a
fresh Unit of Work when its own retry policy covers the exception, as described
in [A nested handler's conflict reaches the enclosing handler or the
caller](#a-nested-handlers-conflict-reaches-the-enclosing-handler-or-the-caller).
An exception outside that policy propagates after one run.

#### How to fix it

Let the exception propagate out of the outer block, so the caller handles it.
Sometimes the outer work must be saved even when the inner step fails. Then run
the inner step outside the outer Unit of Work, for example in an event handler
that reacts to an event the outer aggregate raises.

### A stopping worker finishes its batch, and a starting worker claims unacknowledged messages

On `SIGTERM`, the engine used to refuse every message left in a batch it had
already read. Those messages stayed pending in the Redis consumer group under
the stopped worker's consumer name. No later worker reads that name, so the
messages were lost.

The engine now keeps handling a batch it has read until `server.drain_timeout`
ends, and cancels it then. A partitioned stream subscription (`sequential_by`)
is the exception: it cancels its partition workers as soon as shutdown starts. A message the worker did not handle stays pending.
On startup, each stream subscription and broker subscription on Redis claims
the group's entries that have stayed unacknowledged for at least
`server.reclaim_idle_seconds` (120 by default), then handles them. A claimed
message counts its earlier deliveries toward `max_retries`.

What to check when you upgrade:

- Handlers can now run after `SIGTERM`, inside the drain window. A handler
  must not assume that no message arrives once shutdown has begun.
- Keep `server.reclaim_idle_seconds` above `circuit_breaker_reset_seconds` and
  above your longest batch. If a running worker leaves its entries unread
  longer than the threshold, a worker that starts can claim them. Both workers
  can then handle the same entries.
- A worker that starts claims only the entries last delivered at least
  `server.reclaim_idle_seconds` earlier. A later start claims the rest. A
  partitioned subscription (`sequential_by`) does not use this threshold: the
  partition's next owner claims its entries through the lease handover.
- `POST /drainz` now returns `"drained": true` once the worker has no batch in
  flight. To stop a worker without interrupting a batch, repeat the `POST`
  until `drained` is `true`. Then send `SIGTERM`. See [Draining: `POST
  /drainz`](../server/hardening.md#draining-post-drainz).
- To keep the old behaviour of never claiming, set
  `server.reclaim_idle_seconds` higher than any entry can wait, such as
  `31536000` (one year). A subscription that claims messages on start logs how
  many it claimed.

### A process manager's dates, datetimes and decimals keep their type after a reload

A process manager stores its fields as JSON in each transition event. Protean
rebuilds the process manager from those events when the next event arrives.
Protean 0.18.1 changes how it saves and reloads these fields.

- **Saving a `Decimal` field now works.** A `Decimal` field used to fail the
  save with `TypeError: Object of type Decimal is not JSON serializable`, which
  rolled back the unit of work. It is now stored as a string, such as
  `"100.50"`.
- **Reloading returns the field's type.** A `Date`, `DateTime` or `Decimal`
  field used to come back as the stored string, such as
  `"2025-06-15T10:30:00"`. It now comes back as a `date`, `datetime` or
  `Decimal`. When a stored value no longer fits the field's type, for example a
  value written before the type changed, Protean keeps the stored value. The
  process manager still loads.

#### Who is affected

A handler that read a reloaded date or datetime field as a string, for example
by parsing it with `datetime.fromisoformat()`, now receives a `datetime` and
the parse raises `TypeError`. Use the value directly. A process manager with a
`Decimal` field works for the first time.

### Outbox reconciliation repairs every lost row in its window

`protean outbox reconcile`, and the reconcile at server start, rebuild an
outbox row when two things hold. The event of an event-sourced aggregate is in
the event store, and its internal outbox row is missing. They used to check
only the newest such event in the window. When that event had its row, they
repaired nothing. So an event whose row was lost in a crash stayed unpublished
once another process in the same domain committed a later event.

They now rebuild the rows of every such event in the window that is newer than
the shorter of `published_retention_hours` and `abandoned_retention_hours`. A
`published` event also gets back one row per broker in
`[outbox].external_brokers`.

No action is needed for most domains. After the upgrade:

- The first restart, or the first `protean outbox reconcile`, can publish
  events that lost their rows before the upgrade. The old check missed those
  events. Consumers can receive these events after the events committed after
  them.
- For a `sequential_by` key, a rebuilt event is delivered after the events of
  later commits for the same key when their rows are in the same priority
  lane. A rebuilt row has priority 0.
- Say you raised the shorter retention after cleanup ran with a lower value.
  The next run rebuilds the rows that cleanup deleted in between, and Protean
  publishes those events again. Raise the shorter retention only when your
  consumers can take a repeated event.
- When an event-sourced aggregate is on the provider, every run reads the whole
  `--limit` window, 1000 messages by default. It looks up the outbox rows of
  the window's events in batches. Before, a run with nothing to repair read one
  message.

See [Recover from a crash: reconciliation](../../guides/server/outbox.md#recover-from-a-crash-reconciliation).

### Datetimes are compared and stored as UTC

A query that filtered a `DateTime` field with a value in another UTC offset
could return the wrong rows. A row saved at `12:00+00:00` and filtered with
`lte=13:00+02:00` (11:00 UTC) was returned, because the provider compared the
wall-clock digits. The memory provider compared the string form of the two
values. SQLite, MySQL, MariaDB and SQL Server store a datetime with no offset,
so they wrote the caller's wall-clock time and compared it the same way.
PostgreSQL gave the right answer.

Every provider now compares the instant for the operators listed below:

- **Memory.** `exact`, `in`, `lt`, `lte`, `gt`, `gte`, `any` and `overlap`
  compare two datetimes as UTC instants. A naive datetime on either side is
  read as UTC. `contains`, `startswith` and `endswith` still compare the string
  form. A datetime filtered with a string also compares the string form.
- **SQLite, MySQL, MariaDB and SQL Server.** A `DateTime` column converts each
  value to UTC before it writes or compares it. It reads a naive value as UTC.
  A load returns a UTC-aware `datetime`, where it used to return a naive one.
  The column definition is unchanged, so existing tables need no schema change.

PostgreSQL and Elasticsearch are unchanged. A custom SQLAlchemy model keeps the
column types it declares.

#### Who is affected

Code that compares a loaded datetime with a naive one, such as
`datetime.now()`, changes on SQLite, MySQL, MariaDB and SQL Server. An ordering
comparison (`<`, `<=`, `>`, `>=`) now raises `TypeError`. An equality check
raises nothing: `==` always returns `False` and `!=` always returns `True`.
Compare with an aware value, such as `datetime.now(UTC)`.

Rows written before the upgrade keep the wall-clock time they were saved with.
A row saved with the `+00:00` offset, or as a naive UTC value, already holds
UTC and needs nothing. Two kinds of row are now read as UTC and are off by
their offset:

- a row saved with any other offset, such as `+02:00`;
- a row saved as a naive local time, such as a field with
  `default=datetime.now`, which is off by the server's offset.

#### How to fix it

If your application wrote one known offset, such as `+02:00`, convert the
column once. Stop every writer before the upgrade, and keep it stopped until
the conversion finishes. A row that the upgraded version writes already holds
UTC, and the statement would shift it too. Each statement below converts
`placed_at` on an `orders` table from `+02:00` to UTC:

```sql
-- MySQL and MariaDB
UPDATE orders SET placed_at = CONVERT_TZ(placed_at, '+02:00', '+00:00');

-- SQL Server
UPDATE orders SET placed_at = DATEADD(hour, -2, placed_at);

-- SQLite; datetime() gets only the whole seconds, because some SQLite
-- versions round the fraction into the seconds, and substr keeps the fraction
UPDATE orders
SET placed_at = datetime(substr(placed_at, 1, 19), '-2 hours') || substr(placed_at, 20)
WHERE placed_at IS NOT NULL;
```

If the offset changed over time, for example with daylight saving time, run
one statement per period and limit each with a `WHERE` clause on the column.
