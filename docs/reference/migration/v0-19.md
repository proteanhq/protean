# Migrating to 0.19

!!! abstract "From 0.18 to 0.19"

This page lists the changes in 0.19 that may need action when you upgrade.

**On this page:**

- [Outbox claim order](#outbox-claim-order): Rows of equal priority are claimed in commit order, and the `ix_outbox_active` index gains two columns

---

## Outbox claim order

The outbox processor used to claim rows by priority alone. Rows of the same
priority came back in whatever order the database returned them, so on
PostgreSQL one aggregate's events could be published out of commit order.

From 0.19, `claim_batch` and `find_unprocessed` order rows by:

1. `priority`, highest first.
2. `created_at`, oldest first.
3. `sequence_number`, lowest first.

The Unit of Work now writes `sequence_number` on every outbox row. It holds
the event's position within its commit: 0 for the first event, 1 for the
next, and so on. The Unit of Work numbers events one aggregate at a time, each
aggregate's events in the order it raised them. The number decides the order
when two rows of one commit share a `created_at`. Every outbox row written for one event (the internal row and
one row per external broker) carries the same number. The startup sweep that
rebuilds lost outbox rows from the event store numbers the rows it rebuilds in
event store order.

A higher-priority message can still be claimed ahead of an earlier
lower-priority one. A retried row, or a second worker, can still publish an
aggregate's events out of order.

### Rows written before the upgrade

Rows already in the outbox have a NULL `sequence_number`. They are ordered by
`created_at` alone. Where a NULL sorts among numbered rows with the same
`created_at` depends on the database. This only affects rows written in the
same commit before the upgrade.

### Rebuild `ix_outbox_active`

The partial polling index `ix_outbox_active` now covers the claim order:
`status`, `priority DESC`, `created_at`, `sequence_number`.

- **New deployments**: Nothing to do. Tables created on 0.19 get the new
  index.
- **Existing deployments**: Protean does not change an existing table's
  indexes. Claims work without the rebuild, but the old index does not cover
  the new sort. Drop and recreate the index once.

The statements below use the default table name `outbox`.

=== "PostgreSQL"

    ```sql
    DROP INDEX IF EXISTS ix_outbox_active;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number)
        WHERE status IN ('pending', 'failed');
    ```

    On a busy table, use `DROP INDEX CONCURRENTLY` and
    `CREATE INDEX CONCURRENTLY` to avoid blocking writes. Neither runs inside
    a transaction block.

=== "SQLite"

    ```sql
    DROP INDEX IF EXISTS ix_outbox_active;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number)
        WHERE status IN ('pending', 'failed');
    ```

=== "SQL Server (full index)"

    Protean builds a full index on SQL Server, without the `WHERE` filter.

    ```sql
    DROP INDEX IF EXISTS ix_outbox_active ON outbox;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number);
    ```

=== "MySQL / MariaDB (full index)"

    MySQL and MariaDB have no partial indexes, so Protean builds a full
    index there.

    ```sql
    DROP INDEX ix_outbox_active ON outbox;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number);
    ```
