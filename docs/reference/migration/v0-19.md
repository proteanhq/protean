# Migrating to 0.19

!!! abstract "From 0.18 to 0.19"

This page lists the changes in 0.19 that may need action when you upgrade.

**On this page:**

- [Outbox claim order](#outbox-claim-order): Rows of equal priority are claimed in the order they were written, and the `ix_outbox_active` index gains two columns
- [Outbox rows wait for their partition key's earlier rows](#outbox-rows-wait-for-their-partition-keys-earlier-rows): The outbox gains a `stream_category` column and an `ix_outbox_hold_back` index, and a partition key can now halt

## Outbox claim order

The outbox processor used to claim rows by priority alone. Rows of the same
priority came back in whatever order the database returned them, so on
PostgreSQL one aggregate's events could be published out of commit order.

`claim_batch` and `find_unprocessed` now order rows by:

1. `priority`, highest first.
2. `created_at`, oldest first.
3. `sequence_number`, lowest first.
4. `id`, lowest first.

The last key, `id`, says nothing about commit order. It only makes the order
the same on every run when the other three keys tie.

The Unit of Work now writes `sequence_number` on every outbox row. It holds
the event's position within its commit: 0 for the first event, 1 for the
next, and so on. Each database provider has its own outbox table, and the
count starts at 0 for each provider in the commit. Within a provider, the Unit
of Work numbers events one aggregate at a time, each aggregate's events in the
order it raised them. When two rows share a
`created_at`, the row with the lower number is claimed first. Every outbox row
written for one event (the internal row and one row per external broker)
carries the same number. At startup, a sweep rebuilds lost outbox rows from the
event store. The sweep numbers the rebuilt rows in event store order.

### When can the claim order differ from commit order?

`created_at` is the time the Unit of Work built the row, just before the
commit. One aggregate's events go out in commit order, because a second commit
on that aggregate has to load it after the first commit finished. Rows of
different aggregates go out in the order their rows were built, which can
differ from the order their commits finished.

The claim order can also differ from commit order in these cases:

- A higher-priority message is claimed ahead of an earlier lower-priority one.
- A retried row, or a second worker, publishes events out of order. This
  does not apply to a category partitioned with `sequential_by`: a later row
  of a key waits until the key's earlier rows have published (see
  [below](#outbox-rows-wait-for-their-partition-keys-earlier-rows)).
- `created_at` comes from the clock of the host that wrote the row. If two
  hosts' clocks disagree, or a clock steps back, a later commit can get an
  earlier `created_at` and be claimed first.
- On a SQL Server outbox table created before 0.19 and not converted,
  `created_at` is a `DATETIME`, which rounds to about 3 milliseconds. When two
  commits write rows in the same rounding step, their rows share a
  `created_at`. Each commit numbers its events from 0, so the rows of the two
  commits can interleave. See
  [SQL Server stores `DateTime` as `DATETIME2`](#sql-server-stores-datetime-as-datetime2).

### Rows written before the upgrade

Rows already in the outbox have a NULL `sequence_number`. They are ordered by
`created_at` first, like every other row. Among rows with the same
`created_at`, a NULL `sequence_number` sorts after every number, on the
in-memory adapter and every SQL database.

To place NULLs the same way everywhere, an ascending sort on a nullable column
now puts NULLs last on SQLite, MySQL, MariaDB and SQL Server, and a descending
sort puts them first. PostgreSQL and the in-memory adapter already did this.
The rule applies to every repository query that orders by a nullable field, not
only to the outbox. If a query relied on NULLs coming first in an ascending
sort on SQLite, MySQL, MariaDB or SQL Server, the query now gets them last.

### Rebuild `ix_outbox_active`

The partial polling index `ix_outbox_active` now covers the claim order:
`status`, `priority DESC`, `created_at`, `sequence_number`.

- **New deployments**: Nothing to do. Tables Protean creates on 0.19 get the
  new index. A schema you manage yourself, with Alembic or by hand, needs the
  rebuild below.
- **Existing deployments**: Protean does not change an existing table's
  indexes. Claims work without the rebuild, but the old index does not cover
  the new sort. Drop and recreate the index once.

The statements below use the default table name `outbox`.

=== "PostgreSQL"

    ```sql
    DROP INDEX IF EXISTS ix_outbox_active;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number)
        WHERE status IN ('pending', 'failed');
    ```

    On a busy table, use `DROP INDEX CONCURRENTLY` and
    `CREATE INDEX CONCURRENTLY` to avoid blocking writes. Neither runs inside
    a transaction block.

=== "SQLite"

    ```sql
    DROP INDEX IF EXISTS ix_outbox_active;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number)
        WHERE status IN ('pending', 'failed');
    ```

=== "SQL Server (full index)"

    Protean builds a full index on SQL Server, without the `WHERE` filter.

    ```sql
    DROP INDEX IF EXISTS ix_outbox_active ON outbox;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number);
    ```

=== "MySQL / MariaDB (full index)"

    MySQL and MariaDB have no partial indexes, so Protean builds a full
    index there.

    ```sql
    DROP INDEX ix_outbox_active ON outbox;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number);
    ```

## Outbox rows wait for their partition key's earlier rows

A handler category that declares
[`sequential_by`](../server/sequential-by.md) gives each outbox row a
partition key. The outbox processor used to claim and publish each row on its
own. If a key's first row failed, its second row could still publish, and the
consumer saw the two events out of commit order.

The claim now groups partitioned rows by target broker, stream category,
partition key and priority lane. A row is claimed only when every earlier row
of its group has been published or discarded, or is claimed in the same call. An earlier
row holds the later ones while it is `pending`, `processing`, `failed` or
`abandoned`. Rows without a partition key are claimed as before.

### Add the `stream_category` column

The outbox table has a new `stream_category` column. The Unit of Work copies
it from the event's `metadata.domain.stream_category` when it writes a row. A
new index, `ix_outbox_hold_back`, backs the lookup of a row's earlier group
rows.

- **New deployments**: Nothing to do. Tables Protean creates on 0.19 have the
  column and the index.
- **Existing deployments**: Protean does not change an existing table. Add the
  column before you start 0.19, because every outbox query reads it. Then
  create the index.

The statements below use the default table name `outbox`.

=== "PostgreSQL"

    ```sql
    ALTER TABLE outbox ADD COLUMN stream_category VARCHAR(255);
    CREATE INDEX ix_outbox_hold_back
        ON outbox (target_broker, stream_category, partition_key, status);
    ```

    On a busy table, use `CREATE INDEX CONCURRENTLY` to avoid blocking
    writes. It does not run inside a transaction block.

=== "SQLite"

    ```sql
    ALTER TABLE outbox ADD COLUMN stream_category VARCHAR(255);
    CREATE INDEX ix_outbox_hold_back
        ON outbox (target_broker, stream_category, partition_key, status);
    ```

=== "SQL Server"

    ```sql
    ALTER TABLE outbox ADD stream_category VARCHAR(255);
    CREATE INDEX ix_outbox_hold_back
        ON outbox (target_broker, stream_category, partition_key, status);
    ```

=== "MySQL / MariaDB"

    ```sql
    ALTER TABLE outbox ADD COLUMN stream_category VARCHAR(255);
    CREATE INDEX ix_outbox_hold_back
        ON outbox (target_broker, stream_category, partition_key, status);
    ```

### Rows already in the outbox

Rows already in the outbox have a NULL `stream_category`. The claim treats
them as rows without a partition key: they are not held, and they do not hold
later rows.

are not yet published. Protean stores each row's metadata pickled, so plain
SQL cannot read the stream category out of it. Run this function once, with
0.19 installed, after the `ALTER TABLE` and before you start the server:

```python

```

It returns the number of rows it filled. Pass the provider name when the
outbox lives on a provider other than `default`. A row whose metadata has no
stream category is left NULL.

The fill also sets the column on `abandoned` rows, and a filled abandoned row
halts its key as soon as 0.19 starts (see the next section). That includes
every row the key gets after the upgrade. Before you run the fill, list the
abandoned rows that have a partition key, and retry or skip the ones you do not
want to halt their key:

```sql
SELECT id, partition_key, created_at, last_error
FROM outbox
WHERE status = 'abandoned' AND partition_key IS NOT NULL;
```

### A partition key can halt

A key whose earliest row is `abandoned` stops: none of its later rows publish
until you retry or skip that row. A key whose earliest row is `failed` waits
until the row's retry is due. When the row runs out of retries it becomes
`abandoned` and the key stops. Other keys, rows without a key, and the other
priority lane keep publishing.

The cleanup job no longer deletes abandoned rows that have a partition key,
since deleting one would let the key's later rows publish out of order.

To restart a halted key, either retry the abandoned row or skip it.
`protean outbox halted` lists the halted keys with the id of each one's abandoned
row. Retrying sends the row again with a fresh retry budget:

```bash
protean outbox retry <row id> --domain=my_domain
```

Skipping the row marks it `discarded` without sending it. The skipped row's
event is dropped for the row's target broker. The processor can then claim the
key's next row. The row stays in the table, with your reason in `last_error`,
until cleanup deletes it after `abandoned_retention_hours`:

```bash
protean outbox discard <row id> --reason "payload rejected by the broker" --domain=my_domain
```

Both commands refuse a row that is not `failed` or `abandoned`. See the
[`protean outbox` reference](../cli/data/outbox.md).

Two outbox methods changed with these commands:

- `Outbox.reset_for_retry()` now also sets `retry_count` back to 0, so a
  retried row gets the full number of attempts again. Code that called it and
  expected the count to carry over now sees 0. A row whose `max_retries` is 0
  gets `max_retries` 1, since the processor never claims a row with no
  attempts left.
- `OutboxRepository.cleanup_old_messages()` now also deletes discarded rows
  older than `abandoned_retention_hours`, and its result has a `discarded`
  count. `total` includes that count.

Do not delete an abandoned row to restart its key. Outbox reconciliation runs
when the server starts and can rebuild a deleted row of a recent event-sourced
aggregate's event as `pending`. The rebuilt row would then publish after the
key's later rows.

## SQL Server stores `DateTime` as `DATETIME2`

On SQL Server, a `DateTime` field used to map to a `DATETIME` column, which
rounds to increments of about 3 milliseconds. Protean writes
microsecond-precision timestamps, so two values written less than 3 ms apart
could read back equal, and a value read back could differ from the one written.

A `DateTime` field now maps to `DATETIME2`, which keeps 100-nanosecond steps.
`Date` fields still map to `DATE`. Other databases are unchanged.

- **New deployments**: Nothing to do. Tables Protean creates on 0.19 get
  `DATETIME2` columns.
- **Existing deployments**: Protean does not change an existing table, so its
  columns stay `DATETIME` and keep rounding. Convert them.

The column that matters most is the outbox's `created_at`. The outbox processor
claims rows in `created_at` order. So when SQL Server rounds `created_at`, the
processor can publish the events of two commits interleaved
(see [When can the claim order differ from commit order?](#when-can-the-claim-order-differ-from-commit-order)).

### Convert a column

```sql
ALTER TABLE <table> ALTER COLUMN <column> DATETIME2 NULL;
```

Write `NULL` for an optional field and `NOT NULL` for a required one.
`ALTER COLUMN` sets the column's nullability to what the statement says, and
makes it nullable when the statement says nothing.

SQL Server refuses to alter a column that an index or a constraint uses. Drop
an index with `DROP INDEX <index> ON <table>` and create it again after the
`ALTER`. A `DateTime(unique=True)` field has a `UNIQUE` constraint with a name
SQL Server generated. Find the name in `sys.key_constraints`, drop it with
`ALTER TABLE <table> DROP CONSTRAINT <name>`, and add it back with
`ALTER TABLE <table> ADD UNIQUE (<column>)` after the `ALTER`.

### Convert the outbox

All five outbox timestamps are nullable, and `ix_outbox_active` uses
`created_at`. The statements below use the default table name `outbox`:

```sql
DROP INDEX IF EXISTS ix_outbox_active ON outbox;
ALTER TABLE outbox ALTER COLUMN created_at DATETIME2 NULL;
ALTER TABLE outbox ALTER COLUMN published_at DATETIME2 NULL;
ALTER TABLE outbox ALTER COLUMN last_processed_at DATETIME2 NULL;
ALTER TABLE outbox ALTER COLUMN next_retry_at DATETIME2 NULL;
ALTER TABLE outbox ALTER COLUMN locked_until DATETIME2 NULL;
CREATE INDEX ix_outbox_active
    ON outbox (status, priority DESC, created_at, sequence_number);
```

The statements above also do the
[`ix_outbox_active` rebuild](#rebuild-ix_outbox_active) for SQL Server.

Rows already in the table keep the point in time `DATETIME` stored, but they
can read back with different microseconds. `DATETIME` stores steps of 1/300
second, and `DATETIME2` shows them in full, so `.123` reads back as `.123333`.
Code that compares against a timestamp it read before the conversion no longer
finds a match.

The `processed_message` table records the messages each handler has handled.
Its `processed_at` column also stays `DATETIME`. Convert it the same way, with
`ALTER TABLE processed_message ALTER COLUMN processed_at DATETIME2 NULL`. Until
then, the cutoff for removing old records can be off by up to 3 ms.

## Generated `.proto` files import each other

`protean schema generate --format protobuf` used to copy every value object
and entity an element referenced into that element's file, as a sibling
message. The referenced element also had its own file. When both were in the
same package, `protoc` rejected the tree with "already defined" when it
compiled the files together.

Each value object and entity is now defined only in its own file. A file that
uses one adds an import of that file, by its path under `schemas/`:

```protobuf
syntax = "proto3";
package shop.ordering;
import "Order/entities/Package.v1.proto";

message Order {
  string id = 1;
  repeated .shop.ordering.Package packages = 2;
}
```

What this changes for you:

- **Compiling the files.** Pass `-I <output>/schemas` to `protoc`, so it can
  find the imported files. This applies even when you compile one file at a
  time.
- **Type names.** A referenced type is named by its full name with a leading
  dot (`.shop.ordering.Package`). A value object from another module keeps its
  own full name, such as `shared.kernel.Money`. It is no longer copied into the
  referencing element's package, so generated code that used the local copy
  (`sales.ordering.Money`) must use `shared.kernel.Money`.
- **Nested messages.** A value object that belongs to no aggregate cluster,
  such as one only projections use, has no file. Entities that refer to each
  other through `HasOne` or `HasMany` would import each other in a cycle. In
  both cases the type is defined as a nested message inside the file that uses
  it, such as `.shop.ordering.CustomerCard.ShippingAddress`.
- **Timestamps.** Dates are written as `.google.protobuf.Timestamp`, with a
  leading dot, so a package with a `google` part cannot shadow it.
- **Name clashes.** `protean schema generate` now fails with an error when two
  elements would be written to the same file, in any format. Before, the second
  file silently replaced the first. Rename one of the two classes.

Field names, field numbers and labels are unchanged, so the bytes on the wire
are the same. Tools that compare message names, such as a schema registry's
compatibility check, `Any` type URLs and generated class paths, see the new
names.

`generate_proto_schemas()` still returns one self-contained file per element
with sibling messages. So does `generate_proto_schema()` when you call it
without the new `import_path` argument.

## Avro schemas no longer mark `Identifier` fields as `uuid`

`protean schema generate --format avro` used to write every `Identifier`
field with the Avro `uuid` logical type. An `Identifier` can hold any string,
such as an email address or an order number. An Avro reader that checks the
`uuid` logical type rejected those values.

Before, an `email` identifier was written like this:

```json
{ "name": "email", "type": { "type": "string", "logicalType": "uuid" } }
```

Every `Identifier` field is now a plain `string`:

```json
{ "name": "email", "type": "string" }
```

Protobuf and JSON Schema already wrote `Identifier` fields as plain strings,
and the Avro auto identity never carried the `uuid` logical type. Only Avro
`Identifier` fields change.

What this changes for you:

- **Schema registries.** A registry that compares the generated `.avsc` files
  sees a changed type on each `Identifier` field. Re-register the schemas, or
  check the subject's compatibility mode before you do.
- **Avro readers.** Code that read the field as a UUID object through the
  logical type now gets a plain string. Parse it yourself where you need a
  UUID.

## Deprecation versions must be strings

`deprecated=` used to accept a version written as a number and turn it into a
string. A number cannot keep a trailing zero, so `0.20` became `"0.2"`. That
sorts before 0.18, so `diff_ir(..., current_version="0.18")` classed a field
due for removal in 0.20 as safe to remove. `protean ir diff` and the
`protean-check-compat` hook pass no current version, so they class every
deprecated removal as premature and were not affected. A declared
`since: 0.20` showed as "deprecated since v0.2" in diagnostics.

`deprecated=` on an element, a field or a `FieldSpec` now raises
`ConfigurationError` when `since` or `removal` is not a string. `removal: None`
still means there is no removal version.

```python
# fragment
# Accepted before and read as "0.2". Now raises ConfigurationError.
name = String(deprecated={"since": "0.18", "removal": 0.20})
```

Quote both versions:

```python
from protean.fields import String

name = String(deprecated={"since": "0.18", "removal": "0.20"})
```

`diff_ir()` and `classify_changes()` now check every `deprecated` block in
both IR files before comparing them, on elements and on fields, whether or not
anything changed. They raise `ConfigurationError` naming the element or field
when:

- `since` is not a string, or `removal` is neither a string nor `null`.
- `since` is missing.
- The block is not an object, such as `"deprecated": "0.15"`.

A `current_version` that is not a string raises too. Before, the diff read a
block only on a removed published event or a removed field. It read a numeric
version as text, and could crash with an `AttributeError` or `KeyError` on a
block that is not an object or has no `since`.

`protean ir diff` prints the error on stderr and exits `2`. The `protean-check-compat`
hook prints it and blocks the commit, under `strictness = "warn"` too. With
`strictness = "off"`, both skip the comparison.

A baseline that Protean generated never holds a number. The old code wrote
`0.20` into it as the string `"0.2"`, and the diff cannot tell that the value
was meant as 0.20.

To upgrade:

1. Quote every `since` and `removal` version in `deprecated=`.
2. Regenerate the IR baseline, so that a version that lost its zero, such as
   `"0.2"`, is written again as `"0.20"`.

## The IR's `$schema` URL moved

The IR used to name its schema `https://protean.dev/ir/v{X}/schema.json`, which
does not resolve. New IR files name
`https://docs.proteanhq.com/assets/ir/v{X}/schema.json`, where the docs site
serves every schema version. Each schema's `$id` moved to the same URL.

The URL change needs no action. `protean ir check` and `protean ir diff`
ignore `$schema`, so the old URL alone does not make a baseline stale or show up
as a change. The v0.4.0 schema does make a baseline stale (see
[The IR schema is now v0.4.0](#the-ir-schema-is-now-v040-and-schemas-type-a-dict-of-value-objects)).
The baseline gets the new URL the next time you regenerate it. If a tool of
yours matches the `$schema` value, accept both URLs.

## New in `ir diff`: value type changes on `Dict` and `List` fields

`ir diff` now compares the value type of a `Dict` or `List` field that keeps
its type. Moving a field from `Dict()` to
`Dict(value_type=ValueObject(TierPrice))` used to show up only in the text
diff: the compatibility report listed nothing for it and the command exited
`2`, the 0.18 code for non-breaking changes. Rows stored while the field was untyped can fail to load once it is
typed.

Adding, changing or removing a value type is now a breaking
`field_type_changed`, and a published event lists it as
`contract_field_type_changed`. Under `strictness = "strict"`, a diff that
exited `2` (the 0.18 non-breaking code) now exits `1`, so a CI job that runs `protean ir diff` or the
`protean-check-compat` hook fails on a value type change. Under
`strictness = "warn"`, it exits `0` and the hook passes. See
[Dict and List value types](../compatibility/index.md#dict-and-list-value-types).

## New in `ir diff`: moving an event's Protobuf field numbers is breaking

Protean numbers an event's Protobuf fields in sorted name order. Adding or
removing a field that does not sort last moves the numbers of the fields after
it. Renaming a field with `renamed_from` moves numbers when the new name sorts
to a different position than the old name. A
consumer that decodes by the old numbers then reads the wrong field. `ir diff`
used to report such a rename as a safe `field_renamed` and such an addition of
an optional field as safe.

`ir diff` now reports a breaking `field_number_changed` when an event keeps its
`__version__` and a field it keeps gets a different number. A CI gate on
`protean ir diff` or the `protean-check-compat` hook can now fail on an event
change it used to pass. To fix it, bump the event's `__version__` and register
an upcaster for the old version, which may return the payload unchanged. See
the `field_number_changed` row in
[Breaking change rules](../compatibility/index.md#breaking-change-rules).

## The IR schema is now v0.4.0, and schemas type a `Dict` of value objects

A `Dict(value_type=ValueObject(Address))` field now records the value object's
fully qualified name as `target` in the IR, next to the short name in
`content_type`:

```json
"address_book": {"kind": "dict", "type": "Dict", "content_type": "Address", "target": "my_app.Address"}
```

The IR schema declares the new key, so `ir_version` moved from `0.3.0` to
`0.4.0`. A `0.3.0` document still passes the `0.4.0` schema. The `v0.3.0`
schema stays published.

The `0.4.0` schema also accepts any string as a subscription's `profile`, so an
IR that names a custom profile from `[server.profiles]` validates.

### Who is affected

Anyone with a committed `.protean/ir.json`. `protean ir check` reports a version
mismatch and exits `3`, and the `protean-check-staleness` hook fails, until you
regenerate the baseline:

```shell
protean ir show --domain <module> --canonical > .protean/ir.json
```

The pre-commit hook regenerates it for you if you run it with `--fix`.

If your domain has no `Dict` field with a value object as its value type, the
regenerated baseline differs only in `$schema` and `ir_version`. Otherwise,
`protean ir diff` against the old baseline shows `target` as changed on each
such field. A value object that only a `Dict` field uses now belongs to its
aggregate's cluster, so `protean ir diff` also lists it as added. The change is
not breaking: `protean ir diff` exits `3`, the code for non-breaking changes,
and the `protean-check-compat` hook passes.

### What changes in the generated contracts

`protean schema generate` used to write a `Dict` of value objects as a map of
untyped values. The map's values now refer to the value object:

| Generator | Before | After |
|-----------|--------|-------|
| JSON Schema | `{"type": "object"}` | `{"type": "object", "additionalProperties": {"$ref": "#/$defs/Address"}}`, with `Address` in `$defs` |
| Avro | `{"type": "map", "values": "string"}` | `{"type": "map", "values": <the Address record>}` |
| Protobuf | `map<string, string>` | `map<string, Address>` |

The map's values are records, so the old Avro schema did not match the data.
Register the new schema with every registry and consumer that holds the old
one. `protean schema generate` writes the Protobuf value type as
`map<string, .<package>.Address>` and imports the value object's file. An
untyped `Dict()` field keeps its old output in every format.

Some value object names end in `Entry`, such as `LedgerEntry`. Any Protobuf
field that refers to such a value object now names it by its full name in the
`.proto` file. The short name could resolve to the hidden entry message that
`protoc` creates for a map field such as `ledger`. Where it already resolved to
the value object, the wire format does not change. A `.proto` file can define
such a value object as a nested message inside its main message, beside a map
field whose hidden entry message has the same name. In that case, the file
names the nested message with a trailing underscore, such as `LedgerEntry_`.

## The IR records a value object on a command or event

A `ValueObject` field on a command or event used to appear in the IR as a
plain string:

```json
"addr": {"kind": "standard", "type": "String", "required": true}
```

The IR now records it as a `value_object` field with the value object's
`target`, the kind and target the same field gets on an aggregate:

```json
"addr": {"kind": "value_object", "target": "my_app.Address", "required": true}
```

The entry carries `required` when the field is required. A command or event
still drops the `deprecated`, `description` and `renamed_from` arguments given
to `ValueObject(...)`, so the entry does not carry them, as before.

A field annotated with a value object class, such as `addr: Address`, gets the
same kind of entry. It used to appear as a required `String`.

A value object that only commands and events hold now belongs to the cluster
of their aggregate, under `value_objects`. When messages of two aggregates hold
the value object, Protean scans commands before events, each in registration
order. The aggregate of the first message it finds gets the value object. A
value object that an aggregate, an entity or `part_of` already places keeps
its cluster.

### Who is affected

Anyone with a command or event that has a `ValueObject` field or a field
annotated with a value object class, and a committed `.protean/ir.json` or
schemas generated from one. Regenerate the baseline and commit it:

```shell
protean ir show --domain <module> --canonical > .protean/ir.json
```

Against the old baseline, `protean ir diff` shows each such field's `kind`,
`target` and `type` as changed and lists the value object as added to the
cluster. It reports the field as a breaking type change from `String`. Under
`strictness = "strict"`, it exits `1`, so the `protean-check-compat` hook fails
until the regenerated baseline is committed. Under `strictness = "warn"`, it
exits `0` and the hook passes. The message payloads Protean writes do not
change: the old IR described them wrongly.

`protean check` now also checks value objects that only commands and events
hold. One with a `List` or `Dict` field gets a `VALUE_OBJECT_MUTABLE_FIELD`
warning that it did not get before.

### What changes in the generated contracts

`protean schema generate` used to type the field as a string. It now refers to
the value object:

| Generator | Before | After |
|-----------|--------|-------|
| JSON Schema | `{"type": "string"}` | `{"$ref": "#/$defs/Address"}`, with `Address` in `$defs` |
| Avro | `"string"` | the `Address` record |
| Protobuf | `string addr` | `.<package>.Address addr`, importing the value object's file |

An optional field keeps its `null` union in JSON Schema and Avro and its
`optional` label in Protobuf. The old schemas did not match the data, which
holds an object. Register the new schemas with every registry and consumer that
holds the old ones.

Three kinds of field keep their old IR entries: a query's `ValueObject` field,
a `List(content_type=ValueObject(...))` field on a command or event, and a
field annotated with a union of a value object and another type, such
as `addr: Address | str`.

## `ir diff` exits 3 for non-breaking changes and 2 for errors

`protean ir diff` used to exit `2` both for "non-breaking changes only" and for
an unknown option, and `1` both for breaking changes and for every other error.
A CI gate could not tell a broken run from a safe change, or a load error from
a breaking change.

The exit codes are now:

| Code | Meaning |
|------|---------|
| 0 | No changes, breaking changes under `strictness = "warn"`, or `strictness = "off"` |
| 1 | Breaking changes |
| 2 | Usage, load or config error |
| 3 | Non-breaking changes only |

Three things moved:

- Non-breaking changes only: `2` became `3`.
- A usage, load or config error (a bad option, a missing or invalid IR file, a
  `--domain` that does not load, a missing `.protean/ir.json`, an unknown
  `--base` commit, a malformed `.protean/config.toml`, an IR file that does
  not have the IR structure, or a malformed `deprecated` block in an IR): `1`
  became `2`. The message now goes to
  stderr, and stdout stays empty, including under `--format json`.
- Under `strictness = "off"`, the command used to exit `0` before it checked
  its argument combinations or loaded either side. It now checks them and
  loads both sides first, so a bad command line or an IR file that cannot be
  found or parsed exits `2`. When both sides load, the command still exits `0`
  without comparing them. Only the comparison checks `deprecated` blocks, so a
  malformed `deprecated` block does not fail the step.

Update a CI step that reads the exit code:

- Accept `3` as the code for safe changes. A gate that treated `2` as safe
  now passes a broken run.
- Treat `2` as a failed gate that needs fixing.
- A project on `strictness = "off"` whose IR does not load now fails the step.
  Fix the load error, or remove the step.

Non-breaking changes used to exit `2` and now exit `3`. A gate that fails on
any non-zero exit failed on them before and still fails on them. Allow `3` if
safe changes should pass.

## `upgrade-check` exits 1 for warnings and 2 for errors

`protean upgrade-check` used to exit `2` when it found warnings. Click also
exits `2` for an unknown option, so a script could not tell "review these
findings" from "the command did not run". Other errors exited `1` or ended in
a traceback.

The exit codes are now:

| Code | Meaning |
|------|---------|
| 0 | No findings, or `info` findings only |
| 1 | At least one `warning` finding, including `CHECK_FAILED` |
| 2 | Usage or environment error |

Each outcome moved like this:

| Outcome | 0.18 | 0.19 |
|---------|------|------|
| Warning findings | `2` | `1` |
| A bad `--format`, a malformed `--pinned-version`, or `--pinned-version` without `--opportunities` | `1` | `2` |
| A `--domain` that does not load | `1` | `2` |
| A `--domain` module that raises an error other than `ImportError` at import, an error while the domain initializes, or an error outside a single check | traceback, `1` | `2` |
| An unknown option | `2` | `2` |

Every error message now goes to stderr, and stdout stays empty, including
under `--format json`. Before, the messages printed on stdout.

Update a script that reads the exit code:

- Read `1` as "warnings found" and `2` as a run that failed and needs fixing.
  A script that treated `2` as "warnings found" now reads a broken run as
  findings to review.
- Under `--format json`, an error leaves stdout empty. If the script checked
  that stdout parses as a JSON list to detect an error, check the exit code
  instead.

## `protean new` drops the `migrate` target and lists empty folders

**Generated projects and scripts that read the dry-run list.** Two things
change for a project that `protean new` creates.

The generated `Makefile` no longer has a `migrate` target, for any database.
The target only printed "Add your migration command here". A project on the
`postgresql`, `sqlite` or `mssql` database gets `db-migrate`, `db-upgrade` and
`db-check` targets instead, and a `migrations/` folder. See
[Schema migrations](../cli/project/new.md#schema-migrations).

The `--dry-run` list, and the list that `protean.scaffold.create_project`
returns, now include each empty folder the command creates, with a trailing
`/`. Before, both lists held files only. On a SQL database the list now
includes `migrations/versions/`. A project on `memory` or `elasticsearch` has
no empty folder, so its list is unchanged.

### Who is affected

Anyone whose script or CI runs `make migrate` in a project generated by 0.19.
The target is gone, so `make` stops with "No rule to make target". Run
`make db-migrate m="message"` and `make db-upgrade` on a SQL project, or remove
the call.

Anyone who reads the dry-run output or the `create_project` return value and
treats every entry as a file. Skip or handle entries that end in `/`.

Projects generated before 0.19 keep their `Makefile`. Nothing changes in them.

## Email port removed

The email subsystem was deprecated in 0.17, and 0.18 warned that it would be
removed in 0.19.0. It is now removed. Sending email is an application concern,
so Protean no longer ships a port for it.

These names are gone, and using them raises `AttributeError` or `ImportError`:

- The `@domain.email` decorator and the `DomainObjects.EMAIL` element type.
- `Domain.send_email()`, `Domain.get_email_provider()` and the
  `Domain.email_providers` attribute.
- `domain.registry.emails`.
- `BaseEmail` and `BaseEmailProvider` (`protean.core.email`).
- `EmailProviders`, `DummyEmailProvider` and `SendgridEmailProvider`
  (`protean.adapters.email`, and the two names re-exported from
  `protean.adapters`).

The `sendgrid` extra is gone too, so `pip install "protean[sendgrid]"` no
longer installs the SendGrid client. If your code calls SendGrid directly,
install the `sendgrid` package yourself.

An `[email_providers]` block in `domain.toml` is now ignored. Creating the
`Domain` no longer warns about it, and `protean check` no longer reports it. You can
delete the block. An `[email_providers]` block inside an environment section
(for example `[production.email_providers]`) is still loaded when that
environment is active, so a `${VAR}` placeholder in it must still resolve.
Delete those blocks too.

`protean check` no longer has the `DEPRECATED_EMAIL` and `DEPRECATED_CONFIG`
codes. A `suppress_checks` list or a `[lint].suppressions` table that still
names them keeps working, because nothing emits those codes now. You can drop
those entries.

To keep sending email, do it from an event handler or a subscriber that calls
a notification service in your application:

```python
# fragment
@domain.event_handler(part_of=User)
class WelcomeNotifier:
    @handle(UserRegistered)
    def send_welcome(self, event: UserRegistered) -> None:
        notifications.send_welcome_email(event.email)
```

Here `notifications` is your own module. It can wrap SendGrid, SMTP or any
other service.

## State-based aggregates save their events only through `add()`

A Unit of Work used to save the events of every state-based aggregate it had
read, whether or not `add()` was called on it. The aggregate's field changes
were saved only through `add()`. Suppose a handler read an aggregate, called a
method that raised an event, and never called `add()`. The Unit of Work stored
the event, but the database kept the old state:

```python
# fragment
@handle(ConfirmOrder)
def confirm(self, command: ConfirmOrder) -> None:
    repo = current_domain.repository_for(Order)
    order = repo.get(command.order_id)
    order.confirm()  # sets status and raises OrderConfirmed
    # No repo.add(order): before 0.19, OrderConfirmed was saved and
    # published, but status stayed unchanged in the database.
```

An aggregate's events are now saved only when `add()` has saved the aggregate
in the same Unit of Work. This is the rule event-sourced aggregates already
followed. Events raised on an aggregate that was only read are not saved at
commit. Protean logs nothing and raises nothing. An aggregate removed with
`_dao.delete()` does not count as saved either, so events raised on it before
the delete are not saved.

To keep the event, pass the aggregate to `add()`. That saves its field changes
too:

```python
# fragment
@handle(ConfirmOrder)
def confirm(self, command: ConfirmOrder) -> None:
    repo = current_domain.repository_for(Order)
    order = repo.get(command.order_id)
    order.confirm()
    repo.add(order)
```

Call `add()` after the last change. When an aggregate has no change since it
was read and no pending events, `add()` on it writes nothing. As a result, that
`add()` does not keep an event raised later. If the aggregate changes again
after `add()`, call `add()` again.

Look for this pattern in command handlers, event handlers, application
services and process managers: an aggregate loaded with `get()` or a query, a
method called on it that raises an event, and no `add()` before the Unit of
Work ends. Tests that expect such an event in the event store or the outbox
fail after the upgrade, which is one way to find the places to fix.

## `Float` and `Integer` fields reject a boolean

A `Float` or `Integer` field accepted `True` and `False` and stored them as
`1.0` and `0.0`, or `1` and `0`. A `List` of `Float` or `Integer` did the same
for each element. A flag passed to a numeric field by mistake was saved as a
number with no error.

The fields now reject `True` and `False` with a `ValidationError` keyed on the
field name. This holds at construction on aggregates, entities, value objects,
commands and events, and on assignment to an aggregate or entity field. The fields accept every other value
they accepted before, including a string that holds a number. `Decimal` and
`Boolean` fields are unchanged.

```python
# fragment
reading = Reading(count=True)
# ValidationError: {'count': ['Input should be a valid number, not a boolean']}
```

When your code means to store a flag as a number, convert it first:

```python
# fragment
reading = Reading(count=int(is_enabled), temperature=float(is_enabled))
```

An event stored before 0.19 with `true` or `false` in a `Float` or `Integer`
field now raises `DeserializationError` when it is read back. Correct the
stored data, or raise the event's version and register an upcaster from the
old version to the new one that converts the value to a number. When you
correct a stored payload in place, also set `metadata.envelope.checksum` to
`MessageEnvelope.compute_checksum(corrected_payload)`, imported from
`protean.utils.eventing`. Protean checks the checksum when it reads the event,
and a payload that no longer matches raises `DeserializationError`. See
[Bump the version and write upcasters](../../guides/evolving-events.md#bump-the-version-and-write-upcasters).

## Invariant errors carry a plain `dict`

A pre- or post-invariant can fail on an entity or aggregate that already
exists, for example on a field assignment, inside `atomic_change()` or when
adding a child entity. The `ValidationError` raised there carried `messages` as
a `defaultdict`. When your code read a missing key from `messages`, the
`defaultdict` returned `[]` and added the key. A later `in` check or a loop
over the keys then saw the added key. The same failure during construction
carried a plain `dict`, where a missing key raises `KeyError`.

`messages` is now a plain `dict` on every path. The keys and messages it holds
are unchanged, and so are `codes` and `str(e)`.

No action is needed unless your code reads a key that may be absent from
`e.messages` after an update. That read now raises `KeyError` and leaves
`e.messages` as it was. Use `e.messages.get(key, [])` instead:

```python
# fragment
try:
    account.balance = -5.0
except ValidationError as e:
    balance_errors = e.messages.get("balance", [])
```

## `protean check` reads imports inside a method

`protean check` used to resolve a name in a method body only through the
module's top-level imports and definitions. A name imported inside the method, such as
`from .events import Closed` in the method that raises `Closed`, resolved to
nothing. It now resolves to the imported name for every use after the import,
unless the method could also bind the name another way. Such a name stays
unresolved: for example an assignment or `del` of it, a nested `def` of that
name, a `global` declaration, a second import from a different object, or a
parameter of that name when the import sits inside an `if`, `try`, loop or
`with`.

Every check that reads method bodies sees these imports, so a domain that
imports inside its methods may get different results:

- `UNRAISED_EVENT` no longer reports an event that a method imports and raises.
- `HANDLER_PERSISTS_AND_CALLS_OUT` can report a handler that persists and then
  calls a client it imported inside the method.
- `UNSOURCED_PROJECTION_FIELD` can report a field of a projection that a
  projector imports inside its handler.
- The opt-in `ADAPTER_CALL_IN_DOMAIN` can report an adapter imported inside the
  method.
- The IR's per-method `raises` edges include events imported inside the
  method.

The IR checksum covers the edges and the findings, so `protean ir check` reports
a materialized IR as stale when either changed. To upgrade:

1. Run `protean check` and fix or suppress each new finding.
2. Regenerate the IR baseline.

## Deleting an absent cache or provider raises `KeyError`

`domain.caches` maps each name to its `Cache` service, and `domain.providers`
maps each name to its provider. Deleting a name that is not in them now raises
`KeyError` naming the key, as it does for a `dict`. On a mapping that held no names, which is the case before
`domain.init()`, the same `del` raised a bare `AssertionError`. On a mapping
that held names, it did nothing.

Deleting a configured name works as before.

No action is needed unless your code deletes a cache or provider that may not
be configured. Use `pop()` with a default instead:

```python
# fragment
domain.caches.pop("reporting", None)
domain.databases.pop("analytics", None)
```

## `process(..., asynchronous=True)` inside a Unit of Work waits for the commit

In a domain with `command_processing = "sync"`, `domain.process(command,
asynchronous=True)` used to handle the command at once, inside the caller's Unit
of Work. A version conflict on the command's aggregate then retried the whole
caller, including any outside call the caller had made before.

Now, when a Unit of Work is active and the command has a registered handler,
`process` stores the command and returns `None`. A key that already succeeded still returns the cached result, or raises
`DuplicateCommandError` with `raise_on_duplicate`. The command runs after the
caller's Unit of Work commits, in its own Unit of Work with its own version
retry. This applies wherever a Unit of Work is active:

- a command or event handler method,
- a process manager's handler method,
- a `@use_case` method,
- a `with UnitOfWork():` block,
- code between `UnitOfWork.start()` and `commit()`.

If the caller rolls back, the command does not run. If the command fails while
it runs, the caller's `commit()` raises `TransactionError`, after the caller's
writes are saved. Its cause is the failure, or an `ExceptionGroup` when more
than one command or event handler failed. When the command's deadline has
already passed at the `process` call, `process` still
raises `CommandExpiredError`.

In a process manager, the transition is saved before the command runs, so it
stays saved when the command fails. The `TransactionError` then stops the
process manager's remaining handler methods for that event.

Outside any Unit of Work, the call handles the command at once and returns its
result, as before. A call without `asynchronous=True`, or in a domain with
`command_processing = "async"`, is unchanged.

A command that Protean handles itself, at once or after the commit, is now
stored with `asynchronous` set to `False` in its metadata. A command handled at
once was stored with `True` before, so a running engine could handle it a
second time.

To upgrade:

1. Find code that reads the return value of `process(..., asynchronous=True)`
   inside a handler, a `@use_case` method or a `with UnitOfWork():` block. It
   now gets `None`.
2. Find code that expects the command's changes to be visible later in the same
   Unit of Work. Read them after the Unit of Work commits instead, or call
   `process` without `asynchronous=True`.
3. Find code that catches a command's error around a
   `process(..., asynchronous=True)` call. The error now reaches the caller
   from `commit()` as a `TransactionError`.

## Idle event-store subscriptions wait up to 1 second between reads

With the default `tick_interval` of 0, an event-store subscription used to read
the event store again as soon as a read came back empty, so every idle
subscription queried the store in a tight loop.

Now an idle subscription waits longer between reads. With the default
`tick_interval` of 0, the wait starts at 10 ms after the first empty read. With a
longer `tick_interval`, it doubles from `tick_interval`. Each further empty read
doubles it again, and it stops growing at `max_tick_interval`, 1 second by
default. A read that returns messages sets the wait back to
`tick_interval`. The backoff adds up to 1 second before a new event written to an
idle category reaches its handler. An idle server can also take up to 1 second
longer to shut down, because each idle subscription finishes its current wait
first.

Stream subscriptions and the outbox processor are unchanged. Tests that run the
engine in test mode keep their speed, because test mode caps every wait at
10 ms.

To keep the old behaviour, set `max_tick_interval` to 0:

```toml
# domain.toml
[server.event_store_subscription]
max_tick_interval = 0
```

A value above 0 and below `tick_interval` is ignored, and the subscription logs
`subscription.max_tick_interval_ignored`. When the domain does not set
`max_tick_interval` and `tick_interval` is above 1, the wait stays at
`tick_interval`.

A value that is not a finite number of 0 or more, such as `true`, `nan`, `inf`
or a negative number, is ignored. The subscription logs
`subscription.max_tick_interval_invalid` and uses the 1-second default.

## Adapter registries moved to `protean.infra.registry`

**Breaking, custom adapters.** `ProviderRegistry` and the `registry` instance
in `protean.port.provider` are removed. So are `BrokerRegistry` and the
`registry` instance in `protean.port.broker`. One class, `AdapterRegistry` in
`protean.infra.registry`, now serves all four ports, with one instance each:
`providers`, `brokers`, `event_stores` and `caches`.

These names are removed as well:

- `registry` in `protean.adapters.repository` and `protean.adapters.broker`.
- `EVENT_STORE_PROVIDERS` in `protean.adapters.event_store`.
- `CACHE_PROVIDERS` in `protean.adapters.cache`.

### Who is affected

Anyone whose adapter's `register()` function imports `registry` from
`protean.port.provider`, `protean.port.broker`, `protean.adapters.repository` or
`protean.adapters.broker`. Change the import and the name you call `register()`
on:

```python
# fragment
# Before
from protean.port.provider import registry

registry.register("dynamodb", "my_package.provider.DynamoDBProvider")

# After
from protean.infra.registry import databases

databases.register("dynamodb", "my_package.provider.DynamoDBDatabase")
```

A broker's `register()` function imports `brokers` from
`protean.infra.registry` in the same way. The registry instance for databases
was first named `providers`, and the entry-point group `protean.providers`.
Both are renamed in 0.19; see
[The database port is named Database](#the-database-port-is-named-database).

Code that added an event store or cache by adding a key to
`EVENT_STORE_PROVIDERS` or `CACHE_PROVIDERS` now declares an entry point in the
`protean.event_stores` or `protean.caches` group instead. See
[Building Adapters](../adapters/building-adapters.md#event-store-and-cache-adapters).

### What else changes

- Event stores and caches can now come from other packages. Declare an entry
  point in the `protean.event_stores` or `protean.caches` group whose
  `register()` function calls `event_stores.register()` or `caches.register()`.
  See [Building Adapters](../adapters/building-adapters.md#event-store-and-cache-adapters).
- An unknown name in `[event_store]` or `[caches.<name>]` used to raise
  `KeyError` from `Domain.init()`. It now raises `ConfigurationError` that lists
  the registered names.
- The message for an unknown name now reads the same on every port, for example
  `Unknown database provider 'x'. Available: memory, sqlite. Ensure the package
  that provides it is installed.` Code that matched the old text
  `Available providers:` or `Broker 'x' is not registered` needs updating.
- When a database provider class fails to import, the message now begins
  `Failed to load database provider 'x'`. It began `Failed to load provider
  'x'`.
- The registry rejects an adapter class that leaves an abstract method or
  property unimplemented. `Domain.init()` raises `ConfigurationError` that
  names each missing member. It used to raise `TypeError` when it created the
  instance.

`ProviderRegistry`, `BrokerRegistry` and their `registry` instances belonged to
the adapter-author interface in `protean.port`, which is Provisional. The other
removed names live in adapter implementation modules under `protean.adapters`,
which are Internal. Both tiers allow a change in a minor release with no
deprecation period.

## Provider capability helpers removed

**Breaking, custom database adapters.** `BaseProvider.has_capability`,
`has_all_capabilities` and `has_any_capability` are removed. Check a provider's
`capabilities` with `in` and `&` instead:

```python
# fragment
# Before
if provider.has_capability(DatabaseCapabilities.RAW_QUERIES): ...
if provider.has_all_capabilities(
    DatabaseCapabilities.NATIVE_JSON | DatabaseCapabilities.NATIVE_ARRAY
): ...
if provider.has_any_capability(
    DatabaseCapabilities.TRANSACTIONS | DatabaseCapabilities.SIMULATED_TRANSACTIONS
): ...

# After
if DatabaseCapabilities.RAW_QUERIES in provider.capabilities: ...
if (
    DatabaseCapabilities.NATIVE_JSON | DatabaseCapabilities.NATIVE_ARRAY
) in provider.capabilities: ...
if provider.capabilities & (
    DatabaseCapabilities.TRANSACTIONS | DatabaseCapabilities.SIMULATED_TRANSACTIONS
): ...
```

`in` with a set of flags is true only when the provider declares every flag in
the set. `&` with a set is true when the provider declares at least one of
them. Brokers keep their helper methods.

`BaseProvider` belongs to the adapter-author interface in `protean.port`, which
is Provisional. That tier allows a change in a minor release with no
deprecation period.

### Who is affected

Anyone whose code calls one of the three methods on a database provider, and
anyone whose custom provider overrides one of them. An override is no longer
called by Protean. A custom provider that only defines the `capabilities`
property keeps working unchanged.

### What else changes

`DatabaseCapabilities` has three new flags for claims and deletes. No
convenience set includes them. A fourth new flag, `INSERT_IF_ABSENT`, comes with
the [`DAOPort` split](#basedao-is-split-into-daoport-and-the-dao-service).

- `NATIVE_CLAIM`: the provider claims rows in one statement. PostgreSQL
  declares it.
- `BOUNDED_DELETE`: the provider deletes up to `limit` rows in one operation,
  without a separate read of their ids. Memory, SQLite, PostgreSQL, MSSQL and Elasticsearch declare it.
- `FILTERED_CLAIM_CANDIDATES`: the provider can leave held rows out of a
  claim's candidates. SQLite, PostgreSQL, MSSQL and MySQL declare it.

A built-in provider's `capabilities` is no longer equal to a convenience set
alone. For example, the memory provider returns
`IN_MEMORY | BOUNDED_DELETE | INSERT_IF_ABSENT`, not `IN_MEMORY`. Code that compares a provider's set with a convenience set,
such as `provider.capabilities == DatabaseCapabilities.IN_MEMORY`, must check
for the flags it needs with `in` instead.

## Capability flags choose the claim and bounded-delete paths

**Breaking, custom database adapters.** The `DAO` service's `claim` and
`delete_top` choose their path from the provider's capability flags.
Each flag goes with a port in `protean.port.dao` and a public DAO method:

| Flag | Port | DAO method |
|------|------|------------|
| `NATIVE_CLAIM` | `NativeClaimPort` | `claim` |
| `FILTERED_CLAIM_CANDIDATES` | `ClaimCandidatesPort` | `claim_candidates` |
| `BOUNDED_DELETE` | `BoundedDeletePort` | `delete_top` |

When the provider declares `NATIVE_CLAIM`, the service calls the adapter's
`claim` for every claim with a positive `limit`. When it declares
`BOUNDED_DELETE`, the service calls the adapter's `delete_top` for every
bounded delete with a positive `limit`. A non-positive `limit` claims or
deletes nothing and calls no adapter method. Without these flags, the service
runs the portable claim or delete. The portable claim calls
`claim_candidates` to read each page only for a claim with a `hold_back`, and
only when the provider declares `FILTERED_CLAIM_CANDIDATES`. A provider that
declares a flag for a DAO class that does not subclass the port raises
`ConfigurationError` when the `DAO` service is built, on the first use of a
repository for the entity.

```python
# fragment
# Before
class MyDAO(BaseDAO):
    def _delete_top(self, criteria, limit, order_by=None) -> int: ...


# After
class MyDAO(DAOPort, BoundedDeletePort):
    def delete_top(self, session, criteria, limit, order_by=None) -> int: ...


class MyDatabase(BaseDatabase):
    @property
    def capabilities(self) -> DatabaseCapabilities:
        return DatabaseCapabilities.BASIC_STORAGE | DatabaseCapabilities.BOUNDED_DELETE
```

`DAOPort` belongs to the adapter-author interface in `protean.port`, which is
Provisional. That tier allows a change in a minor release with no deprecation
period.

### Who is affected

Anyone whose custom DAO overrides `_claim`, `_claim_candidates` or
`_delete_top`:

- `BaseDAO` is gone, so Protean no longer calls a `_claim_candidates`
  override. Rename it to `claim_candidates`, subclass
  `ClaimCandidatesPort`, and declare `FILTERED_CLAIM_CANDIDATES`.
- Rename an override of `_claim` or `_delete_top` to `claim` or
  `delete_top`, add the `session` first argument, subclass the port, declare
  the flag, and drop any `super()` fallback, since the `DAO` service runs the
  portable path itself.
- An override of `_claim` that only wrapped the portable claim in a lock
  becomes an override of `claim_lock()`. The portable claim and delete run
  inside `claim_lock()`, which locks nothing by default.
- A custom provider that subclasses `SAProvider` directly, not one of the
  dialect providers, declares no claim or delete flag. Before 0.19, `SADAO`
  chose the one-statement claim on a PostgreSQL connection and the
  one-statement delete on PostgreSQL, SQLite and SQL Server connections. Such a
  provider now takes the portable claim and delete, which give the same
  results in more round trips. To keep the one-statement paths, add the flags
  that `PostgresqlProvider`, `SqliteProvider` or `MssqlProvider` declares to
  its `capabilities`.
- Such a provider also does not declare `INSERT_IF_ABSENT`. Before 0.19,
  `SADAO.save_if_absent` returned `None` on every `SAProvider` when the
  database's unique index rejected the write. Such a provider now checks the
  key and then saves. When two writers pass the check together, the database
  rejects the second write with its own error, and that writer gets the error
  instead of `None`. Add `INSERT_IF_ABSENT` to its `capabilities` to keep the
  earlier behaviour.

A custom DAO that overrides none of these needs only the changes in
[`BaseDAO` is split into `DAOPort` and the `DAO` service](#basedao-is-split-into-daoport-and-the-dao-service).

See [Declaring Capabilities](../adapters/database/custom-databases.md#declaring-capabilities)
for the method signatures.

## `BaseDAO` is split into `DAOPort` and the `DAO` service

**Breaking, custom database adapters.** `BaseDAO` is gone. An adapter's DAO
class now implements the `DAOPort` protocol in `protean.port.dao`, and Protean
wraps it in its own `DAO` service from `protean.infra.dao`. The service runs
the save lifecycle, the capability checks and the session handling that
`BaseDAO` ran. Repositories and the query API call the service.

Each storage operation on the adapter takes the session to run in as its first
argument. The adapter writes in that session and never commits, rolls back or
closes it. The Elasticsearch adapter is the exception: Elasticsearch has no
transactions, so `ElasticsearchDAO` ignores the session and writes through the
provider's client at once.

| Before | After |
|--------|-------|
| `class MyDAO(BaseDAO)` | `class MyDAO(DAOPort)`, plus the optional ports the provider's flags need |
| `_filter(criteria, offset=0, limit=10, order_by=(), with_total=True, fields=None)` | `filter(session, criteria, *, offset=0, limit=10, order_by=(), with_total=True, fields=None)` |
| `_count(criteria)` | `count(session, criteria)` |
| `_create(model_obj)` | `insert(session, model)` |
| `_update(model_obj, expected_version=None)` | `update(session, model, *, expected_version=None)` |
| `_update_all(criteria, *args, **kwargs)` | `update_all(session, criteria, values)` |
| `_delete(model_obj)` | `delete(session, model)` |
| `_delete_all(criteria=None)` | `delete_all(session, criteria=None)` |
| `_raw(query, data=None)` | `raw(session, query, data=None)` on `RawQueryDAOPort` |
| `claim(criteria, claim_fields, limit, order_by=(), hold_back=None)` on `NativeClaimPort` | `claim(session, criteria, claim_fields, limit, order_by=(), hold_back=None)` |
| `claim_candidates(criteria, limit, offset, order_by, hold_back)` on `ClaimCandidatesPort` | `claim_candidates(session, criteria, limit, offset, order_by, hold_back)` |
| `delete_top(criteria, limit, order_by=None)` on `BoundedDeletePort` | `delete_top(session, criteria, limit, order_by=None)` |
| An override of `save_if_absent(entity_obj, *, apply_hooks=True)`, as in `DictDAO` and `SADAO` | `insert_if_absent(session, model)` and `update_if_absent(session, model, *, expected_version=None)` on `InsertIfAbsentPort`, with the `INSERT_IF_ABSENT` flag |

The adapter DAO's constructor takes `(provider, entity_cls,
database_model_cls)`, without the domain.

The `DAO` service that a repository holds renames the framework operations:

| Before (on `BaseDAO`) | After (on `DAO`) |
|-----------------------|------------------|
| `_update_all(criteria, *args, **kwargs)` | `update_all(criteria, values)`, with the new values as one mapping |
| `_delete_all(criteria=None)` | `delete_all(criteria=None)` |
| `delete_all()`, which returned `None` | `delete_all()`, which returns the number of rows deleted |
| `_claim(criteria, claim_fields, limit, order_by=None, hold_back=None)` | `claim(criteria, claim_fields, limit, order_by=None, hold_back=None)` |
| `_delete_top(criteria, limit, order_by=None)` | `delete_top(criteria, limit, order_by=None)` |

`DatabasePort` gains three abstract members that the service uses outside a
Unit of Work: `new_session()`, `commit(session)` and `rollback(session)`. A
provider can also override `flush(session)`, which does nothing by default.
For each standalone operation, the service gets a session from
`new_session()`, calls `commit(session)` when the operation succeeds, and
calls `rollback(session)` when the operation or the commit raises an
`Exception`. It then closes the session. A `BaseException` that is not an
`Exception`, such as `KeyboardInterrupt`, closes the session with no rollback.

An override of `save_if_absent` becomes the two `InsertIfAbsentPort` methods,
and the provider declares `DatabaseCapabilities.INSERT_IF_ABSENT`. The
`IN_MEMORY` and `RELATIONAL` capability sets include `RAW_QUERIES`, so a
provider that declares either set needs a DAO class that subclasses
`RawQueryDAOPort`.

A provider that declares a flag whose port the DAO class does not subclass
raises `ConfigurationError`, which names the flag and the class. The error is
raised when the `DAO` service is built: for a SQL provider that is when the
provider registers its tables, and for any other provider it is the first use
of a repository for the entity.

```python
# fragment
# Before
class MyDAO(BaseDAO):
    def _create(self, model_obj):
        conn = self._get_session()
        ...
        self._commit_if_standalone(conn)


class MyDatabase(BaseDatabase):
    def dao_for(self, entity_cls, model_cls):
        return MyDAO(self.domain, self, entity_cls, model_cls)


# After
class MyDAO(DAOPort):
    def __init__(self, provider, entity_cls, database_model_cls):
        self.provider = provider
        self.entity_cls = entity_cls
        self.database_model_cls = database_model_cls
        self.schema_name = entity_cls.meta_.schema_name

    def insert(self, session, model):
        ...


class MyDatabase(BaseDatabase, DatabasePort):
    def dao_for(self, entity_cls, model_cls):
        return MyDAO(self, entity_cls, model_cls)

    def new_session(self):
        return MySession()

    def commit(self, session):
        session.commit()

    def rollback(self, session):
        session.rollback()
```

`DAOPort` and `DatabasePort` belong to the adapter-author interface in
`protean.port`, which is Provisional. That tier allows a change in a minor
release with no deprecation period.

### Who is affected

- **Anyone who wrote a database adapter.** Rename the DAO's operations, add the
  `session` argument, remove calls to `_get_session()` and
  `_commit_if_standalone()`, and add `new_session()`, `commit()` and
  `rollback()` to the provider.
- **Code that called `_update_all`, `_delete_all`, `_claim` or `_delete_top`
  on a repository's DAO.** Call `update_all`, `delete_all`, `claim` or
  `delete_top`, and pass `update_all` its values as a dict.
- **Code that checks `isinstance(dao, SADAO)` or another adapter class on a
  repository's DAO.** The repository holds the `DAO` service. The adapter DAO
  is `dao._adapter`.
- **Code that imports `BaseDAO` from `protean.port.dao`.** The import raises
  `ImportError`. Import `DAOPort` for an adapter, or `DAO` from
  `protean.infra.dao` for the service.
- **A custom session class.** `SessionProtocol.is_active` is now a read-only
  property, so a session class must define `is_active` as a property or an
  attribute.
- **Code that calls `save_if_absent` on the memory adapter.** The pre-persist
  hooks (`auto_now` stamping and aggregate enrichers) now run before the key
  check, as they already did on SQL databases. When another row holds the key,
  `save_if_absent` still writes nothing and returns `None`, and the entity
  keeps the hooks' changes.

Application code that uses repositories and `QuerySet` needs no other change.
A standalone read now commits its session as well, so on a backend whose
commit fails, a read outside a Unit of Work raises the commit's error.

## `BaseCache` is replaced by three cache protocols

**Breaking, custom cache adapters.** `BaseCache` is removed. A cache adapter now
stores plain dicts under string keys. A new `Cache` class does the projection
work on top of it: it builds the keys, serializes and rebuilds projections,
resolves TTLs and caps `_get_all`.

`protean.port.cache` defines three protocols:

- `CachePort`, which every adapter subclasses: `capabilities`, `ping`,
  `health`, `get_connection`, `clear`, `get`, `put` and `delete`. `close` is
  optional and does nothing by default.
- `CacheTTLPort`, which an adapter that declares `CacheCapabilities.TTL` also
  subclasses: `set_ttl` and `get_ttl`.
- `CachePatternPort`, which an adapter that declares
  `CacheCapabilities.PATTERN_MATCH` also subclasses: `keys_matching`,
  `count_matching` and `delete_matching`.

### Who is affected

Anyone who wrote a cache adapter. Rewrite it against the protocols:

```python
# fragment
# Before
from protean.port.cache import BaseCache


class MyCache(BaseCache):
    def add(self, projection, ttl=None): ...
    def get(self, key): ...
    def flush_all(self): ...


# After
from protean.port.cache import CacheCapabilities, CachePatternPort, CacheTTLPort


class MyCache(CacheTTLPort, CachePatternPort):
    def __init__(self, name, domain, config):
        self.name = name
        self.domain = domain
        self.config = config

    @property
    def capabilities(self):
        return CacheCapabilities.LOCAL

    def get(self, key): ...  # the stored dict, or None
    def put(self, key, value, ttl): ...  # ttl is seconds, or None for no expiry
    def clear(self): ...
```

The example shows four members. Python refuses to build `MyCache` until it also
defines `ping`, `health`, `get_connection` and `delete`, the `set_ttl` and
`get_ttl` members of `CacheTTLPort`, and the `keys_matching`, `count_matching`
and `delete_matching` members of `CachePatternPort`.

`Domain.init()` raises `ConfigurationError` when an adapter declares `TTL` or
`PATTERN_MATCH` and does not subclass the matching protocol. The message names
the cache and the capability, and lists the methods the adapter lacks when it
lacks any. `Domain.init()` also raises `ConfigurationError`, naming the cache,
when an adapter has no `capabilities` or no `config` attribute.

### What else changes

- A cache whose adapter does not declare `TTL` stores an entry with no expiry
  when you call `add` without a TTL. With an explicit TTL, `add` raises
  `NotSupportedError`.
- `set_ttl`, `get_ttl`, `count`, `remove_by_key_pattern` and `_get_all` raise
  `NotSupportedError` on a cache whose adapter does not declare the capability
  they need.

The cache protocols belong to the adapter-author interface in `protean.port`,
which is Provisional, so this change lands in a minor release with no
deprecation period.

## `BaseLookup` is now `LookupPort`

**Breaking.** `protean.port.dao.BaseLookup` is removed. A lookup subclasses
`protean.port.dao.LookupPort`, a Protocol that declares `lookup_name`,
`source`, `target`, `database_model_cls` and the constructor
`(source, target, *, database_model_cls=None)`.

The Protocol declares no `as_expression()`, `process_source()` or
`process_target()`. Each adapter's lookup base class declares the method its
DAO calls. The SQL and Elasticsearch `DefaultLookup` classes keep
`as_expression()`, `process_source()` and `process_target()`. The memory
adapter's `MemoryLookup` keeps `evaluate()` and no longer defines
`as_expression()`.

`get_lookup()` checks that the registered class has `LookupPort` in its MRO.
When it does not, or when no lookup is registered under the name, it raises
`NotImplementedError` with a message that names the lookup and the provider.

### Who is affected

A custom adapter whose lookups subclass `BaseLookup`. Subclass `LookupPort`,
set `source`, `target` and `database_model_cls` in the base class constructor,
and declare the evaluation method there. `LookupPort` supplies no constructor
body, so a lookup class without its own constructor builds without these
attributes:

```python
# fragment
# Before
from protean.port.dao import BaseLookup


class YourLookup(BaseLookup):
    def as_expression(self): ...


# After
from protean.port.dao import LookupPort


class YourLookup(LookupPort):
    def __init__(self, source, target, *, database_model_cls=None):
        self.source, self.target = source, target
        self.database_model_cls = database_model_cls

    def as_expression(self): ...
```

`BaseLookup` also supplied `process_source()` and `process_target()`, which
returned `source` and `target` unchanged. A lookup that called them on a
direct `BaseLookup` subclass defines them itself.

A lookup that subclasses the SQL or Elasticsearch `DefaultLookup` needs no
change. A lookup that subclasses the memory adapter's `MemoryLookup` and calls
`process_source()` or `process_target()` reads `self.source` and `self.target`
instead, because `MemoryLookup` no longer has those methods.

```python
# fragment
store.get_stream_messages("user-1", position=5, limit=20)
```

A custom event store no longer implements one `_read` for every scope. It
implements `get_stream_messages`, `get_category_messages` and
`get_all_messages`. The `EventStore` service picks one of the three from the
stream name it is given.

**Breaking, custom event stores and code that reads raw messages.** `_read` on
a category such as `user` is now `get_category_messages(category, position=0,

`position`. A call that read 100 rows of `user` with `_read` becomes:

```python
# fragment
```

The memory store now matches a category only up to the `-` that starts the
stream ID. Before, a read of `user` also returned the rows of `poweruser-1`.

On Message DB, the method also takes `consumer_group_member` and
`consumer_group_size` as keywords, and Message DB now declares
`CONSUMER_GROUPS`. The memory store raises `NotSupportedError` when either
argument is given.

## Reading the whole store uses `get_all_messages`

**Breaking, custom event stores and code that reads raw messages.**

**Breaking, custom event stores and code that reads raw messages.**

| `_read_last_message("user-1")` | `get_last_stream_message("user-1")` |

## A custom event store must define `ping()`, `health()` and `get_connection()`

**Breaking, custom event stores.** `BaseEventStore` declares `ping()`,
`health()` and `get_connection()` as abstract methods. A custom event store
that does not define all three raises `TypeError` when the domain builds it.

- `ping()` returns `True` when the store answers and `False` when it does not.
  It never raises.
- `health()` returns an `EventStoreHealth` with `reachable` set to the result
  of `ping()`, and `pool` set to the store's pool statistics or `None`.
- `get_connection()` returns the store's native client, or `None` when the
  store has none.

The event store check behind `/readyz` now calls `ping()`. It used to read the
last message of a stream that does not exist.

```python
# fragment
from protean.port.event_store import EventStoreHealth


class MyEventStore(BaseEventStore):
    def ping(self) -> bool:
        return True

    def health(self) -> EventStoreHealth:
        return EventStoreHealth(reachable=self.ping(), pool=None)

    def get_connection(self) -> None:
        return None
```

## `EventStore` moved to `protean.infra.event_store`

**Code that imports `EventStore` or reads the event store adapter.** Import
`EventStore` from `protean.infra.event_store`; `protean.adapters.event_store`
no longer defines it. `domain.event_store` is the `EventStore` service, and the
adapter it builds is `domain.event_store._adapter`. `domain.event_store.store`
returns the same adapter in 0.19.

The service has the event store's reads, writes, aggregate loading and

`category_head_position`, `load_aggregate`, `create_snapshot`,
`create_snapshots` and `category`. It also has causation tracing and the

`adapter.domain.event_store._adapter`, not on the instance they are called on.

`BaseEventStore._last_event_of_type` and `BaseEventStore._events_of_type` are
removed. To find the events of one type, read the stream with
`domain.event_store.read_all(stream)` and filter on

## Event handler and projector categories get the domain prefix

**Behaviour change, event handlers that set `stream_category` or
`source_stream`, and projectors that set `stream_categories`.** Protean now
prefixes each of these values with the domain name when the value has no `::`.
In a domain named `ecommerce`, `stream_category="all_orders"` registers as
`ecommerce::all_orders`, which is the category an aggregate with
`stream_category="all_orders"` writes to. Two values stay as written: `$all`,
and a value that already contains `::`, such as `billing::invoice`.

An aggregate's category follows a different rule. Protean prefixes it even
when it contains `::`, so an aggregate with `stream_category="billing::invoice"`
in a domain named `ecommerce` writes to `ecommerce::billing::invoice`. To read
that aggregate, a handler names `ecommerce::billing::invoice` or uses
`part_of`.

The handler and the projector now read the same streams on the memory store
and on Message DB. Before, Message DB delivered nothing to a bare category, and
the memory store delivered the events because its category match was looser.
A bare `source_stream` never matched before, because the origin stream in an
event's metadata always carries the domain prefix.

The category also names the handler's position stream
(`position-<Handler>-<category>`) and its dead-letter stream
(`<category>:dlq`). A handler with a bare category finds no stored position under
the prefixed name, so at its first start after the upgrade it reads the
category from the first event. On Message DB, the handler never received these
events before, so it now handles every event the category already holds. Check
that its side effects are safe to run for past events before you deploy. The
positions and dead-letter messages stored under the bare name stay where they
are.

A handler that read streams written without a domain prefix, for example by a
producer outside Protean, can no longer name them with a bare value. Subscribe
it to `$all` and filter the events in the handler, or consume the stream with
a [subscriber](../../guides/consume-state/subscribers.md).

Code that compares `meta_.stream_category` to a bare string compares it to the
prefixed value:

```python
# fragment
assert OrderReportHandler.meta_.stream_category == "ecommerce::all_orders"
```

## A memory event store row carries `time` as a `datetime`

**Behaviour change, code that reads raw messages from the memory store.** A
row that the memory event store returns used to carry `time` as an ISO-8601
string. It now carries a `datetime`, as a Message DB row does. Code that
parsed the value with `datetime.fromisoformat(row["time"])` now raises
`TypeError`. Use `row["time"]` directly.

## A memory event store write survives a Unit of Work rollback

**Breaking, tests that run on the memory event store.** The memory
event store used to save each message through an internal aggregate and its
repository. The save joined the active Unit of Work,
so a rollback discarded a message the store had already reported as written.
The store now keeps its messages in its own list and writes each one at once,
as Message DB does. A message appended inside a Unit of Work that then raises,
such as a command a handler issues before it fails, stays in the store.

A test that counted events or commands after a rolled-back Unit of Work now
counts the appended messages too. Change the expected count to the one Message
DB gives.

The domain no longer registers that internal aggregate or its repository, and
`protean.adapters.event_store.memory` no longer defines them. Code that read
rows through the aggregate's repository reads them through the store instead, with `get_stream_messages`, `get_category_messages` or
`get_all_messages`. `get_connection()` on the memory store returns the list of
stored rows, so a test can seed a row directly.

`time` with `str()`, as in `2026-04-01 12:00:00+00:00`. It now writes it with

## `domain.brokers` returns `Broker` services

**Breaking, custom adapters.** `domain.brokers[name]` now returns a `Broker`
service from `protean.infra.broker`. The service wraps the broker adapter. It
records messages on the current Unit of Work, retries once after a connection
error, checks capabilities, times pings, builds the health envelope and hands
messages to subscribers in synchronous processing. The adapter itself is the
service's `_adapter` attribute, which is Internal.

A broker adapter now implements the `BrokerPort` Protocol from
`protean.port.broker`. Declare it as `class MyBroker(BaseBroker, BrokerPort)`,
with `BaseBroker` first, and implement the Port's methods under their public
names: `publish`, `read`, `ack`, `nack`, `create_group`, `consumer_groups`,
`ping`, `health`, `get_connection`, `reconnect`, `clear` and the `capabilities`
property. The underscore hooks (`_publish`, `_read`, `_get_next`, `_ack`,
`_nack`, `_ping`, `_health_stats`, `_ensure_connection`, `_info`,
`_data_reset` and `_ensure_group`) are gone. The `_dlq_*` hooks do not change.

### Who is affected

Anyone who wrote a broker adapter, and anyone whose code reads an attribute
that only the adapter has, such as `redis_instance` or `conn_info`. See
[Custom Brokers](../adapters/broker/custom-brokers.md) for the full Port.

```python
# fragment
# Before
class KafkaBroker(BaseBroker):
    def _publish(self, stream, message): ...

# After
from protean.port.broker import BaseBroker, BrokerPort


class KafkaBroker(BaseBroker, BrokerPort):
    def publish(self, stream, message): ...
```

`read` returns a list of `BrokerMessage` records. A `BrokerMessage` unpacks as
`(id, payload)`, so a loop written as `for identifier, payload in messages`
keeps working. `read` takes a keyword argument `new_messages`, which replaces
the `_get_next` hook. With `new_messages=True` the adapter skips messages that
are pending in the group, meaning delivered and not yet acknowledged. A broker
that redelivers a nacked message by putting it back on the stream, as the
inline broker does, returns that message as a new one. The service's
`get_next` calls `read` with `limit=1` and `new_messages=True`.

`BaseBroker` and `BrokerPort` are Provisional, and a minor release may change
them with no deprecation period.


A custom adapter implements `health()` in place of `_health_stats()`, and

The two Redis brokers now count `total_messages` on fewer streams. The Redis

## Broker `info()` is now `consumer_groups()`

**Breaking, custom adapters.** The adapter method `info()` and its hook
`_info()` are replaced by `consumer_groups()`. `info()` returned
`{"consumer_groups": {...}}`. `consumer_groups()` returns the inner dict,
keyed by group name, and each value is a `ConsumerGroupInfo` with these keys:

- `name`, `consumer_count` and `pending` on every broker.
- `consumers`, a list of `{"name": ..., "pending": ...}`, where the broker
  tracks consumers.
- `last_delivered_id` and `created_at` where the broker records them.

A broker without acknowledgement reports `pending` as `0`. The Redis broker
adds up a group's pending counts over the streams it reads, counts each
consumer once, and no longer returns the copy keyed by stream. The inline broker no longer returns
`in_flight_messages`, `failed_messages` or `dlq_messages`.

The `Broker` service does not expose `consumer_groups()` as a public method,
and it has no `info()`. Code that called `domain.brokers[name].info()` gets an
`AttributeError`, and has no public replacement in this release.

On a broker that has no Redis client, `protean subscriptions status` reads
the groups through the service and reports each group's pending and consumer
counts. A broker whose `get_connection()` returns a Redis client, such as Redis
Streams or Redis PubSub, is read through Redis directly.

On the inline broker, `pending` counts messages delivered to the group and not
yet acknowledged or nacked. So `protean subscriptions status` now reports a
subscriber on the inline broker as `lagging` while a delivered message waits
for its acknowledgement. Before, it reported `ok`.



## Broker partition methods move to `PartitioningPort`

**Breaking.** A custom broker that declares
`BrokerCapabilities.STREAM_PARTITIONING` subclasses `PartitioningPort` from
`protean.port.broker` and implements its nine public methods:
`record_partition`, `partition_keys`, `reap_partition`,
`acquire_partition_lease`, `renew_partition_lease`, `release_partition_lease`,
`read_partition_fenced`, `ack_partition_fenced` and
`reclaim_partition_pending`. The underscore hooks on `BaseBroker`, such as
`_record_partition`, are gone, and so are the public wrappers that called
them. If the broker declares the capability and does not subclass
`PartitioningPort`, `domain.init()` raises `ConfigurationError`.
`ENTERPRISE_STREAMING` includes `STREAM_PARTITIONING`, so a broker that
declares that tier needs `PartitioningPort` too.

Three arguments change name. The `count` argument of `read_partition_fenced`
and `reclaim_partition_pending` is renamed `limit`, and the `identifier`
argument of `ack_partition_fenced` is renamed `message_id`. Both reads return
`BrokerMessage` records, which unpack as `(id, payload)`. The Port methods have
no default arguments, so the adapter receives every argument on every call.

```python
# fragment
# Before

                              new_messages): ...
```

The `Broker` service that `domain.brokers[name]` returns has no public
partition methods, because only Protean's outbox processor, partitioned
subscriptions and the subscription status collector call them. Code that called
`broker.partition_keys(...)` calls it on the adapter, `broker._adapter`.

`_ensure_connection()`. It returns `True` when the connection works or was
restored. The `Broker` service has no public `reconnect()` or
`ensure_connection()`, so code that called `domain.brokers[name].ensure_connection()`
gets an `AttributeError`.

After a connection error in `publish`, `read`, `get_next`, `ack`, `nack`,
`read_blocking` or `read_blocking_streams`, the service calls `reconnect()`
once and retries the operation. Code that called `ensure_connection()` before
one of these can drop the call. The dead-letter, trim and partition
operations are not retried, so code that called `ensure_connection()` before
them has no replacement.

---

## Broker `close()` is called through `domain.brokers.close()`

**Breaking.** `domain.brokers[name]` has no public `close()`. Close the
brokers through `domain.brokers.close()`, which closes each one. A custom
adapter still implements `close()`, and the `BrokerPort` default does
nothing.

```python
# fragment
# Before
domain.brokers["default"].close()

# After
domain.brokers.close()
```

---

## Broker `_ensure_group()` is now `create_group()`

**Breaking, custom adapters.** A custom adapter implements
`create_group(stream, consumer_group)` in place of
`_ensure_group(group_name, stream=None)`. The stream is now the first
argument, and both arguments are required.

```python
# fragment
# Before
def _ensure_group(self, group_name, stream=None): ...

# After
def create_group(self, stream, consumer_group): ...
```

---

## Broker `_reclaim_idle_pending()` is now `reclaim_idle_pending()`

**Breaking, custom adapters.** The Port names the hook
`reclaim_idle_pending()`, without the underscore. Its `group_name` argument is
now `consumer_group`. The Port's default does nothing and returns an empty
dict, so an adapter without pending-message tracking does not define it.

---

## Broker `_cleanup_stale_consumers()` and `_mark_subscription_owned()` lose the underscore

**Breaking, custom adapters.** The Port names these hooks
`remove_stale_consumers(stream, consumer_group, current_consumer)` and
`mark_subscription_owned(stream, consumer_group)`. The framework no longer
calls the old names, so an adapter that overrides `_cleanup_stale_consumers()`
or `_mark_subscription_owned()` renames its method. The Port's defaults do
nothing, and `remove_stale_consumers()` returns `0`.

---

## Broker `conn_info` is now `config`

**Breaking, custom adapters.** `BaseBroker.__init__` takes `config` in place of
`conn_info`, and the adapter reads its settings from `self.config`. `config`
is a copy of the domain's broker settings, so writing to it does not change
the domain configuration.

```python
# fragment
# Before
def __init__(self, name, domain, conn_info):
    super().__init__(name, domain, conn_info)
    self.client = connect(self.conn_info["URI"])

# After
def __init__(self, name, domain, config):
    super().__init__(name, domain, config)
    self.client = connect(self.config["URI"])
```

---

## The database port is named Database

**Breaking, every domain that sets a `provider` option or imports a database
adapter.** The database port, its adapters and the options that point at it
now use the word "database", as the broker, event store and cache ports use
their own names. There are no aliases. An old import path raises
`ImportError`. A renamed option raises `ConfigurationError` that names its
replacement, for example ``Renamed option(s): `provider` is now `database` ``.

The prose and the "Before" code in other sections on this page use the names
from before the rename. Their "After" code uses the new names. Read the old
names with this table.

| Before | After |
| --- | --- |
| `protean.port.provider` | `protean.port.database` |
| `ProviderPort` | `DatabasePort` |
| `RawQueryProviderPort` | `RawQueryDatabasePort` |
| `ProviderHealth` | `DatabaseHealth` |
| `BaseProvider` | `BaseDatabase` |
| `protean.adapters.repository` | `protean.adapters.database` |
| `MemoryProvider` | `MemoryDatabase` |
| `SAProvider` | `SADatabase` |
| `PostgresqlProvider` | `PostgresqlDatabase` |
| `SqliteProvider` | `SqliteDatabase` |
| `MssqlProvider` | `MssqlDatabase` |
| `MysqlProvider` | `MysqlDatabase` |
| `ESProvider` | `ESDatabase` |
| `Providers`, `domain.providers` | `Databases`, `domain.databases` |
| `protean.infra.registry.providers` | `protean.infra.registry.databases` |
| Entry-point group `protean.providers` | `protean.databases` |
| `provider=` on an aggregate, entity, projection or subscriber | `database=` |
| `meta_.provider` | `meta_.database` |
| `database=` on a repository or database model | `database_type=` |
| `meta_.database` on a repository or database model | `meta_.database_type` |
| `protean.utils.Database` | A string, such as `"postgresql"`, or a dialect's `database_type` |
| `SAProvider.databases` | Each dialect's `database_type`, such as `PostgresqlDatabase.database_type` |
| `protean.utils.Cache` | A string, such as `"redis"` |
| `__broker__` on a broker class | `broker_type` |

The `provider` key inside `[databases.<name>]`, `[brokers.<name>]`,
`[caches.<name>]` and `[event_store]` keeps its name, so `domain.toml` does not
change. The IR keeps its keys as well: an aggregate, entity or projection still
records `"provider"`, and a repository or database model still records
`"database"`, so a committed `.protean/ir.json` stays valid.

### How to upgrade

1. Rename `provider=` to `database=` on every `@domain.aggregate`,
   `@domain.entity`, `@domain.projection` and `@domain.subscriber`, and in
   every `domain.register()` call for those elements.
2. Rename `database=` to `database_type=` on every `@domain.repository` and
   `@domain.database_model`.
3. Replace `Database.postgresql.value` and the other enum members with the
   string they held, such as `"postgresql"`.
4. Change imports from `protean.port.provider` and `protean.adapters.repository`
   to `protean.port.database` and `protean.adapters.database`, and rename the
   classes by the table.
5. Rename `domain.providers` to `domain.databases`.
6. In a custom database adapter's package, rename the entry-point group to
   `protean.databases` and import `databases` from `protean.infra.registry`.
7. In a custom broker, rename the class attribute `__broker__` to
   `broker_type`.

```python
# fragment
# Before
@domain.aggregate(provider="analytics")
class Report: ...


@domain.repository(part_of=Report, database="postgresql")
class ReportRepository: ...


# After
@domain.aggregate(database="analytics")
class Report: ...


@domain.repository(part_of=Report, database_type="postgresql")
class ReportRepository: ...
```

```toml
# Before
[project.entry-points."protean.providers"]
dynamodb = "my_package.provider:register"

# After
[project.entry-points."protean.databases"]
dynamodb = "my_package.provider:register"
```

### What else changes

- `domain.init()` now checks each repository's and database model's
  `database_type`. A repository may name `"ALL"`, and a database model may
  leave it unset. Any other value must be a string equal to the
  `database_type` of an installed adapter, or `domain.init()` raises
  `ConfigurationError`. `protean check` reports the same error. A repository
  or database model registered after `domain.init()` is checked when it
  registers. Before 0.19, `@domain.repository` checked the value against the
  `Database` enum when the class was registered and raised
  `IncorrectUsageError`. A custom adapter's `database_type` is now accepted.
- The built-in type names `postgresql`, `sqlite`, `mssql`, `mysql` and
  `elasticsearch` pass the check even when their extra is not installed, as
  they did before 0.19. An adapter that is registered but fails to load counts
  under its registered name, because its `database_type` cannot be read.
- An adapter package that still declares the `protean.providers` entry-point
  group is not loaded. Protean logs a warning that names it.
- `BaseBroker` declares `broker_type` as a class attribute, so a type checker
  reads it on any broker.

The port types belong to the adapter-author interface in `protean.port`,
which is Provisional. The adapter classes belong to modules under
`protean.adapters`, which are Internal. Both tiers allow a change in a minor
release with no deprecation period. The element options, `domain.providers`,
`meta_.provider`, the `Database` and `Cache` enums and the entry-point group
are public. This release renames or removes them with no deprecation period.
A renamed option raises `ConfigurationError` that names the new option.
`domain.providers` and `meta_.provider` raise `AttributeError`.
