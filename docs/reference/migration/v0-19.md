# Migrating to 0.19

!!! abstract "From 0.18 to 0.19"

This page lists the changes in 0.19 that may need action when you upgrade.

**On this page:**

- [Outbox claim order](#outbox-claim-order): Rows of equal priority are claimed in the order they were written, and the `ix_outbox_active` index gains two columns
- [Outbox rows wait for their partition key's earlier rows](#outbox-rows-wait-for-their-partition-keys-earlier-rows): A new `stream_category` column and `ix_outbox_hold_back` index, and a partition key can now halt
- [`eventstore verify` exits 2 when it cannot connect](#eventstore-verify-exits-2-when-it-cannot-connect): A connection error is now a usage error, with an envelope under `--json`

## Outbox claim order

The outbox processor used to claim rows by priority alone. Rows of the same
priority came back in whatever order the database returned them, so on
PostgreSQL one aggregate's events could be published out of commit order.

`claim_batch` and `find_unprocessed` now order rows by:

1. `priority`, highest first.
2. `created_at`, oldest first.
3. `sequence_number`, lowest first.
4. `id`, lowest first.

The last key, `id`, says nothing about commit order. It only makes the order
the same on every run when the other three keys tie.

The Unit of Work now writes `sequence_number` on every outbox row. It holds
the event's position within its commit: 0 for the first event, 1 for the
next, and so on. Each database provider has its own outbox table, and the
count starts at 0 for each provider in the commit. Within a provider, the Unit
of Work numbers events one aggregate at a time, each aggregate's events in the
order it raised them. When two rows share a
`created_at`, the row with the lower number is claimed first. Every outbox row
written for one event (the internal row and one row per external broker)
carries the same number. The startup sweep that rebuilds lost outbox rows from
the event store numbers the rows it rebuilds in event store order.

### When can the claim order differ from commit order?

`created_at` is the time the Unit of Work built the row, just before the
commit. One aggregate's events go out in commit order, because a second commit
on that aggregate has to load it after the first commit finished. Rows of
different aggregates go out in the order their rows were built, which can
differ from the order their commits finished.

The claim order can also differ from commit order in these cases:

- A higher-priority message is claimed ahead of an earlier lower-priority one.
- A retried row, or a second worker, publishes events out of order. This
  does not apply to a category partitioned with `sequential_by`: a later row
  of a key waits until the key's earlier rows have published (see
  [below](#outbox-rows-wait-for-their-partition-keys-earlier-rows)).
- `created_at` comes from the clock of the host that wrote the row. If two
  hosts' clocks disagree, or a clock steps back, a later commit can get an
  earlier `created_at` and be claimed first.
- On SQL Server, Protean stores `created_at` as `DATETIME`, which rounds to
  about 3 milliseconds. Rows of two commits that land in the same tick share a
  `created_at`, and since each commit numbers its events from 0, their rows
  can interleave.

### Rows written before the upgrade

Rows already in the outbox have a NULL `sequence_number`. They are ordered by
`created_at` first, like every other row. Among rows with the same
`created_at`, a NULL `sequence_number` sorts after every number, on the
in-memory adapter and every SQL database.

To place NULLs the same way everywhere, ordering on a nullable column now puts
NULLs last when ascending and first when descending on SQLite, MySQL, MariaDB
and SQL Server. PostgreSQL and the in-memory adapter already did this. The rule
applies to every repository query that orders by a nullable field, not only to
the outbox. If a query relied on NULLs coming first in an ascending sort on one
of those databases, it now gets them last.

### Rebuild `ix_outbox_active`

The partial polling index `ix_outbox_active` now covers the claim order:
`status`, `priority DESC`, `created_at`, `sequence_number`.

- **New deployments**: Nothing to do. Tables Protean creates on 0.19 get the
  new index. A schema you manage yourself, with Alembic or by hand, needs the
  rebuild below.
- **Existing deployments**: Protean does not change an existing table's
  indexes. Claims work without the rebuild, but the old index does not cover
  the new sort. Drop and recreate the index once.

The statements below use the default table name `outbox`.

=== "PostgreSQL"

    ```sql
    DROP INDEX IF EXISTS ix_outbox_active;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number)
        WHERE status IN ('pending', 'failed');
    ```

    On a busy table, use `DROP INDEX CONCURRENTLY` and
    `CREATE INDEX CONCURRENTLY` to avoid blocking writes. Neither runs inside
    a transaction block.

=== "SQLite"

    ```sql
    DROP INDEX IF EXISTS ix_outbox_active;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number)
        WHERE status IN ('pending', 'failed');
    ```

=== "SQL Server (full index)"

    Protean builds a full index on SQL Server, without the `WHERE` filter.

    ```sql
    DROP INDEX IF EXISTS ix_outbox_active ON outbox;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number);
    ```

=== "MySQL / MariaDB (full index)"

    MySQL and MariaDB have no partial indexes, so Protean builds a full
    index there.

    ```sql
    DROP INDEX ix_outbox_active ON outbox;
    CREATE INDEX ix_outbox_active
        ON outbox (status, priority DESC, created_at, sequence_number);
    ```

## Outbox rows wait for their partition key's earlier rows

A handler category that declares
[`sequential_by`](../server/sequential-by.md) gives each outbox row a
partition key. The outbox processor used to claim and publish each row on its
own. If a key's first row failed, its second row could still publish, and the
consumer saw the two events out of commit order.

The claim now groups partitioned rows by target broker, stream category,
partition key and priority lane. A row is claimed only when every earlier row
of its group has been published, or is claimed in the same call. An earlier
row holds the later ones while it is `pending`, `processing`, `failed` or
`abandoned`. Rows without a partition key are claimed as before.

### Add the `stream_category` column

The outbox table has a new `stream_category` column. The Unit of Work copies
it from the event's `metadata.domain.stream_category` when it writes a row. A
new index, `ix_outbox_hold_back`, backs the lookup of a row's earlier group
rows.

- **New deployments**: Nothing to do. Tables Protean creates on 0.19 have the
  column and the index.
- **Existing deployments**: Protean does not change an existing table. Add the
  column before you start 0.19, because every outbox query reads it. Then
  create the index.

The statements below use the default table name `outbox`.

=== "PostgreSQL"

    ```sql
    ALTER TABLE outbox ADD COLUMN stream_category VARCHAR(255);
    CREATE INDEX ix_outbox_hold_back
        ON outbox (target_broker, stream_category, partition_key, status);
    ```

    On a busy table, use `CREATE INDEX CONCURRENTLY` to avoid blocking
    writes. It does not run inside a transaction block.

=== "SQLite"

    ```sql
    ALTER TABLE outbox ADD COLUMN stream_category VARCHAR(255);
    CREATE INDEX ix_outbox_hold_back
        ON outbox (target_broker, stream_category, partition_key, status);
    ```

=== "SQL Server"

    ```sql
    ALTER TABLE outbox ADD stream_category VARCHAR(255);
    CREATE INDEX ix_outbox_hold_back
        ON outbox (target_broker, stream_category, partition_key, status);
    ```

=== "MySQL / MariaDB"

    ```sql
    ALTER TABLE outbox ADD COLUMN stream_category VARCHAR(255);
    CREATE INDEX ix_outbox_hold_back
        ON outbox (target_broker, stream_category, partition_key, status);
    ```

### Rows already in the outbox

Rows already in the outbox have a NULL `stream_category`. The claim treats
them as rows without a partition key: they are not held, and they do not hold
later rows.

are not yet published. Protean stores each row's metadata pickled, so plain
SQL cannot read the stream category out of it. Run this function once, with

stream category is left NULL.

### A partition key can halt

A key whose earliest row is `abandoned` stops: none of its later rows publish
until someone deals with that row. A key whose earliest row is `failed` waits
until the row's retry is due. Other keys, rows without a key, and the other
priority lane keep publishing.

The cleanup job no longer deletes abandoned rows that have a partition key,
since deleting one would let the key's later rows publish out of order.

To restart a halted key, either retry the abandoned row or delete it. The
[outbox guide](../../guides/server/outbox.md#investigate-abandoned-messages)
shows how to find abandoned rows. Retrying sends the row again with a fresh
retry budget:

```sql
UPDATE outbox
SET status = 'pending', retry_count = 0, locked_by = NULL, locked_until = NULL
WHERE id = '<row id>';
```

Deleting the row drops its event for that broker, and the key's next row
publishes on the next tick:

```sql
DELETE FROM outbox WHERE id = '<row id>';
```

## `eventstore verify` exits 2 when it cannot connect

`protean eventstore verify` used to exit `1` with a logged traceback when it
could not connect to the event store. Under `--json`, stdout stayed empty.

It now exits `2`, the code for a usage or environment error:

- Under `--json`, stdout holds one [result envelope](../cli/conventions.md)
  with `status` set to `error` and the connection error under `data.error`.
- Without `--json`, the connection error is printed as one line on stderr,
  with no traceback.

A script that checked for exit `1` no longer gets it when the command cannot
connect. Other errors during the scan still exit `1` with a traceback. If a CI
job treated any non-zero exit as a failure, nothing changes for it.
