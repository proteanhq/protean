# Migrating to 0.15

!!! abstract "From 0.14 to 0.15"

Protean 0.15 is a major release. It rebuilds domain element internals on
Pydantic v2 and restructures the messaging system. It also adds a large set of
new capabilities. This guide focuses on what you need to change to upgrade.

## Required changes

These changes break your code if you do not make them.

### 1. Install Pydantic v2

Protean 0.15 requires `pydantic>=2.10,<3.0`.

```bash
uv add pydantic@">=2.10,<3.0"
# or
pip install "pydantic>=2.10,<3.0"
```

### 2. Wrap VO lists in a `ValueObject` descriptor

`from protean.fields import List` now returns a generic list factory.
If you use it to embed Value Object lists, wrap the Value Object class in a
`ValueObject` descriptor:

```python
# fragment
# Before
from protean.fields import List
items = List(content_type=OrderItem)
```

After:

```python
--8<-- "reference/migration/v0-15/001.py:value_object_list"
```

Generic `List(content_type=String)` usage is unchanged.

### 3. Remove extra kwargs from Value Object constructors

Value Objects now use `extra="forbid"`. Passing unknown keyword arguments
raises `ValidationError`:

```python
# fragment
# Before: silently ignored. Now raises ValidationError.
address = Address(street="123 Main", city="NYC", extra_field="ignored")
```

After, with `extra_field` removed:

```python
--8<-- "reference/migration/v0-15/002.py:address"
```

### 4. Replace `domain.publish()` with broker access

`domain.publish()` has been removed.

```python

domain.publish("order_events", message_dict)
```

After:


### 5. Update Message class imports and method names

The `Message` class moved from `protean.utils.mixins` to
`protean.utils.eventing`. Three methods were renamed:

| 0.14 | 0.15 |
|---|---|
| `Message.from_dict(d)` | `Message.deserialize(d)` |
| `Message.to_object()` | `Message.to_domain_object()` |
| `Message.to_message(obj)` | `Message.from_domain_object(obj)` |

`MessageRecord` has been removed, use `Message` directly.

### 6. Update message metadata access

Metadata was a flat object in 0.14. It is now grouped hierarchically:

| 0.14 | 0.15 |
|---|---|
| `msg._metadata.id` | `msg._metadata.headers.id` |
| `msg._metadata.type` | `msg._metadata.headers.type` |
| `msg._metadata.stream` | `msg._metadata.headers.stream` |
| `msg._metadata.timestamp` | `msg._metadata.headers.time` |
| `msg._metadata.fqn` | `msg._metadata.domain.fqn` |
| `msg._metadata.kind` | `msg._metadata.domain.kind` |
| `msg._metadata.payload_hash` | Removed (use `msg._metadata.envelope.checksum`) |

New groups: `headers`, `envelope`, `domain`, `event_store`, `extensions`.

### 7. Add `@apply` handlers for every event-sourced event

For `is_event_sourced=True` aggregates, `@apply` handlers are now mandatory.
They run in both the live path and during replay. Business methods must no
longer mutate state directly, only raise events.

```python
# fragment
# Before: direct mutation in business methods
@domain.aggregate(is_event_sourced=True)
class Account:
    balance = Float()

    def withdraw(self, amount):
        self.balance -= amount                 # Direct mutation
        self.raise_(Withdrawn(amount=amount))

    @apply
    def on_withdrawn(self, event):
        self.balance -= event.amount           # Only ran during replay
```

After, the `@apply` handlers make every state change. Replay starts from a
blank aggregate, so the first event's handler sets the identity and the opening
balance:

```python
--8<-- "reference/migration/v0-15/004.py:events"
--8<-- "reference/migration/v0-15/004.py:account"
```

A missing `@apply` handler now raises `IncorrectUsageError`, both in `raise_()`
and during replay. In 0.14 the same case raised `NotImplementedError` in place
of `IncorrectUsageError`. It raised that error only during replay. Code that
catches `NotImplementedError` for this case must catch `IncorrectUsageError`
instead.

### 8. Handle `from __future__ import annotations`

Annotation-style field definitions break under PEP 563 deferred evaluation. If
you use `from __future__ import annotations`, either:

- If you do not need the import, remove it, or
- Use assignment style: `name = String(max_length=50)`
- Use raw Pydantic style: `name: Annotated[str, Field(max_length=50)]`

## Behavioral changes

These won't necessarily break your code, but may change runtime behavior.

### Invariants skip when field validation fails

Pre- and post-invariants now only run if field-level validation passes.
If your tests expected both field errors and invariant errors together,
you will now see only the field errors. Fix those first, invariants evaluate
after.

### HasMany `add_*`/`remove_*` trigger pre-invariants

`add_<field>()` and `remove_<field>()` now evaluate `@invariant.pre`
checks, matching the behavior of direct assignment. You may see new
invariant errors where these methods previously bypassed checks.

### `to_dict()` vs `model_dump()`

`to_dict()` is the canonical serialization method for domain elements. Avoid
using Pydantic's `model_dump()` directly. It does not handle domain-specific
concerns correctly:

| Aspect | `to_dict()` | `model_dump()` |
|---|---|---|
| Reference fields | Skipped | May be included |
| ValueObject fields | Nested dict at domain level | Flat Pydantic output |
| DateTime values | Strings | `datetime` objects |

Always use `to_dict()` for serializing domain elements.

### Set up your IDE for annotation-style fields

Annotation-style fields may confuse type checkers.
**Pyright/Pylance:** set `"reportInvalidTypeForm": false` in
`pyrightconfig.json`. **mypy:** enable the plugin with
`plugins = ["protean.ext.mypy_plugin"]` in `pyproject.toml`.

### Re-index Elasticsearch for explicit field mappings

The Elasticsearch adapter now builds **explicit index mappings** from
aggregate/entity attributes instead of relying on Elasticsearch's dynamic
mapping. String fields are mapped as `Keyword` (exact match) by default.

**You must re-index.** Existing Elasticsearch indexes created with prior
versions use dynamic mappings where string fields are `text` with an
auto-generated `.keyword` subfield. After upgrading, queries target the field
name directly (without `.keyword`), so old indexes will return incorrect
results. After upgrading, run this code to drop and recreate your Elasticsearch
indexes:

```python
--8<-- "reference/migration/v0-15/005.py:recreate_indexes"
```

Or use the CLI: `protean db drop && protean db setup`.

**Define a custom model for full-text search.** If you need full-text search
with analyzers on specific fields, define a custom `@domain.database_model`
using `elasticsearch.dsl` field types directly:

```python

--8<-- "reference/migration/v0-15/005.py:custom_model"
```

Fields you define take precedence. The Elasticsearch adapter fills in the
unmapped attributes automatically.

## Upgrade checklist

1. Update dependencies: `uv add protean@"^0.15.0"`
2. Wrap each VO class used in a `List` for VO embedding in a `ValueObject`
   descriptor: `List(content_type=ValueObject(...))`
3. Remove extra kwargs from VO constructors
4. Replace each `domain.publish()` call with
   `domain.brokers["default"].publish()`
5. Search for `Message.from_dict`, `.to_object`, `.to_message`, rename and update imports to `protean.utils.eventing`
6. Replace each `MessageRecord` with `Message`
7. Update flat metadata access (`msg._metadata.id`, etc.) to the hierarchical
   structure
8. For ES aggregates, move each direct state mutation from business methods
   into an `@apply` handler
9. If using `from __future__ import annotations`, switch to assignment-style fields
10. If using Elasticsearch, drop and recreate indexes (mapping format changed)
11. Fix any new validation or invariant errors that your test suite reports
    when you run it

## What's new

Protean 0.15 adds many new capabilities. For full details, see the
documentation for each topic.

**Query the CQRS read side.** Use `@domain.query`, `@domain.query_handler`,
`domain.dispatch()`, `domain.view_for()` and `domain.connection_for()`, with
`ResultSet` pagination (`page`, `total_pages`, `has_next`).

**Coordinate processes across aggregates.** `@domain.process_manager`
coordinates stateful, multi-aggregate processes with event store persistence.

**Evolve and query event-sourced aggregates.** Use `@domain.upcaster` for
schema evolution, temporal queries (`repo.get(id, at_version=N)` /
`as_of=datetime`) and manual snapshots (`domain.create_snapshot()`), and test
them with the `protean.testing.given` BDD-style test DSL.

**Monitor your domain.** The `protean observatory` monitoring dashboard
provides Prometheus metrics, SSE streaming and subscription lag tracking.
`structlog` integration and FastAPI `DomainContext` middleware.

**Trace messages.** `domain.process(cmd, correlation_id="...")` propagates
`correlation_id` and `causation_id` end to end. Causation chain API and
`@domain.command_enricher` hooks.

**Recover from failures.** Replay messages from the dead letter queue, and
rebuild projections with `domain.rebuild_projection()` or the `protean
projection rebuild` CLI. Route events through two priority lanes, and make
commands idempotent with Redis (`domain.process(cmd, idempotency_key="...")`).

**Scale out to several workers.** `protean server --workers N` runs a
multi-worker supervisor.

**Set up and reset databases.** Use the database lifecycle API
(`domain.setup_database()`, `domain.truncate_database()`,
`domain.drop_database()`) or the `protean db` CLI commands. `DomainFixture`
pytest plugin. Provider registry via entry points. Adapter conformance testing.
Event store inspection CLI (`protean events`). Python 3.11–3.14 support.
